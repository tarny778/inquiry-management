# 問い合わせ管理アプリ (inquiry-management)

情報システム課が、社内各部署から受けた問い合わせを記録・管理するためのWebアプリです。
問い合わせ・調査・対応の経過を一元管理し、「あの件、どうなった?」を探しやすくすることを目指しています。

> 個人開発のポートフォリオです。画面や設計書は、すべてダミーデータを前提にしています。

## 作った背景

情報システム課には、似たような問い合わせが何度も届きます。
担当者が覚えていれば、同じ答えを繰り返すだけで済みますが、それも手間です。覚えていなければ、毎回調べ直す手間が加わります。

このアプリは、問い合わせへの回答・調査・対応を記録し、あとから活かせるようにするために作りました。

題材は、現職で使っている既存システムをモデルにせず、業務分析からゼロで考えられるものを選びました。
単純なCRUDにとどまらず、複数のテーブルが関わり、レコードの状態が変わっていく業務を扱うことで、設計の練習にもなると考えました。

## 主な機能

### 問い合わせ対応を記録する

- **問い合わせの登録・管理**: 受付経路、分類、緊急度、受付時の処理などを記録します。問い合わせ者が異動しても、どこからの問い合わせか分かるよう、問い合わせ当時の所属も保持します。
- **担当者の管理**: 受付担当者と対応担当者を記録し、受付から対応完了までを追跡します。
- **調査の管理**: 原因・仮説、情シス側の対応、問い合わせ者側に必要な対応、次回更新予定などを記録します。
- **問い合わせと調査の紐付け(多対多)**: 同じ時期に似た問い合わせが重なることや、1件の問い合わせに複数の調査が必要なことがあるため、多対多の関係にしています。

### 問い合わせ者とのやり取りを、システム上で完結させる

- 問い合わせた一般職員も、対応の進捗を自分で確認でき、調査へのリアクション(OK/NG)をシステム上で返せます。情シス職員が折り返し連絡する手間が要りません。

### 情報共有と、見たい情報が先に見える画面

- 問い合わせも調査も、一般職員を含む全職員が、すべてのレコードを参照できます。ログインしていない外部の人は、参照できません。
- 一覧画面の初期表示は、利用者ごとに切り替えます。
  - 情シス職員: 新着の問い合わせと、自分が対応すべき問い合わせ
  - 一般職員: 自分の問い合わせ

### 認証と権限

- **ログイン**: 職員番号とパスワードで認証します。パスワードは、総当たり攻撃に強い Argon2 でハッシュ化して保存します。
- **セッション**: ログイン後のセッションIDは、SHA-256 のハッシュで保存します。無操作期限と絶対有効期限を設けています。
- **権限チェック**: 担当者のみ可能な操作は、画面の制御だけでなく、API側でも権限をチェックしています。

### 主な画面

| 画面ID | 画面名 | 内容 |
|---|---|---|
| 101 | 問い合わせ詳細 | 問い合わせの確認・登録・編集 |
| 102 | 問い合わせ一覧・検索 | 問い合わせの検索・一覧表示・一括操作 |
| 201 | 調査詳細 | 調査と、関連する問い合わせごとの調査状況の確認・操作 |
| 202 | 調査一覧・検索 | 調査の検索・一覧表示 |
| 401 | ログイン | 利用者の認証 |

詳細な仕様は `docs/` の設計書を参照してください。

## 設計で意識したこと

### 「問い合わせ」と「調査」に分け、事実だけを記録する

当初は、よくある問題とそれへの回答をまとめる「問題」テーブルを設けて、システム上のFAQにすることを考えました。
しかし、問い合わせは一件ごとに少しずつ違います。この問い合わせを既存の問題に紐づけるのか、新しい問題を作るのかは、担当者の解釈に依存します。「問題の1レコードとは何か」を定義できず、行き詰まりました。

そこで、解釈を必要としない「問い合わせ」と「調査」という、事実を淡々と記録する構成にしました。
知識が蓄積しない最大の原因は「記録を残さないこと」なので、担当者が解釈で迷わないこと、気軽に記録できることを最優先にした

### 安全に使い続けられること

- パスワードはハッシュ化して保存し、セッションには無操作期限と絶対有効期限を設定
- 開発用スクリプトは、接続先DBや実行環境を確認してから動き、何度実行しても安全
- 秘密情報は環境変数で管理し、リポジトリには含めない

## ローカルでの実行方法

自分のPCで、このアプリを動かしたり、テストしたりする手順です。

### どこで何が動くか

実行の目的によって、アプリとDBが動く場所が変わります。

| やりたいこと | バックエンド / フロントエンド | DB |
|---|---|---|
| 画面を触って試す | コンテナ | コンテナ |
| API テスト(pytest) | 自分のPC(テストの中から直接呼び出す) | コンテナ |
| E2E テスト(Playwright) | 自分のPC(テスト開始時に自動で起動・終了) | コンテナ |

DBは、どの場合も、Dockerの `db` コンテナを使います(PCには、PostgreSQLを入れる必要はありません)。

使用するポートは、次のとおりです。**他のアプリや、別のコンテナが同じポートを使っていると、起動できません。**

| ポート | 用途 |
|---|---|
| 5433 | PostgreSQL(コンテナ) |
| 8000 | バックエンド(FastAPI) |
| 5173 | フロントエンド(Vite) |

画面を触って試す場合と、E2Eテストは、8000番と5173番を使うので、同時には実行できません。

### 事前に必要なもの

- Docker / Docker Compose
- Python 3.10 以上
- Node.js(E2Eテストのみ)
- [dbmate](https://github.com/amacneil/dbmate)(マイグレーションツール)

### 1. 準備(最初に1回)

リポジトリを取得し、Python の仮想環境を作って、ライブラリをインストールします。

```bash
git clone https://github.com/tarny778/inquiry-management.git
cd inquiry-management
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

次に、環境変数ファイルを作ります。`.env.docker.example` を `.env.docker` という名前でコピーし、パスワードを書き換えます。

- パスワードは、`DOCKER_POSTGRES_PASSWORD` と `DATABASE_URL` の2か所に、同じ値を書きます。
- パスワードには、英数字だけを使ってください(記号があると、URLとして読めなくなります)。

`.env.docker` は、Git の管理外です。

### 2. 画面を触って試す

1. コンテナを起動する(DB、バックエンド、フロントエンドの3つが起動します)

   ```bash
   docker compose --env-file .env.docker up -d --build
   ```

2. テーブルを作成する(DB名の入力を求められます)

   ```bash
   python scripts/dbmate_safe.py docker migrate
   ```

3. 開発用の職員データとアカウントを登録する(パスワードの入力を求められます)

   ```bash
   python scripts/setup_docker_accounts.py
   ```

4. ブラウザで開く

   | 内容 | URL |
   |---|---|
   | フロントエンド | http://localhost:5173 |
   | API(Swagger UI) | http://localhost:8000/docs |

   ログインには、手順3で登録した職員番号(`J0001`、`J0002`、`T0001`)と、入力したパスワードを使います。

5. 終わったら、コンテナを止める

   ```bash
   docker compose --env-file .env.docker stop
   ```

   DBのデータは、残ります。データごと消す場合は、`docker compose --env-file .env.docker down -v` を実行します。

### 3. テストを実行する

テストに必要なのは、DBのコンテナだけです。DBだけを起動します。

```bash
docker compose --env-file .env.docker up -d db
```

#### API テスト(pytest)

1. `.env.test.example` を `.env.test` としてコピーし、`DATABASE_URL` のパスワードを、`.env.docker` と同じ値にする
2. テスト用DBを作成して、テーブルを作る(DBがなければ自動で作成されます)

   ```bash
   python scripts/dbmate_safe.py test up
   ```

3. テストを実行する(職員データは、テストが自動で用意します)

   ```bash
   python -m pytest -v
   ```

#### E2E テスト(Playwright)

E2Eテストは、専用のDB(`inquiry_management_e2e`)と、専用の設定ファイル(`.env.e2e`)を使うので、開発用のデータには影響しません。

1. 「2 画面を触って試す」で、バックエンドとフロントエンドのコンテナを起動していた場合は、止める(ポートが重なるため)

   ```bash
   docker compose --env-file .env.docker stop backend frontend
   ```

2. `.env.e2e.example` を `.env.e2e` としてコピーし、`DATABASE_URL` のパスワードを、`.env.docker` と同じ値にする。`E2E_TEST_PASSWORD`(E2E用アカウントのパスワード)も設定する
3. E2E用DBを作成して、テーブルを作る

   ```bash
   python scripts/dbmate_safe.py e2e up
   ```

4. E2E用のアカウントを登録する(パスワードは `.env.e2e` から読み込みます)

   ```bash
   python scripts/setup_e2e_accounts.py
   ```

5. テストを実行する(初回のみ、テスト用ブラウザの取得に時間がかかります)

   ```bash
   cd frontend
   npm install
   npx playwright install
   npm run test:e2e
   ```

   テスト開始時に、バックエンドとフロントエンドが自動で起動し、終了時に自動で停止します。

これらのテストは、GitHub Actions でも、自動で実行されます。
