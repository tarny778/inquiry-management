# 20261007午後_01_要件定義

## 1. システム概要

本システムは、職員から寄せられる問い合わせを登録・管理し、対応担当者による調査、問題解決確認、問い合わせ全体の対応完了までを管理するWebアプリケーションである。

単純な問い合わせのCRUDだけではなく、

- 問い合わせ受付
- 対応担当者への引き継ぎ
- 問題ごとの調査
- 問い合わせ者による解決確認
- 未解決時の再調査
- 対応担当者変更
- 問い合わせ全体の完了

という業務フローを一貫して管理することを目的とする。

---

## 2. システムの目的

現在の問い合わせ対応では、問い合わせを受け付けた後の調査状況や、複数の問題が存在する場合の個別の対応状況を把握しにくいという課題がある。

そこで、本システムでは、

**「問い合わせ全体」と「問い合わせに含まれる個々の問題」を分けて管理する。**

これにより、

- 問い合わせ全体が現在どの段階にあるか
- その問い合わせに関連する問題は何か
- 各問題の調査がどこまで進んでいるか
- 問い合わせ者が問題解決を確認したか
- 問い合わせ全体がいつ完了したか

を明確に管理できるようにする。

---

# 3. 利用者

主な利用者は以下とする。

### 3-1. 受付担当者

問い合わせを最初に受け付ける職員。

主な操作：

- 問い合わせの登録
- 問い合わせ内容の確認
- 受付時の処理の選択

### 3-2. 対応担当者

要調査となった問い合わせを引き受け、調査・対応を行う職員。

主な操作：

- 問い合わせの引き受け
- 問題の設定
- 問題の調査
- 調査終了の記録
- 問い合わせ者への確認
- 未解決時の再調査
- 問題解決確認
- 問い合わせ全体の対応完了

### 3-3. 問い合わせ者

問い合わせを行った職員。

対応担当者からの回答を確認し、問題が解決したかどうかを判断する。

---

# 4. 問い合わせと問題の定義

## 4-1. 問い合わせ

問い合わせとは、問い合わせ者から寄せられた一回の問い合わせを、一つのライフサイクルとして管理する単位である。

一度対応完了となった問い合わせについて、後日新たな問い合わせや反応が発生した場合でも、過去の問い合わせを再開するのではなく、新しい問い合わせとして登録する。

これにより、それぞれの問い合わせのライフサイクルを独立して管理する。

## 4-2. 問題

問題とは、問い合わせの中で調査・対応が必要となった具体的な課題である。

一つの問い合わせに複数の問題が存在する場合がある。

また、同じ問題が複数の問い合わせで発生する可能性もある。

そのため、問い合わせと問題は別の情報として管理する。

---

# 5. 基本業務フロー

基本的な流れは以下とする。

```text
問い合わせ受付
    ↓
受付時の処理を判断
    │
    ├─ 即時解決
    │      ↓
    │   対応完了
    │
    ├─ 要調査
    │      ↓
    │   引き受け待ち
    │      ↓
    │   対応担当者が引き受ける
    │      ↓
    │   対応中
    │      ↓
    │   問題を設定・調査
    │      ↓
    │   問題ごとに解決確認
    │      ↓
    │   必要な問題がすべて解決確認済み
    │      ↓
    │   対応完了
    │
    └─ 他所属へ案内
           ↓
        対応完了
```

---

# 6. 受付時の処理

問い合わせ受付時には、以下の3種類から処理を判断する。

| 処理 | 内容 |
|---|---|
| 即時解決 | 受付担当者がその場で解決できる |
| 要調査 | 調査・対応担当者による対応が必要 |
| 他所属へ案内 | 本システムの対象外で、他所属へ案内して対応を終了する |

---

# 7. 問い合わせ全体の状態

問い合わせ全体の状態は、以下の3状態とする。

| 状態 | 意味 |
|---|---|
| 引き受け待ち | 要調査となったが、まだ対応担当者が引き受けていない |
| 対応中 | 対応担当者が引き受け、対応責任を持っている |
| 対応完了 | 問い合わせ全体の対応が完了している |

### 重要な設計方針

**対応担当者が引き受けた時点で、問い合わせ全体は「対応中」とする。**

引き受けた後、

- まだ具体的な問題を設定していない
- 仮の問題を設定している
- 一つの問題を調査している
- 複数の問題を調査している
- 一部の問題は解決確認済みで、別の問題を調査している

という状態であっても、問い合わせ全体としては「対応中」である。

具体的な調査状況は、`問い合わせ問題` で管理する。

---

# 8. 問い合わせ状態の判定

問い合わせ状態そのものをデータベースに保存する状態カラムは設けない。

以下の日時から状態を判断する。

### 引き受け待ち

```text
引き受け日時 IS NULL
```

### 対応中

```text
引き受け日時 IS NOT NULL
AND
対応完了日時 IS NULL
```

### 対応完了

```text
対応完了日時 IS NOT NULL
```

これにより、状態と日時情報の二重管理を避ける。

---

# 9. 即時解決

受付担当者がその場で問い合わせを解決した場合、

- 受付時の処理：即時解決
- 問い合わせ：対応完了
- 対応完了日時：登録日時

とする。

この場合、問題を登録する必要はない。

---

# 10. 他所属へ案内

問い合わせが本システムの対象外であり、他所属へ案内して対応を終了した場合、

- 受付時の処理：他所属へ案内
- 問い合わせ：対応完了
- 対応完了日時：登録日時

とする。

この場合も、問題を登録する必要はない。

---

# 11. 要調査

要調査となった問い合わせは、対応担当者の引き受けを待つ。

対応担当者が引き受けた時点で、

```text
引き受け日時を設定
```

し、問い合わせ全体を「対応中」とする。

この時点では、まだ具体的な問題が設定されていなくてもよい。

その後、対応担当者は必要に応じて問題を設定し、調査を開始する。

---

# 12. 問題単位の調査

問題ごとの対応状況は `問い合わせ問題` で管理する。

主に以下の日時を使用する。

- 調査開始日時
- 調査を終えた日時
- 未解決リアクション日時
- 問題解決確認日時

問題単位の状態は、これらの日時から判断する。

---

# 13. 問題単位の状態

| 調査終了 | 未解決リアクション | 解決確認 | 状態 |
|---|---|---|---|
| NULL | NULL | NULL | 調査中・調査が必要 |
| あり | NULL | NULL | 調査終了・問い合わせ者確認待ち |
| あり | NULL | あり | 問題解決確認済み |
| NULL | あり | NULL | 未解決リアクション後、再調査が必要 |
| あり | あり | NULL | 再調査終了・再度確認待ち |
| あり | あり | あり | 問題解決確認済み |

最も重要なルールは、

```text
調査を終えた日時 IS NULL
    → 現在は調査中・再調査が必要
```

である。

---

# 14. 未解決リアクション

問い合わせ者から「まだ解決していない」との反応があった場合、

1. 未解決リアクション日時を設定する
2. 調査を終えた日時をNULLに戻す
3. 再調査を行う
4. 再調査終了時に調査を終えた日時を設定する
5. 問い合わせ者が解決を確認したら問題解決確認日時を設定する

とする。

---

# 15. 複数問題を持つ問い合わせ

一つの問い合わせに複数の問題が関連する場合がある。

例えば、

```text
問い合わせA
 ├─ 問題A：解決確認済み
 ├─ 問題B：調査中
 └─ 問題C：確認待ち
```

という状態を許容する。

この場合、問い合わせ全体は「対応中」である。

必要な問題がすべて解決確認済みとなった時点で、問い合わせ全体を対応完了とする。

---

# 16. 問い合わせ完了

要調査の問い合わせについて、必要な問題がすべて解決確認済みとなった場合、

```text
対応完了日時
```

を設定する。

この時点で問い合わせ全体が「対応完了」となる。

対応完了日時は、最後に必要な問題について問題解決確認が行われた日時とする。

したがって、

**問題解決確認日時は問題単位のイベントであり、対応完了日時は問い合わせ全体のイベントである。**

---

# 17. 完了後の新しい問い合わせ

対応完了となった問い合わせについて、後日新たな問い合わせや反応があった場合、過去の問い合わせを再開しない。

新しい問い合わせ番号で、新しい問い合わせとして登録する。

これにより、一つの問い合わせのライフサイクルを後から変更せずに保持できる。

---

# 18. 対応担当者変更

対応中の問い合わせについて、対応担当者を変更できる。

現在の対応担当者は `問い合わせ` に保持し、変更の履歴は `対応担当者変更履歴` に保存する。

これにより、

- 現在誰が担当しているか
- 過去に誰が担当していたか
- いつ変更されたか
- 誰が変更処理を行ったか

を管理できる。

---

# 19. スナップショット情報

問い合わせ時点の事実を保持するため、以下の情報は問い合わせに保存する。

- 問い合わせ当時の所属
- 受付担当者
- 対応担当者

職員の所属変更などによって現在の職員マスタが変わっても、過去の問い合わせ記録が変化しないようにする。

# 20. 機能要件

## 問い合わせ管理

- 問い合わせを登録できる
- 問い合わせを検索できる
- 問い合わせの詳細を確認できる
- 問い合わせを更新できる

- 問題を登録できる
- 問い合わせと問題を関連付けられる

- 問題の調査終了を記録できる
- 未解決リアクションを記録できる
- 問題解決確認を記録できる

## 担当者管理

- 対応担当者を設定できる
- 対応担当者を変更できる
- 担当者変更履歴を確認できる

# 22. 今回の設計で重視する原則

本システムでは、状態を必要以上にデータとして保存しない。

特に、

**「日時から一意に判断できる状態を、別の状態カラムとして重複保存しない」**

ことを基本方針とする。

そのため、

- 問い合わせ状態 → `引き受け日時` と `対応完了日時` から判断
- 問題状態 → 問題単位の各日時から判断

とする。

これにより、状態カラムと日時の不整合を防ぐ。
