# 20261008午後_01_要件定義

## 1. システム概要

本システムは、職員から寄せられる問い合わせを登録・管理し、対応担当者による調査、問題解決確認、問い合わせ全体の対応完了までを管理するWebアプリケーションである。

単純な問い合わせのCRUDだけではなく、

- 問い合わせ受付
- 対応担当者への引き継ぎ
- 問題ごとの調査
- 問い合わせ者による解決確認
- 未解決時の再調査
- 対応担当者変更
- 問い合わせ全体の完了

という業務フローを一貫して管理することを目的とする。

---

## 2. システムの目的

現在の問い合わせ対応では、問い合わせを受け付けた後の調査状況や、複数の問題が存在する場合の個別の対応状況を把握しにくいという課題がある。

そこで、本システムでは、

**「問い合わせ全体」と「問い合わせに含まれる個々の問題」を分けて管理する。**

これにより、

- 問い合わせ全体が現在どの段階にあるか
- その問い合わせに関連する問題は何か
- 各問題の調査がどこまで進んでいるか
- 問い合わせ者が問題解決を確認したか
- 問い合わせ全体がいつ完了したか

を明確に管理できるようにする。

---

# 3. 利用者

主な利用者は以下とする。

### 3-1. 受付担当者

問い合わせを最初に受け付ける職員。

主な操作：

- 問い合わせの登録
- 問い合わせ内容の確認
- 受付時の処理の選択

### 3-2. 対応担当者

要調査となった問い合わせを引き受け、調査・対応を行う職員。

主な操作：

- 問い合わせの引き受け
- 問題の設定
- 問題の調査
- 調査終了の記録
- 問い合わせ者への確認
- 未解決時の再調査
- 問題解決確認
- 問い合わせ全体の対応完了

### 3-3. 問い合わせ者

問い合わせを行った職員。

対応担当者からの回答を確認し、問題が解決したかどうかを判断する。

---

# 4. 問い合わせと問題の定義

## 4-1. 問い合わせ

問い合わせとは、問い合わせ者から寄せられた一回の問い合わせを、一つのライフサイクルとして管理する単位である。

問い合わせ全体は、

- 引き受け待ち
- 対応中
- 対応完了

の状態を持つ。

一度対応完了となった問い合わせについても、**対応再開依頼受付期間内であれば、問い合わせ者からの再開依頼を受けて、同じ問い合わせを再開できる。**

対応再開依頼受付期間を過ぎた後に、新たな問い合わせや新たな問題が発生した場合は、過去の問い合わせを再開せず、新しい問い合わせとして登録する。

これにより、通常の問い合わせのライフサイクルを保持しながら、対応完了直後の追加確認や再対応にも対応できるようにする。

## 4-2. 問題

問題とは、問い合わせの中で調査・対応が必要となった具体的な課題である。

一つの問い合わせに複数の問題が存在する場合がある。

また、同じ問題が複数の問い合わせで発生する可能性もある。

そのため、問い合わせと問題は別の情報として管理する。

# 5. 基本業務フロー

基本的な流れは以下とする。

```text
問い合わせ受付
    ↓
受付時の処理を判断
    │
    ├─ 即時解決
    │      ↓
    │   対応完了
    │
    ├─ 要調査
    │      ↓
    │   引き受け待ち
    │      ↓
    │   対応担当者が引き受ける
    │      ↓
    │   対応中
    │      ↓
    │   問題を設定・調査
    │      ↓
    │   問題ごとに解決確認
    │      ↓
    │   対応担当者が問い合わせ全体の対応完了を判断
    │      ↓
    │   対応完了
    │
    └─ 他所属へ案内
           ↓
        対応完了
```

要調査の問い合わせでは、問い合わせ問題ごとの調査・解決確認と、問い合わせ全体の対応完了を別の処理として扱う。

**問い合わせ者による問題の解決確認だけでは、問い合わせ全体を自動的に対応完了とはしない。**

問い合わせ全体の対応完了は、対応担当者が「対応完了」と判断して操作した時点で成立する。

---

# 6. 受付時の処理

問い合わせ受付時には、以下の3種類から処理を判断する。

| 処理 | 内容 |
|---|---|
| 即時解決 | 受付担当者がその場で解決できる |
| 要調査 | 調査・対応担当者による対応が必要 |
| 他所属へ案内 | 本システムの対象外で、他所属へ案内して対応を終了する |

---

# 7. 問い合わせ全体の状態

問い合わせ全体の状態は、以下の3状態とする。

| 状態 | 意味 |
|---|---|
| 引き受け待ち | 要調査となったが、まだ対応担当者が引き受けていない |
| 対応中 | 対応担当者が引き受け、対応責任を持っている |
| 対応完了 | 対応担当者が問い合わせ全体の対応完了を判断し、対応完了日時が設定されている |

### 重要な設計方針

**対応担当者が引き受けた時点で、問い合わせ全体は「対応中」とする。**

引き受けた後、

- まだ具体的な問題を設定していない
- 仮の問題を設定している
- 一つの問題を調査している
- 複数の問題を調査している
- 一部の問題は調査無事終了し、別の問題を調査している
- 問題の調査が終了し、問い合わせ者のリアクションを待っている

という状態であっても、問い合わせ全体としては「対応中」である。

具体的な問題の調査状況や終了状況は、`問い合わせ問題` で管理する。

また、**問い合わせ問題がすべて終了した場合でも、問い合わせ全体を自動的に対応完了とはしない。**

問い合わせ全体の対応完了は、対応担当者が明示的に判断する。

---

# 8. 問い合わせ状態の判定

問い合わせ状態そのものをデータベースに保存する状態カラムは設けない。

以下の日時から状態を判断する。

### 引き受け待ち

```text
引き受け日時 IS NULL
AND
対応完了日時 IS NULL
```

### 対応中

```text
引き受け日時 IS NOT NULL
AND
対応完了日時 IS NULL
```

### 対応完了

```text
対応完了日時 IS NOT NULL
```

これにより、状態と日時情報の二重管理を避ける。

なお、対応完了後に対応再開依頼を受け付けた場合は、`対応完了日時` をNULLに戻すことで、問い合わせ全体を「対応中」に戻す。

---

# 9. 即時解決

受付担当者がその場で問い合わせを解決した場合、

- 受付時の処理：即時解決
- 問い合わせ：対応完了
- 対応完了日時：登録日時

とする。

この場合、問題を登録する必要はない。

---

# 10. 他所属へ案内

問い合わせが本システムの対象外であり、他所属へ案内して対応を終了した場合、

- 受付時の処理：他所属へ案内
- 問い合わせ：対応完了
- 対応完了日時：登録日時

とする。

この場合も、問題を登録する必要はない。

---

# 11. 要調査

要調査となった問い合わせは、対応担当者の引き受けを待つ。

対応担当者が引き受けた時点で、

```text
引き受け日時を設定
```

し、問い合わせ全体を「対応中」とする。

この時点では、まだ具体的な問題が設定されていなくてもよい。

その後、対応担当者は必要に応じて問題を設定し、調査を開始する。

問い合わせ問題の調査や解決確認が完了しても、問い合わせ全体の対応完了は自動的には行わない。

対応担当者が問い合わせ全体として対応を完了してよいと判断した時点で、「対応完了」の操作を行う。

---

# 12. 問題単位の調査

問題ごとの対応状況は `問い合わせ問題` で管理する。

主に以下の情報を使用する。

- 問い合わせ問題状態
- 調査開始日時
- 調査を終えた日時
- 最新NG日時
- リアクション要求最新日時
- 現在の調査状況
- 次回更新予定日時
- 問題との関連情報

`調査を終えた日時` は、単に一回の調査作業を終了した日時ではない。

**問い合わせ問題と問題との関係を最終的に終了した日時**を意味する。

そのため、問い合わせ者にリアクションを要求した時点では設定せず、問い合わせ者がOKした場合、または調査断念となった場合に設定する。

---

# 13. 問題単位の状態

問い合わせ問題の状態は、`問い合わせ問題状態` カラムで管理する。

状態は、以下の4状態とする。

| 状態 | 意味 |
|---|---|
| 調査中 | 問題について調査・対応が必要な状態 |
| リアクション待ち | 調査を一旦終え、問い合わせ者による確認を待っている状態 |
| 調査無事終了 | 問い合わせ者からOKのリアクションを受け、この問い合わせにおける問題との関係を終了した状態 |
| 調査断念 | この問い合わせについて、この問題との関連調査を終了した状態 |

状態遷移は以下とする。

```text
調査中
  ↓
リアクション要求
  ↓
リアクション待ち
  ↓
問い合わせ者OK
  ↓
調査無事終了
```

未解決の場合：

```text
リアクション待ち
  ↓
問い合わせ者NG
  ↓
調査中
  ↓
再調査
  ↓
リアクション待ち
```

調査を継続しない場合：

```text
調査中 または リアクション待ち
  ↓
調査断念
```

`調査を終えた日時` は、リアクション要求時や調査中には設定しない。

問い合わせ者がOKした場合は、`調査無事終了` とし、`調査を終えた日時` に現在日時を設定する。

調査断念の場合は、`調査断念` とし、`調査を終えた日時` に現在日時を設定する。

問い合わせ者がNGした場合は、`調査中` に戻り、再調査を行う。

この場合、`調査を終えた日時` は、OKまたは調査断念となるまでNULLである。

---

# 14. 未解決リアクション

問い合わせ者から「まだ解決していない」との反応があった場合、

1. 問い合わせ問題状態を「調査中」に戻す
2. `最新NG日時` に現在日時を設定する
3. 再調査を行う
4. 再調査終了時に、再度リアクションを要求する
5. `リアクション要求最新日時` を更新する
6. 問い合わせ者がOKしたら、問い合わせ問題状態を「調査無事終了」とする
7. `調査を終えた日時` に現在日時を設定する

`調査を終えた日時` は、問い合わせ者がOKするか、調査断念となるまでNULLとする。

`現在の調査状況` は、対応担当者が実際の調査内容を記録するための項目であり、未解決リアクションを受けたことだけを理由に、システムが特定の文言へ自動変更することはしない。

---



# 15. 複数問題を持つ問い合わせ

一つの問い合わせに複数の問題が関連する場合がある。

例えば、

```text
問い合わせA
 ├─ 問題A：調査無事終了
 ├─ 問題B：調査中
 └─ 問題C：リアクション待ち
```

という状態を許容する。

この場合、問い合わせ全体は「対応中」である。

また、

```text
問い合わせA
 ├─ 問題A：調査無事終了
 ├─ 問題B：調査無事終了
 └─ 問題C：調査断念
```

のように、関連する問題がすべて終了している場合でも、問い合わせ全体を自動的に対応完了とはしない。

**問い合わせ全体の対応完了は、対応担当者が問い合わせ全体を確認したうえで明示的に判断する。**

---

# 16. 問い合わせ完了

要調査の問い合わせについて、対応担当者が問い合わせ全体の対応状況を確認し、「これで対応完了としてよい」と判断した場合、画面上で「対応完了」の操作を行う。

この操作によって、

```text
問い合わせ.対応完了日時
```

に現在日時を設定する。

これにより、問い合わせ全体の状態が、

```text
対応中
↓
対応完了
```

となる。

重要な設計方針として、

**問題単位の「調査無事終了」と、問い合わせ全体の「対応完了」は別のイベントとして扱う。**

したがって、

```text
問い合わせ者が問題についてOK
    ↓
問い合わせ問題：調査無事終了
    ↓
対応担当者が問い合わせ全体を確認
    ↓
「対応完了」を操作
    ↓
問い合わせ：対応完了
```

という流れになる。

問い合わせ者が問題についてOKしただけでは、`問い合わせ.対応完了日時` は自動的には設定しない。

また、対応完了日時は問題解決確認日時をそのまま利用するのではなく、**対応担当者が対応完了操作を行った日時**とする。

---

# 17. 対応完了後の再開と新しい問い合わせ

対応完了となった問い合わせについては、一定期間、問い合わせ者からの対応再開依頼を受け付ける。

この期間を**対応再開依頼受付期間**とする。

具体的な期間の長さ、営業日基準とするかどうかなどは、別途決定する。

## 17-1. 対応再開依頼受付期間内の再開

対応完了後、対応再開依頼受付期間内に問い合わせ者から再開依頼があった場合は、過去の問い合わせを再利用して対応を再開する。

再開時には、

```text
問い合わせ.対応完了日時
        ↓
NULL
```

とする。

これにより、問い合わせ全体の状態は、

```text
対応完了
↓
対応中
```

に戻る。

再開された問い合わせについては、現在の対応担当者へ再対応が必要であることを通知する。

再開後は、必要に応じて既存の問い合わせ問題を再調査するなどして対応する。

## 17-2. 対応再開依頼受付期間終了後

対応再開依頼受付期間を過ぎた後に、新たな問い合わせや新たな問題が発生した場合は、対応完了した過去の問い合わせを再開しない。

新しい問い合わせ番号で、新しい問い合わせとして登録する。

これにより、

- 対応完了後の一定期間内は、同じ問い合わせとして再対応できる
- 一定期間を過ぎた新たな問い合わせは、新しい問い合わせとして管理する

というルールを明確にする。

---

# 18. 対応担当者変更

対応中の問い合わせについて、対応担当者を変更できる。

現在の対応担当者は `問い合わせ` に保持し、変更の履歴は `対応担当者変更履歴` に保存する。

これにより、

- 現在誰が担当しているか
- 過去に誰が担当していたか
- いつ変更されたか
- 誰が変更処理を行ったか

を管理できる。

---

# 19. スナップショット情報

問い合わせ時点の事実を保持するため、以下の情報は問い合わせに保存する。

- 問い合わせ当時の所属
- 受付担当者
- 対応担当者

職員の所属変更などによって現在の職員マスタが変わっても、過去の問い合わせ記録が変化しないようにする。

# 20. 機能要件

## 問い合わせ管理

- 問い合わせを登録できる
- 問い合わせを検索できる
- 問い合わせの詳細を確認できる
- 問い合わせを更新できる
- 問い合わせ全体の対応完了を記録できる
- 対応完了後、対応再開依頼受付期間内であれば問い合わせを再開できる
- 対応再開依頼を受けた問い合わせについて、現在の対応担当者へ再対応を通知できる
- 問い合わせを削除する場合のルールを設ける

## 問題管理

- 問題を登録できる
- 問い合わせと問題を関連付けられる
- 問い合わせ問題の状態を管理できる
- 問題ごとの調査状況を更新できる
- 問い合わせ者からの未解決リアクションを記録できる
- 問い合わせ者からのOKを受け、問い合わせ問題を「調査無事終了」として記録できる
- 問い合わせについて問題との関連調査を断念し、「調査断念」として記録できる
- 問い合わせ問題の調査を開始した日時を記録できる
- 問い合わせ問題との関係を終了した日時を記録できる
- 最新のNG日時を記録できる
- リアクションを要求した最新日時を記録できる

## 担当者管理

- 対応担当者を設定できる
- 対応担当者を変更できる
- 担当者変更履歴を確認できる

# 22. 状態管理に関する設計方針

本システムでは、状態の管理方法を対象となる情報の性質に応じて定める。

### 問い合わせ全体の状態

問い合わせ全体の状態は、`問い合わせ状態` のような状態カラムを設けず、

- `引き受け日時`
- `対応完了日時`

から判断する。

```text
引き受け日時 IS NULL
AND
対応完了日時 IS NULL
    → 引き受け待ち

引き受け日時 IS NOT NULL
AND
対応完了日時 IS NULL
    → 対応中

対応完了日時 IS NOT NULL
    → 対応完了
```

これにより、問い合わせ全体の状態と日時情報の二重管理を避ける。

### 問い合わせ問題の状態

問い合わせ問題については、問い合わせ全体とは異なり、`問い合わせ問題状態` カラムを設けて状態を管理する。

問い合わせ問題状態は、

- 調査中
- リアクション待ち
- 調査無事終了
- 調査断念

の4状態とする。

問い合わせ問題の状態は、各日時から推測するのではなく、業務上の判断結果として `問い合わせ問題状態` を更新する。

一方、

- `調査開始日時`
- `調査を終えた日時`
- `最新NG日時`
- `リアクション要求最新日時`

などの日時は、状態そのものを表すためではなく、それぞれの業務上のイベントが発生した日時を記録するために保持する。

したがって、

**問い合わせ全体の状態は日時から判断し、問い合わせ問題の状態は状態カラムで管理する。**

それぞれの情報の性質に応じて管理方法を分けることで、状態と日時の意味を明確にする。
