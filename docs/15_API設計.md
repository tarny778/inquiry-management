# API設計（現行版）

## 1. 本書の範囲

本書は、現行のFastAPI実装のうち、現行仕様として扱うエンドポイントを整理する。

## 2. 共通仕様

### 2.1 認証と権限

認証必須APIは `session_id` Cookieを検証し、ログイン中の職員番号・氏名・所属を取得する。操作者職員番号をリクエストから受け取らない。未認証、失効、期限切れ、ログイン不可は401。

情シス職員限定操作、受付担当者・対応担当者本人操作、問い合わせ者本人の回答はAPI側で検証する。権限不足は403、レコード不存在は404、状態不一致・期限切れ・重複等は409を基本とする。入力検証は422。職員不存在・重複番号など一部の業務エラーは400。

エラーはFastAPI形式の `{"detail": ...}` を返す。detailは文字列または、一括処理対象番号などを含むオブジェクトの場合がある。入力検証エラーは422のdetail配列。

### 2.2 トランザクション

状態変更時は対象行をロックして、存在・状態・権限を確認してから更新する。一括処理は全件の検証成功時だけ更新する。NG回答と移行先作成・関連付けは一つのトランザクションで処理する。

### 2.3 ページングと日時

一覧APIは `page`（初期値1）、`page_size`（初期値50、1〜100）を受け取る。日時はISO 8601のタイムゾーン付き文字列で送受信する（例：`2026-10-28T10:00:00+09:00`）。オフセットなしの日時は422とする。バックエンドでは日時をUTCに正規化し、DBでは業務日時・認証日時ともにTIMESTAMPTZへ保存する。画面では日本時間で表示する。

## 3. 認証API

| メソッド・パス | 認証 | 概要 |
|---|---|---|
| GET `/api/auth/me` | 必須 | セッション中の職員情報を返す |
| POST `/api/auth/login` | 不要 | 職員番号・パスワードで認証しセッションCookieを発行 |
| POST `/api/auth/logout` | 不要 | Cookieセッションを失効しCookieを削除 |

### 3.1 ログイン

リクエストは `職員番号`（1〜20文字）と `パスワード`（1〜128文字）。空白だけの値は無効。アカウント不存在、ログイン不可、パスワード不一致は同じ401応答とする。成功時は `message`、職員番号、氏名、所属を返し、セッションIDはレスポンス本文ではなくCookieへ設定する。

Cookie属性：HttpOnly、SameSite=Lax、Path=/、最大有効期間12時間。Secureは `ENVIRONMENT=production` の場合に設定する。DBにはIDのSHA-256ハッシュのみ保存する。

### 3.2 セッション確認

`GET /api/auth/me` は有効セッションの職員番号、氏名、所属を返す。セッションの無操作期限を30分延長するが、ログインから12時間の絶対期限を超えない。無効なセッションは401。

### 3.3 ログアウト

Cookieがある場合は該当セッションを失効する。Cookieがない場合も200でログアウト結果を返し、Cookie削除を指示する。

## 4. 問い合わせAPI

| メソッド・パス | 用途 |
|---|---|
| POST `/api/inquiries` | 問い合わせ登録 |
| PUT `/api/inquiries/{inquiry_number}` | 問い合わせ編集 |
| GET `/api/inquiries` | 問い合わせ検索・一覧 |
| GET `/api/inquiries/{inquiry_number}` | 問い合わせ詳細 |
| POST `/api/inquiries/bulk-accept` | 選択問い合わせの一括引き受け |
| POST `/api/inquiries/bulk-complete` | 選択問い合わせの一括完了 |
| POST `/api/inquiries/{inquiry_number}/reopen` | 対応再開 |
| POST `/api/inquiries/bulk-investigations` | 複数問い合わせへ新規調査作成・関連付け |
| POST `/api/inquiries/bulk-link-investigation` | 複数問い合わせを既存調査へ関連付け |

### 4.1 問い合わせ登録

認証必須。情シス職員のみ登録可能。入力項目：問い合わせ職員番号、受付経路（電話・メール・フォーム）、分類（分類A/B/C）、件名、緊急度（1〜3）、受付時の処理（1〜3）、任意の問い合わせ詳細、条件付き受信日時。必須文字列の空白だけの値は無効。メール・フォームは受信日時必須、電話は受信日時を指定しない。

問い合わせ者の存在と所属を確認し、問い合わせ当時の所属を保存する。ログインユーザーを受付担当者とする。電話の受信日時、登録日時はサーバーで設定する。処理1または3は登録時に対応完了日時を設定する。成功は200でメッセージと問い合わせ番号を返す。

主なエラー：400 職員不存在・所属不正、401 未認証、403 情シス職員以外、422 入力不正。

### 4.2 問い合わせ編集

認証必須。リクエストは登録項目に加え `受信日時` を必須とする。追加項目は拒否し、文字列空白は正規化する。引き受け待ちは受付担当者本人、対応中は対応担当者本人のみ編集できる。対応完了は編集不可。対応中は受付時の処理を変更できない。未引き受け中の処理を1または3に変えた場合は完了日時を設定する。

成功は200で問い合わせ番号を返す。主なエラー：400 問い合わせ者不存在・所属不正、401、403、404、409 状態や変更制限違反、422 入力不正。

### 4.3 問い合わせ検索

認証必須。`初期条件` は必須で1または2。ほかに `問い合わせ番号`、`問い合わせ職員番号`、`問い合わせ当時の所属`、複数値 `受付経路`、`問い合わせ分類`、`件名`、`緊急度`、`受付担当者`、`対応担当者`、複数値 `状態`、`受信日時開始`、`受信日時終了`、`page`、`page_size` を受け取る。

- 初期条件1では、利用者区分に応じた初期範囲だけを検索し、ほかの検索条件を適用しない。
- 初期条件2では、指定された検索条件だけを適用する。未指定なら全件対象。
- 文字列の所属・件名は部分一致。異なる検索項目はAND、状態・受付経路内の複数値はOR。
- 受信日時開始・終了の両方がある場合、開始は終了以前。
- 受信日時降順、問い合わせ番号降順で返す。

レスポンスは `items`、`page`、`page_size`、`total`。各itemは問い合わせ番号、問い合わせ者番号、当時の所属、受付経路、分類、件名、緊急度、受付担当者、対応担当者、受信日時、導出状態を含む。

主なエラー：400 ログイン職員が職員テーブルに存在しない、401、422 クエリ不正。

### 4.4 問い合わせ詳細

認証必須、問い合わせ番号は1以上。詳細項目、導出状態、関連調査番号一覧を返す。不存在は404、番号不正は422。

### 4.5 一括引き受け

リクエスト：`{"問い合わせ番号一覧": [整数, ...]}`。空配列不可。情シス職員のみ。重複番号は400、対象不存在は404、引き受け不能状態は409。対象を番号順にロックし、すべて未引き受け・未完了の場合だけ、操作者を対応担当者として引き受け日時を設定する。成功時は更新した番号一覧と担当者・日時を返す。

### 4.6 一括完了

リクエストは一括引き受けと同じ形。重複は400、対象不存在は404、本人担当でない場合は403、未引き受け・完了済み・未完了の問い合わせ調査（状態1または3）が残る場合は409。全件を番号順にロックし、すべての検証成功時だけ対応完了日時を設定する。

### 4.7 対応再開

`POST /api/inquiries/{inquiry_number}/reopen`。認証必須。対応完了済みであること、ログインユーザーが現在の対応担当者であること、対応完了から7日未満であることを確認する。対応完了日時のみNULLにする。成功は200。不存在404、担当者本人でない403、未完了・期限切れ409、番号不正422。

### 4.8 一括調査作成・関連付け

`POST /api/inquiries/bulk-investigations`。リクエストは問い合わせ番号一覧（1件以上、正数、重複不可）と調査の名称（1〜30文字、空白のみ不可）。すべての問い合わせが対応中かつ操作者が各担当者本人である場合だけ、新規調査1件と状態1の関係を各問い合わせに作成する。主なエラー：401、403、404、409、422。成功時は調査番号、名称、関連付け件数と一覧を返す。

### 4.9 既存調査への一括関連付け

`POST /api/inquiries/bulk-link-investigation`。リクエストは問い合わせ番号一覧と正数の調査番号。対象調査が状態1であること、全問い合わせが対応中かつ操作者本人担当であること、対象関係が重複しないことを検証後、状態1の関係を一括作成する。主なエラー：401、403、404、409、422。

## 5. 調査API

| メソッド・パス | 用途 |
|---|---|
| GET `/api/investigations` | 調査検索・一覧 |
| GET `/api/investigations/{investigation_id}` | 調査詳細 |
| PATCH `/api/investigations/{investigation_id}` | 調査編集 |
| POST `/api/investigations/{investigation_id}/abandon` | 調査全体の断念 |
| POST `/api/investigations/{investigation_id}/request-reaction` | リアクション要求 |
| POST `/api/investigations/relations/{relation_id}/abandon` | 問い合わせ調査の個別断念 |
| POST `/api/investigations/relations/{relation_id}/ok` | 問い合わせ者のOK回答 |
| POST `/api/investigations/relations/{relation_id}/ng` | 問い合わせ者のNG回答・移行 |

### 5.1 調査検索

認証必須。任意クエリ：`調査番号`（1以上）、`調査の名称`（部分一致、前後空白を除去。空白のみは未指定）、`調査状態`（1〜3）、`問い合わせ番号`（1以上）、`問い合わせ職員番号`、`問い合わせ状態`（引き受け待ち・対応中・対応完了）、`対応担当者職員番号`、`page`、`page_size`。

複数条件はAND。関連問い合わせ条件はEXISTSで検索し、調査単位で重複させない。検索対象をログイン職員で制限しない。初期条件は画面が問い合わせ職員番号または対応担当者番号と問い合わせ状態を指定して実現する。

成功レスポンスは `items`、`page`、`page_size`、`total`。itemは調査番号、調査の名称、調査状態、最小の関連問い合わせ番号に対応する担当者職員番号、関連問い合わせ件数、自分の問い合わせを含むかを返す。並び順は調査開始日時降順、調査番号降順。主なエラー：401、422。

### 5.2 調査詳細

認証必須。調査基本情報に加え、関連する問い合わせ調査の配列を返す。配列には問い合わせ番号、問い合わせ者氏名、対応担当者氏名、関係状態、各日時、回答内容、移行先番号、問い合わせ者・担当者の職員番号を含む。`自分の問い合わせを含む` も返す。不存在404、番号不正422。

### 5.3 調査編集

認証必須。PATCH本文は名称、原因・仮説、情シス側対応、問い合わせ者側で必要な対応、予定日時。未指定項目は維持する。名称の空文字・空白のみ・nullは不可。任意テキストの空白のみはnullへ正規化する。更新項目なし、余分な項目、長さ・日時不正は422。

調査が状態1で、関連問い合わせがあり、担当者条件を満たす場合だけ編集可能。権限不足403、対象なし404、状態不一致409。

### 5.4 調査断念

認証必須。調査状態1であること、関連関係状態が1または2のみであること、関連問い合わせの担当者本人であることを確認する。調査を状態3にし、断念日時を記録する。関連する状態1の関係を状態2にし断念日時を記録する。状態不一致409、権限不足403、対象なし404、データ整合性異常500。

### 5.5 リアクション要求

認証必須。調査状態1、少なくとも一件の関係があり、関係状態が1または2のみであることを確認する。調査を状態2にし要求日時を記録し、状態1の関係を状態3にして要求日時を設定する。状態2の関係は維持する。主なエラー：403、404、409、422、データ整合性異常時500。

### 5.6 個別断念

`relation_id` は1以上。親調査が状態1、関係が状態1、操作者が対象問い合わせの対応担当者本人の場合に、関係を状態2へ変更し断念日時を記録する。主なエラー：401、403、404、409、422。

### 5.7 OK回答

`relation_id` は1以上。対象問い合わせの問い合わせ者本人で、関係が状態3の場合に、関係を状態4、リアクション内容1として回答日時を記録する。主なエラー：401、403、404、409、422。

### 5.8 NG回答

`relation_id` は1以上。対象問い合わせの問い合わせ者本人で、関係が状態3であることをロック下で確認する。元関係を状態5、内容2として回答日時と移行先を記録し、進行中の最新移行先を再利用または新規調査を作成して状態1の関係を登録する。すでに同じ問い合わせが移行先に関連付いていれば409とし、すべてロールバックする。主なエラー：401、403、404、409、422。

## 6. エラーコード概要

| HTTP | 用途 |
|---:|---|
| 400 | 一部APIの業務入力不正、重複番号、操作者データ不整合 |
| 401 | 未認証または有効なセッションなし |
| 403 | 職員区分・担当者・問い合わせ者の権限不足 |
| 404 | 指定された問い合わせ、調査、関係が存在しない |
| 409 | 状態不一致、競合、期限切れ、重複関連付け |
| 422 | 型、必須値、許容範囲、パス・クエリ・本文の検証エラー |
| 500 | 一部の複合操作でデータ整合性異常を検出した場合 |

具体的にどのエラーが返るかは各APIの条件を適用する。一括処理では `detail` に該当番号の一覧を含む場合がある。

## 7. 将来機能

メール通知、メール・フォームからの取り込み、CSV出力、FAQ整理支援、担当者変更履歴、論理削除のAPIは、将来構想であり現行仕様に含まない。
