# API設計書（API01〜API２３）

## 1. 共通仕様

### 1.1 認証

認証必須APIでは、`get_current_user()` を通じてログイン中の職員情報を取得する。

ログイン中の職員情報は、以下の項目を持つ。

- 職員番号
- 氏名
- 所属

操作者の職員番号はリクエスト本文やクエリパラメータから受け取らず、ログイン情報から取得する。

未ログイン、セッション失効、セッション期限切れなどの場合はHTTP 401を返す。

### 1.2 リクエストの検証

Pydanticの入力スキーマで、データ型、必須項目、文字数、選択肢などを検証する。

`extra="forbid"` を設定したスキーマでは、定義されていない項目をリクエストに含めることはできない。

入力スキーマの検証エラーは、原則としてHTTP 422となる。

### 1.3 一括処理

一括処理では、対象レコードの存在、状態、権限などを確認してから更新する。

一部だけが更新される状態を避けるため、全件の検証に成功した場合にのみ更新処理を実行する。

### 1.4 日時

日時はJSONではISO 8601形式の文字列として送受信する。

例：`2026-10-17T09:30:00`

実際のタイムゾーン表現は、実装で使用する日時の値に従う。

## 2. API01：問い合わせ登録

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries`

### リクエスト

```json
{
  "問い合わせ職員番号": "T0001",
  "受付経路": "メール",
  "問い合わせ分類": "分類A",
  "件名": "メールが送信できない",
  "緊急度": 2,
  "受付時の処理": 2,
  "問い合わせ詳細": "メール送信時にエラーが発生する",
  "受信日時": "2026-10-17T09:30:00"
}
```

| 項目 | 必須 | 検証・条件 |
|---|---|---|
| 問い合わせ職員番号 | 必須 | 1〜20文字。職員テーブルに存在すること |
| 受付経路 | 必須 | 電話、メール、フォーム |
| 問い合わせ分類 | 必須 | 分類A、分類B、分類C |
| 件名 | 必須 | 1〜100文字 |
| 緊急度 | 必須 | 1、2、3 |
| 受付時の処理 | 必須 | 1、2、3 |
| 問い合わせ詳細 | 任意 | null可。指定する場合は1〜1000文字 |
| 受信日時 | 条件付き | メール・フォームは必須。電話では指定不可 |

### バックエンド処理

1. リクエストの型、必須項目、文字数、選択肢を検証する。
2. 問い合わせ職員番号が職員テーブルに存在することを確認する。
3. 問い合わせ職員の所属を取得し、問い合わせ当時の所属として保存する。
4. ログイン中の職員を受付担当者とする。
5. 受付担当者が職員テーブルに存在し、所属が情報システム課であることを確認する。
6. 登録日時、受信日時、対応完了日時を決定する。
7. 問い合わせを登録し、自動採番された問い合わせ番号を取得する。

日時と状態のルール：

- 電話の場合、受信日時はバックエンドで現在日時を設定する。
- メール・フォームの場合、受信日時はリクエストで指定する。
- 受付時の処理が1または3の場合、対応完了日時を現在日時とする。
- 受付時の処理が2の場合、対応完了日時はnullとする。
- 登録時点では、引き受け日時はnull、対応担当者もnullとする。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問い合わせを登録しました",
  "問い合わせ番号": 123
}
```

`123` は例示用の問い合わせ番号。

### 主なエラー

- 400：問い合わせ職員が存在しない、所属が不正、受付担当者が存在しない、受付担当者が情報システム課ではない
- 401：未認証
- 422：リクエストの型・必須項目・文字数・選択肢・受信日時の条件が不正

## 3. API02：問い合わせの個別引き受け

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/{inquiry_number}/accept`

### リクエスト

本文なし。問い合わせ番号はパスで指定する。

例：

```http
POST /api/inquiries/123/accept
```

### バックエンド処理

1. ログイン中の職員を対応担当者とする。
2. 操作者が職員テーブルに存在し、情報システム課に所属していることを確認する。
3. 引き受け日時を取得する。
4. 引き受け日時と対応完了日時がともにnullの問い合わせだけを更新する。
5. 更新できなかった場合は、対象の不存在と状態不整合を区別する。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問い合わせを引き受けました",
  "問い合わせ番号": 123,
  "対応担当者": "J0001",
  "引き受け日時": "2026-10-17T09:30:00"
}
```

### 主なエラー

- 400：操作者が職員テーブルに存在しない
- 401：未認証
- 403：操作者が情報システム課ではない
- 404：指定された問い合わせが存在しない
- 409：すでに引き受け済み、対応完了済みなど、引き受けできない状態
- 422：問い合わせ番号が1未満など、パスパラメータが不正

## 4. API03：問い合わせの一括引き受け

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/bulk-accept`

### リクエスト

```json
{
  "問い合わせ番号一覧": [123, 124, 125]
}
```

- `問い合わせ番号一覧` は必須。
- 1件以上指定する。
- 同じ問い合わせ番号を重複指定できない。

### バックエンド処理

1. ログイン中の職員の存在と所属を確認する。
2. 情報システム課の職員であることを確認する。
3. 問い合わせ番号の重複を確認する。
4. 対象レコードを問い合わせ番号順にロックして取得する。
5. 指定された番号がすべて存在することを確認する。
6. 全件が未引き受け・未完了であり、対応担当者も未設定であることを確認する。
7. 全件の検証に成功した場合のみ、対応担当者と引き受け日時を更新する。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問い合わせを一括で引き受けました",
  "対応担当者": "J0001",
  "問い合わせ番号一覧": [123, 124, 125],
  "引き受け日時": "2026-10-17T09:30:00"
}
```

### 主なエラー

- 400：操作者が存在しない、問い合わせ番号が重複している
- 401：未認証
- 403：情報システム課ではない
- 404：指定された問い合わせが存在しない。レスポンスのdetailに不足している番号一覧を含む
- 409：引き受けできない状態の問い合わせが含まれている
- 422：リクエストの型・必須項目が不正

## 5. API04：問い合わせの個別対応完了

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/{inquiry_number}/complete`

### リクエスト

本文なし。問い合わせ番号をパスで指定する。

### バックエンド処理

1. 対象問い合わせをロックして取得する。
2. 問い合わせが存在することを確認する。
3. 引き受け済みであり、対応完了していないことを確認する。
4. ログイン中の職員が現在の対応担当者本人であることを確認する。
5. 関連する問い合わせ問題調査の状態を確認する。
6. 完了条件を満たす場合、対応完了日時を記録する。

業務ルール：

- 未引き受けの問い合わせは対応完了できない。
- すでに対応完了している問い合わせは再度完了できない。
- 対応担当者本人だけが完了できる。
- 関連する問い合わせ問題調査に状態1「調査中」または状態3「リアクション待ち」が残っている場合は完了できない。
- 状態2「断念」、状態4「OK」、状態5「NG」は、この完了チェックにおける未完了状態には該当しない。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問い合わせを対応完了しました。",
  "問い合わせ番号": 123
}
```

### 主なエラー

- 401：未認証
- 403：対応担当者本人ではない
- 404：問い合わせが存在しない
- 409：未引き受け、すでに対応完了、未完了の問題調査が残っている

## 7. API06：問い合わせの再開

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/{inquiry_number}/reopen`

### リクエスト

本文なし。問い合わせ番号をパスで指定する。

### バックエンド処理

1. 対象問い合わせをロックして取得する。
2. 問い合わせが存在することを確認する。
3. 対応完了済みであることを確認する。
4. ログイン中の職員が対応担当者本人であることを確認する。

### 成功レスポンス：HTTP 200

```json
{

  "問い合わせ番号": 123
}
```

### 主なエラー

- 401：未認証
- 403：対応担当者本人ではない
- 404：問い合わせが存在しない
- 409：対応完了していない、または再開可能期間を過ぎている
- 422：問い合わせ番号が不正

## 8. API07：問い合わせに問題調査を新規作成・関連付け

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/{inquiry_number}/investigations`

### リクエスト

```json
{
  "問題調査の名称や仮説": "メール送信エラーの原因調査"
}
```

- `問題調査の名称や仮説` は必須。
- 1〜30文字。
- 前後の空白を除いた結果が空文字になる値は不可。

### バックエンド処理

1. 対象問い合わせをロックして取得する。
2. 問い合わせが存在することを確認する。
3. 問い合わせが対応中であることを確認する。
4. ログイン中の職員が対応担当者本人であることを確認する。
5. 問題調査レコードを新規作成する。
6. 問い合わせ問題調査レコードを作成し、問い合わせと関連付ける。

問題調査と問い合わせは別のライフサイクルとして管理し、関連付けレコードによって関係を表す。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問題調査を作成し、問い合わせに関連付けました。",
  "問い合わせ番号": 123,
  "問題調査番号": 45,
  "問い合わせ問題調査番号": 67,
  "問題調査の名称や仮説": "メール送信エラーの原因調査"
}
```

### 主なエラー

- 401：未認証
- 403：対応担当者本人ではない
- 404：問い合わせが存在しない
- 409：問い合わせが対応中ではない
- 422：問題調査の名称や仮説が不正

## 9. API08：既存の問題調査を問い合わせに個別関連付け

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/{inquiry_number}/investigations/{investigation_number}`

### リクエスト

本文なし。問い合わせ番号と問題調査番号をパスで指定する。

例：

```http
POST /api/inquiries/123/investigations/45
```

### バックエンド処理

1. 問題調査をロックし、存在することと状態1「調査中」であることを確認する。
2. 問い合わせをロックし、存在することと対応中であることを確認する。
3. ログイン中の職員が対象問い合わせの対応担当者本人であることを確認する。
4. その問題調査に既に関連付けられている問い合わせを取得する。
5. 既存の関連問い合わせが存在し、その対応担当者が全員ログイン中の職員本人であることを確認する。
6. 同じ問い合わせと問題調査の組み合わせが既に登録されていないことを確認する。
7. 問い合わせ問題調査レコードだけを追加する。問題調査そのものは新規作成しない。

### 成功レスポンス：HTTP 200

```json
{
  "message": "既存の問題調査を問い合わせに関連付けました。",
  "問い合わせ番号": 123,
  "問題調査番号": 45,
  "問い合わせ問題調査番号": 68
}
```

### 主なエラー

- 401：未認証
- 403：対象問い合わせの対応担当者本人ではない、または既存の関連問い合わせの担当者が一致しない
- 404：問い合わせまたは問題調査が存在しない
- 409：問題調査が調査中ではない、問い合わせが対応中ではない、既存の関連付けがない、または重複関連付け
- 422：パスパラメータが不正

## 10. API09：複数の問い合わせに問題調査を新規作成・関連付け

### エンドポイント

- メソッド：`POST`
- パス：`/api/inquiries/bulk-investigations`

### リクエスト

```json
{
  "問い合わせ番号一覧": [123, 124, 125],
  "問題調査の名称や仮説": "メール送信エラーの原因調査"
}
```

- 問い合わせ番号一覧は必須で、1件以上。
- 問い合わせ番号は1以上。
- 問い合わせ番号の重複指定は不可。
- 問題調査の名称や仮説は必須で、1〜30文字。空白だけの値は不可。

### バックエンド処理

1. 対象問い合わせを問い合わせ番号順にロックして取得する。
2. 指定された問い合わせがすべて存在することを確認する。
3. すべての問い合わせが対応中であることを確認する。
4. すべての問い合わせの対応担当者がログイン中の職員本人であることを確認する。
5. 問題調査を1件だけ新規作成する。
6. すべての問い合わせに対して問い合わせ問題調査レコードを作成する。

複数の問い合わせから同じ問題調査を共有するため、問題調査レコードは1件、関連付けレコードは対象問い合わせごとに作成する。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問題調査を作成し、複数の問い合わせに関連付けました。",
  "問題調査番号": 45,
  "問題調査の名称や仮説": "メール送信エラーの原因調査",
  "関連付け件数": 3,
  "関連付け一覧": [
    {
      "問い合わせ番号": 123,
      "問い合わせ問題調査番号": 67
    },
    {
      "問い合わせ番号": 124,
      "問い合わせ問題調査番号": 68
    },
    {
      "問い合わせ番号": 125,
      "問い合わせ問題調査番号": 69
    }
  ]
}
```

### 主なエラー

- 401：未認証
- 403：対応担当者本人ではない問い合わせが含まれる
- 404：指定された問い合わせの中に存在しないものがある
- 409：対応中ではない問い合わせが含まれる
- 422：リクエストの型、件数、番号、名称が不正

## 12. API11：問い合わせ更新

### リクエスト

```json
{
  "問い合わせ当時の所属": "総務課",
  "受付経路": "メール",
  "問い合わせ分類": "分類A",
  "件名": "メール送信エラー",
  "緊急度": 2,
  "受付時の処理": 2,
  "問い合わせ詳細": "送信時にエラーが発生する",
  "受信日時": "2026-10-17T09:30:00"
}
```

| 項目 | 必須 | 検証・条件 |
|---|---|---|
| 問い合わせ当時の所属 | 必須 | 1〜30文字 |
| 受付経路 | 必須 | 電話、メール、フォーム |
| 問い合わせ分類 | 必須 | 分類A、分類B、分類C |
| 件名 | 必須 | 1〜100文字 |
| 緊急度 | 必須 | 1、2、3 |
| 受付時の処理 | 必須 | 1、2、3 |
| 問い合わせ詳細 | 任意 | null可。指定する場合は1〜1000文字 |
| 受信日時 | 必須 | 日時型 |

API01とは異なり、現行の更新スキーマでは受信日時は常に必須である。また、電話の場合に受信日時を禁止する条件は、現在の更新スキーマには設定されていない。

### バックエンド処理

1. 対象問い合わせをロックして取得する。
2. 問い合わせが存在することを確認する。
3. 対応完了済みの場合は編集を拒否する。
4. 現在の状態に応じて編集権限と変更条件を検証する。
5. 編集可能な項目を更新する。
6. 受付時の処理の変更に応じて、対応完了日時を設定する。

#### 未引き受けの場合

- 受付担当者本人だけが編集できる。
- 現在の受付時の処理が2「要調査」であることを前提とする。
- 更新後の受付時の処理が1「即時解決」または3「他部署へ引き継ぎ」の場合、対応完了日時を現在日時にする。
- 更新後の受付時の処理が2の場合、対応完了日時をnullにする。

#### 対応中の場合

- 対応担当者本人だけが編集できる。
- 受付時の処理は変更できない。
- 対応完了日時はnullのままとする。

### 成功レスポンス：HTTP 200

```json
{
  "message": "問い合わせを更新しました。",
  "問い合わせ番号": 123
}
```

### 主なエラー

- 401：未認証
- 403：未引き受けの受付担当者本人ではない、または対応中の対応担当者本人ではない
- 404：問い合わせが存在しない
- 409：対応完了済み、未引き受けなのに現在の受付時の処理が2ではない、対応中なのに受付時の処理を変更しようとした
- 422：リクエストの型、必須項目、文字数、選択肢が不正

## 13. API12：問い合わせ一覧取得・検索

### エンドポイント

- メソッド：`GET`
- パス：`/api/inquiries`

### 初期条件

`初期条件` は必須で、値は1または2とする。

- `初期条件=1`：初期表示
- `初期条件=2`：通常検索

### クエリパラメータ

| パラメータ | 型・条件 | 用途 |
|---|---|---|
| 初期条件 | 必須、1または2 | 初期表示と通常検索の区別 |
| 問い合わせ番号 | 整数、1以上 | 問い合わせ番号による完全一致 |
| 問い合わせ職員番号 | 文字列、1〜20文字 | 問い合わせ者の職員番号 |
| 問い合わせ当時の所属 | 文字列、1〜30文字 | 部分一致 |
| 受付経路 | 複数値可 | 電話、メール、フォーム |
| 問い合わせ分類 | 文字列 | 分類A、分類B、分類C |
| 件名 | 文字列、1〜100文字 | 部分一致 |
| 緊急度 | 整数 | 1、2、3 |
| 受付担当者 | 文字列、1〜20文字 | 受付担当者の職員番号 |
| 対応担当者 | 文字列、1〜20文字 | 対応担当者の職員番号 |
| 状態 | 複数値可 | 引き受け待ち、対応中、対応完了 |
| 受信日時開始 | 日時 | 受信日時の下限 |
| 受信日時終了 | 日時 | 受信日時の上限 |
| page | 整数、1以上 | ページ番号。既定値1 |
| page_size | 整数、1〜100 | 1ページの件数。既定値50 |

受信日時開始と受信日時終了の両方が指定された場合、開始日時は終了日時以前でなければならない。

### 初期表示：`初期条件=1`

初期表示では、通常検索の各検索条件は適用せず、ログイン中の職員の所属と担当状況に基づいて一覧を取得する。

#### 情報システム課の職員

次のいずれかに該当する問い合わせを取得する。

- 引き受け待ちの問い合わせ
- ログイン中の職員本人が担当する対応中の問い合わせ

#### 一般職員

ログイン中の職員本人の問い合わせのうち、対応完了していないものを取得する。

### 通常検索：`初期条件=2`

指定された検索条件だけを適用する。

- 異なる項目間はAND条件。
- 同一項目内で複数値を指定できる状態はOR条件。
- 状態は「引き受け待ち」「対応中」「対応完了」を複数指定できる。
- 問い合わせ当時の所属と件名は部分一致。
- 受付経路と状態は、同じ項目内の複数値をORで扱う。
- 受信日時開始は以上、受信日時終了は以下として扱う。

### 並び順とページネーション

- 受信日時の降順。
- 受信日時が同じ場合は問い合わせ番号の降順。
- `page` と `page_size` によってページネーションする。
- `total` は条件に一致する全件数を表す。

### リクエスト例

初期表示：

```http
GET /api/inquiries?初期条件=1
```

通常検索：

```http
GET /api/inquiries?初期条件=2&件名=メール&状態=対応中&状態=引き受け待ち&page=1&page_size=50
```

### 成功レスポンス：HTTP 200

{

`items` の各要素には、一覧表示に必要な項目を含める。問い合わせ詳細、問い合わせ詳細本文、登録日時、引き受け日時、対応完了日時などは、この一覧レスポンスには含めない。

### 主なエラー

- 401：未認証
- 400：ログイン中の職員番号が職員テーブルに存在しない

## 16. API15：問題調査編集

### エンドポイント

- メソッド：`PATCH`
- パス：`/api/investigations/{investigation_id}`

### パスパラメータ

| パラメータ | 型・条件 | 用途 |
|---|---|---|
| investigation_id | 整数、1以上 | 編集する問題調査番号 |

### リクエストボディ

更新したい項目だけを指定する。指定されていない項目は変更しない。

| 項目 | 型・条件 | 必須・任意 | 用途 |
|---|---|---|---|
| 問題調査の名称や仮説 | 文字列、最大30文字、null不可 | 任意 | 問題調査の名称や仮説を更新する |
| 問題の原因 | 文字列、最大1000文字、null可 | 任意 | 問題の原因を更新する |
| 情シス側での対応 | 文字列、最大1000文字、null可 | 任意 | 情シス側での対応内容を更新する |
| 問い合わせ者側で必要な対応 | 文字列、最大1000文字、null可 | 任意 | 問い合わせ者側で必要な対応内容を更新する |
| 対応案策定予定日時 | 日時、null可 | 任意 | 対応案の策定予定日時を更新する |
| 進捗更新の次回更新予定日時 | 日時、null可 | 任意 | 次回の進捗更新予定日時を更新する |

指定できるのは上記の項目のみとする。問題調査番号、問題調査状態、調査開始日時、リアクション要求日時、問題調査断念日時、最新移行先の問題調査番号などの管理項目は更新対象に含めない。

#### リクエスト例

```json
{
  "問題調査の名称や仮説": "メール送信エラーの原因調査",
  "問題の原因": "メールサーバーへの接続設定に問題がある可能性",
  "対応案策定予定日時": "2026-10-20T17:00:00"
}
```

この例では、指定した3項目だけを更新する。指定されていない項目は変更しない。

### 処理概要

1. ログイン中の職員情報から、操作者の職員番号を取得する。
2. リクエストボディについて、更新項目、データ型、文字数、nullの可否などを検証する。
3. 更新項目が1つも指定されていない場合、422エラーを返す。
4. 指定された問題調査レコードを取得し、対象レコードをロックする。
5. 問題調査が存在しない場合、404エラーを返す。
6. 対象の問題調査に関連付けられたすべての問い合わせについて、操作者が現在の対応担当者であることを確認する。また、関連する問い合わせ問題調査が1件以上存在することを確認する。
7. 編集権限がない場合、403エラーを返す。
8. 問題調査状態が「調査中」であることを確認する。調査中でなければ409エラーを返す。
9. 指定された項目だけを更新し、更新後の問題調査情報をレスポンスとして返す。

### 編集権限と状態の条件

#### 編集権限

次の条件を両方満たす場合に編集できる。

- 対象の問題調査に関連する問い合わせ問題調査レコードが1件以上存在する。
- 関連するすべての問い合わせについて、現在の対応担当者がログイン中の職員と一致する。

関連する問い合わせが存在しない場合や、1件でも別の職員が対応担当者となっている場合は編集できない。

#### 問題調査の状態

問題調査状態が「1：調査中」の場合のみ編集できる。

- 状態1：編集可能（権限条件を満たす場合）
- 状態2：編集不可
- 状態3：編集不可

### 成功レスポンス：HTTP 200

```json
{
  "問題調査番号": 10,
  "問題調査の名称や仮説": "メール送信エラーの原因調査",
  "問題の原因": "メールサーバーへの接続設定に問題がある可能性",
  "情シス側での対応": "メールサーバーの設定を確認する",
  "問い合わせ者側で必要な対応": "再度メール送信を試す",
  "問題調査状態": 1,
  "調査開始日時": "2026-10-17T10:00:00",
  "対応案策定予定日時": "2026-10-20T17:00:00",
  "進捗更新の次回更新予定日時": "2026-10-19T17:00:00",
  "リアクション要求日時": null,
  "問題調査断念日時": null,
  "最新移行先の問題調査番号": null
}
```

更新に成功した場合、更新後の問題調査情報を返す。

レスポンスには、今回更新した項目だけでなく、問題調査番号、状態、各管理日時、最新移行先の問題調査番号などを含める。

### 主なエラー

- 401：未認証（認証機能導入後）
- 403：関連する問い合わせの現在の対応担当者ではない、または関連する問い合わせが存在しない
- 404：指定された問題調査番号のレコードが存在しない
- 409：問題調査状態が「調査中」ではない
- 422：更新項目が指定されていない、データ型が不正、文字数超過、名称や仮説がnull、許可されていない項目が含まれている、など

### 備考

- 画面201「問題調査詳細」で利用する。
- 問題調査の新規作成APIではなく、登録済みの問題調査を部分更新するAPIである。
- リクエストに含まれない項目は更新しない。
- 問題調査状態や日時などの管理項目は、このAPIでは直接変更しない。
- 編集権限と状態はバックエンドで検証する。画面側の編集ボタンの表示制御だけに依存しない。

## API16：問題調査全体の断念

問題調査本体の状態変更に加え、関連する問い合わせ問題調査のうち、状態が「調査中」のレコードを「断念」に変更する。

### 2. エンドポイント

- **HTTPメソッド：** `POST`
- **パス：** `/api/investigations/{investigation_id}/abandon`
- **パスパラメータ：** `investigation_id`
  - データ型：整数
  - 制約：1以上
  - 値の取得元：画面201で表示している問題調査番号

### 3. リクエスト

リクエストボディは指定しない。

操作者の職員番号は、認証済みユーザー情報から取得する。リクエストから操作者の職員番号を受け取らない。

4. 問題調査本体の状態が「調査中」（状態1）である。

| 項目 | 設定値 |
|---|---|
| 問題調査状態 | 3（問題調査断念） |
| 問題調査断念日時 | データベースの現在日時 |

#### 5.7 更新後の整合性確認

関連する問い合わせ問題調査がすべて状態2になっていることを確認する。

状態2以外のレコードが残っている場合は、データ整合性エラーとして500エラーを返し、同一トランザクション内の更新をロールバックする。

## API18：問い合わせ問題調査の個別断念

### 1. 概要

- **API名：** 問い合わせ問題調査の個別断念
- **HTTPメソッド：** POST
- **エンドポイント：** `/api/investigations/relations/{relation_id}/abandon`
- **利用画面：** 画面201「問題調査詳細」
- **目的：** 関連する問い合わせ問題調査のうち、指定した1件だけを個別断念にする。

### 2. リクエスト

#### パスパラメータ

| 項目 | 型・制約 | 説明 |
|---|---|---|
| relation_id | 整数、1以上 | 対象の問い合わせ問題調査番号 |

リクエストボディは不要とする。操作者の職員番号は、認証情報から取得する。

### 3. 実行条件

以下のすべてを満たす場合に実行する。

1. 指定された問い合わせ問題調査が存在する。
2. 親となる問題調査が存在する。
3. 親の問題調査状態が「1：調査中」である。
4. 関連する問い合わせが存在する。
5. 操作者が、当該問い合わせの現在の対応担当者である。
6. 対象の問い合わせ問題調査状態が「1：調査中」である。

### 4. 処理内容

1. 対象の問い合わせ問題調査から親の問題調査番号を取得する。
2. 親の問題調査レコードをロックする。
3. 親の問題調査が存在することを確認する。
4. 親の問題調査状態が「1：調査中」であることを確認する。
5. 親のロックを保持したまま、対象の問い合わせ問題調査レコードをロックする。
6. 対象の問い合わせ番号と問い合わせ問題調査状態を取得する。
7. 関連する問い合わせが存在することを確認する。
8. 問い合わせの現在の対応担当者が操作者本人であることを確認する。
9. 対象の問い合わせ問題調査状態が「1：調査中」であることを確認する。
10. 対象の問い合わせ問題調査だけを個別断念に更新する。
    - 問い合わせ問題調査状態：1 → 2
    - その他の項目は変更しない。

親の問題調査状態や、同じ問題調査に関連付けられたほかの問い合わせ問題調査は変更しない。

### 5. 更新後の整合性

- 親の問題調査が「調査中」であることを確認してから更新する。
- 対象の問い合わせ問題調査だけを更新し、ほかの関連レコードには影響させない。
- すべての処理を同一トランザクションで実行する。
- 処理中にエラーが発生した場合は、トランザクションをロールバックする。

### 6. レスポンス

#### 正常終了：200 OK

| 項目 | 説明 |
|---|---|
| 問い合わせ問題調査番号 | 更新した問い合わせ問題調査番号 |
| 問い合わせ番号 | 関連する問い合わせ番号 |
| 問題調査番号 | 親の問題調査番号 |
| 問い合わせ問題調査状態 | 更新後の状態（2：断念） |
| 断念日時 | 記録した断念日時 |
| message | 処理結果メッセージ |

`message` の値は「問い合わせ問題調査を個別断念にしました。」とする。

### 7. エラー

| HTTPステータス | 発生条件 | エラー内容 |
|---|---|---|
| 401 Unauthorized | 未認証 | 認証エラー |
| 403 Forbidden | 操作者が現在の対応担当者ではない | 対応担当者のみ操作できます。 |
| 404 Not Found | 対象の問い合わせ問題調査が存在しない | 問い合わせ問題調査が見つかりません。 |
| 404 Not Found | 親の問題調査が存在しない | 親となる問題調査が見つかりません。 |
| 404 Not Found | 関連する問い合わせが存在しない | 関連する問い合わせが見つかりません。 |
| 409 Conflict | 親の問題調査が調査中ではない | 調査中の問題調査に関連する問い合わせ問題調査のみ個別断念できます。 |
| 409 Conflict | 対象の問い合わせ問題調査が調査中ではない | 調査中の問い合わせ問題調査のみ個別断念できます。 |
| 422 Unprocessable Entity | パスパラメータが不正 | 入力値エラー |
| 500 Internal Server Error | 想定外のエラー | サーバーエラー |

### 8. 補足事項

- 問題調査全体を断念するAPI16とは異なり、このAPIは指定した問い合わせ問題調査1件のみを断念する。
- 個別断念の対象は、親の問題調査が調査中で、対象の問い合わせ問題調査も調査中の場合に限る。
- 個別断念では、断念日時を更新し、状態を2に変更する。
- ロック順序は「親の問題調査 → 対象の問い合わせ問題調査」とする。関連する他のAPIとのロック順序の整合性は、API設計全体の横断レビューで確認する。

# API19：問い合わせ問題調査のOK回答

## 1. 基本情報

- **HTTPメソッド：** POST
- **エンドポイント：** `/api/investigations/relations/{relation_id}/ok`
- **目的：** 問い合わせ者が、問題調査に対してOKと回答する。

## 2. リクエスト

### パスパラメータ

| 項目 | 内容 |
|---|---|
| `relation_id` | 問い合わせ問題調査番号。整数、1以上、必須 |

### 認証情報

ログイン中の職員を `current_user` から取得する。リクエスト本文は使用しない。

## 3. 実行条件

次の条件をすべて満たすこと。

1. 指定された問い合わせ問題調査が存在する。
2. 関連する問い合わせが存在する。
3. ログイン中の職員が、その問い合わせの問い合わせ者本人である。

| 更新項目 | 設定値 |
|---|---|
| 問い合わせ問題調査状態 | 4（OK） |
| リアクション内容 | 1（OK） |
| リアクション日時 | `CURRENT_TIMESTAMP` |

7. 更新後の値をレスポンスとして返す。

## 5. レスポンス

成功時はHTTP 200を返す。

| 項目 | 内容 |
|---|---|
| `問い合わせ問題調査番号` | 更新した関連レコードの番号 |
| `問い合わせ番号` | 対象の問い合わせ番号 |
| `問題調査番号` | 関連する問題調査番号 |
| `問い合わせ問題調査状態` | 更新後の状態（4） |
| `リアクション内容` | OK（1） |
| `リアクション日時` | OKと回答した日時 |
| `message` | `問い合わせ問題調査にOKと回答しました。` |

## 6. エラー

| HTTPステータス | 条件 |
|---|---|
| 403 Forbidden | 問い合わせ者本人ではない |
| 404 Not Found | 問い合わせ問題調査または関連する問い合わせが存在しない |
| 409 Conflict | 対象の状態が3「リアクション待ち」ではない |
| 422 Unprocessable Entity | `relation_id` が1以上の整数ではない |
| 500 Internal Server Error | 想定外のサーバーエラー |

## 7. トランザクション

- 状態とリアクション情報の更新を一つのトランザクションで実行する。
- 更新が正常に完了した場合にのみ確定する。
- 処理中にエラーが発生した場合は更新をロールバックする。

## 8. 補足

- OK回答は、問い合わせ者本人がリアクション要求に応答する操作である。
- OK回答では、問題調査本体の状態は変更しない。
- 状態4「OK」は、問い合わせ問題調査レコード単位で記録する。

1. 指定された問い合わせ問題調査が存在する。
2. 関連付け元の問題調査が存在する。
3. 対象の問い合わせが存在する。
4. 問い合わせ問題調査の状態が「リアクション待ち（3）」である。
5. ログインユーザーが対象問い合わせの依頼者である。

条件を満たさない場合は、該当するエラーを返し、トランザクションをロールバックする。

## 4. 処理内容

すべての更新処理を1つのトランザクション内で実行する。

### 4.1. 関連付け元の問題調査を取得・ロックする

対象の問い合わせ問題調査から関連付け元の問題調査番号を取得する。

対象の問題調査レコードを行ロック（`FOR UPDATE`）し、以下の情報を取得する。

- 問題調査状態
- 問題調査の名称や仮説
- 原因
- 対応内容・回答
- 対応予定日
- 次回更新予定日
- 最新移行先の問題調査番号

問い合わせ問題調査が存在しない場合は、HTTP 404を返す。

### 4.2. 対象の問い合わせ問題調査を取得・ロックする

対象の問い合わせ問題調査レコードを行ロック（`FOR UPDATE`）し、以下の情報を取得する。

- 問い合わせ番号
- 問題調査番号
- 問い合わせ問題調査状態

取得した問題調査番号が4.1で取得した問題調査番号と一致しない場合は、処理中に関連付けが変更されたものとして、HTTP 409を返す。

問い合わせ問題調査の状態が「リアクション待ち（3）」以外の場合は、HTTP 409を返す。

### 4.3. 問い合わせ依頼者を確認する

対象の問い合わせから依頼者の職員番号を取得する。

問い合わせが存在しない場合は、HTTP 404を返す。

ログインユーザーの職員番号と依頼者の職員番号が一致しない場合は、HTTP 403を返す。

### 4.4. 移行先の問題調査を決定する

関連付け元の問題調査に登録されている「最新移行先の問題調査番号」を確認する。

| 条件 | 処理 |
|---|---|
| 最新移行先が登録されており、その問題調査状態が「調査中（1）」である | 既存の移行先を再利用する |
| 最新移行先が未登録である | 新しい問題調査を作成する |
| 最新移行先のレコードが存在しない | 新しい問題調査を作成する |
| 最新移行先の問題調査状態が「調査中（1）」以外である | 新しい問題調査を作成する |

既存の移行先を再利用する場合は、移行先の問題調査レコードを行ロック（`FOR UPDATE`）する。

新しい問題調査を作成する場合は、関連付け元の問題調査から以下の情報を複写する。

- 問題調査の名称や仮説
- 原因
- 対応内容・回答
- 対応予定日
- 次回更新予定日

新しい問題調査の設定は以下のとおりとする。

- 問題調査状態：調査中（1）
- 問題調査開始日時：現在日時
- 問題調査の名称や仮説：元の名称に「から複写」を付加する
- 元の名称がNULLの場合：「名称未設定から複写」とする

新しい問題調査を作成した場合は、関連付け元の問題調査の「最新移行先の問題調査番号」を、新しく作成した問題調査番号に更新する。

**移行先の再利用時に、移行先に関連付けられた問い合わせの対応担当者との一致検証は追加しない。** 通常の関連付けAPIで対応担当者の整合性を検証する設計を前提とする。

### 4.5. 元の問い合わせ問題調査にNG回答を記録する

対象の問い合わせ問題調査を以下の内容で更新する。

| 項目 | 設定値 |
|---|---|
| 問い合わせ問題調査状態 | NG（5） |
| リアクション内容 | NG（2） |
| リアクション日時 | 現在日時 |
| NGでの移行先問題調査番号 | 4.4で決定した移行先の問題調査番号 |

更新後の値をレスポンス用に取得する。

### 4.6. 移行先への二重関連付けを確認する

新しい問い合わせ問題調査を登録する前に、移行先の問題調査に対して、同じ問い合わせがすでに関連付けられていないかを確認する。

判定条件は、以下の2項目が一致するレコードが存在することである。

- 問題調査番号：4.4で決定した移行先の問題調査番号
- 問い合わせ番号：対象の問い合わせ番号

該当レコードが存在する場合は、HTTP 409を返し、トランザクション全体をロールバックする。

この場合、元の問い合わせ問題調査へのNG回答の記録、移行先問題調査の新規作成、元の問題調査の最新移行先の更新も含め、すべて取り消す。

### 4.7. 移行先に問い合わせ問題調査を新規登録する

二重関連付けが存在しない場合に限り、対象の問い合わせを移行先の問題調査に関連付ける。

登録項目は以下のとおりとする。

- 問い合わせ番号：対象の問い合わせ番号
- 問題調査番号：4.4で決定した移行先の問題調査番号

問い合わせ問題調査状態は、データベースの初期値「調査中（1）」を使用する。

登録後、作成された問い合わせ問題調査番号と状態を取得する。

### 4.8. トランザクションを確定する

すべての処理が正常に完了した場合に限り、トランザクションをコミットする。

途中でエラーが発生した場合は、トランザクションをロールバックする。

## 5. 正常レスポンス

HTTPステータス：`200 OK`

レスポンス例：

```json
{
  "問い合わせ問題調査番号": 101,
  "問い合わせ番号": 2001,
  "問題調査番号": 301,
  "問い合わせ問題調査状態": 5,
  "リアクション内容": 2,
  "リアクション日時": "2026-10-18T10:30:00",
  "NGでの移行先問題調査番号": 302,
  "移行先問題調査番号": 302,
  "移行先問い合わせ問題調査番号": 102,
  "移行先問い合わせ問題調査状態": 1,
  "message": "問い合わせ問題調査にNGと回答し、移行先に関連付けました。"
}
```

※番号・日時は説明用の例である。実際のレスポンスでは、データベースから取得した値を返す。

レスポンス項目は以下のとおりとする。

| 項目 | 内容 |
|---|---|
| 問い合わせ問題調査番号 | NG回答した元の関連レコード番号 |
| 問い合わせ番号 | 対象の問い合わせ番号 |
| 問題調査番号 | 関連付け元の問題調査番号 |

| リアクション内容 | NG（2） |
| リアクション日時 | NG回答日時 |
| NGでの移行先問題調査番号 | 決定した移行先の問題調査番号 |
| 移行先問題調査番号 | 決定した移行先の問題調査番号 |

| 移行先問い合わせ問題調査状態 | 新しい関連レコードの状態（1） |
| message | 処理結果メッセージ |

## 6. エラーレスポンス

| HTTPステータス | 発生条件 |
|---|---|
| 403 Forbidden | ログインユーザーが対象問い合わせの依頼者ではない |
| 404 Not Found | 対象の問い合わせ問題調査、関連付け元の問題調査、または対象の問い合わせが存在しない |
| 409 Conflict | 対象の関連付けが処理中に変更された、問い合わせ問題調査がリアクション待ちではない、または移行先に同じ問い合わせがすでに関連付けられている |
| 422 Unprocessable Entity | パスパラメータが整数1以上という条件を満たさない |
| 500 Internal Server Error | 想定外のエラー |

エラー時には、処理途中のデータ更新を残さない。

## 7. 業務ルール・設計上の補足

1. NG回答した元の問い合わせ問題調査は、状態5「NG」とする。
2. NG回答の内容と日時を記録する。
3. NG回答した問い合わせは、移行先の問題調査にも関連付ける。
4. 移行先の問題調査が状態1「調査中」であれば再利用し、それ以外の場合は新規作成する。
5. 移行先の問題調査に同じ問い合わせが関連付け済みの場合は、二重登録せず、HTTP 409で処理を取り消す。
6. 新規作成した問い合わせ問題調査の状態は、データベースの初期値1「調査中」を使用する。
7. このAPIでは、関連付け元の問題調査自体の状態は変更しない。
8. 元の問題調査と移行先の問題調査は、複数の問い合わせで共有できる。
9. 移行先の対応担当者の一致検証は、このAPIでは追加しない。
10. NG回答の記録、移行先の決定・作成、最新移行先の更新、二重関連付け確認、新規関連付けは、1つのトランザクションとして処理する。

# API21：問題調査の検索結果取得

## 1. 概要

問題調査を検索条件に基づいて検索し、画面202「問題調査一覧・検索」に表示する一覧データを取得する。

検索結果は問題調査単位で取得し、ページングに対応する。

## 2. エンドポイント

| 項目 | 内容 |
|---|---|
| HTTPメソッド | GET |
| パス | `/api/investigations` |
| 認証 | 必須 |
| リクエストボディ | なし |
| 検索条件 | クエリパラメータ |

## 3. リクエスト

すべての検索条件は任意とする。

| パラメータ | データ型 | 検索方法 |
|---|---|---|
| `問題調査番号` | 整数、1以上 | 完全一致 |
| `問題調査の名称や仮説` | 文字列 | 部分一致 |
| `問題調査状態` | 整数、1～3 | 完全一致 |
| `問い合わせ職員番号` | 文字列 | 完全一致 |
| `問い合わせ者氏名` | 文字列 | 部分一致 |
| `対応担当者職員番号` | 文字列 | 完全一致 |
| `page` | 整数、1以上 | ページ番号。初期値1 |
| `page_size` | 整数、1～100 | 1ページの取得件数。初期値50 |

### 検索条件の組み合わせ

- 指定された検索条件が複数ある場合は、異なる条件をANDで結合する。
- 文字列の部分一致検索では、前後の空白を除去して検索する。
- 未指定の条件は絞り込みに使用しない。

### 検索条件の適用方針

- 指定された検索条件を使用して問題調査を検索する。
- 複数の検索条件が指定された場合は、すべての条件をAND条件で適用する。
- 検索条件が指定されていない場合は、全件を検索対象とする。
- 本APIでは、ログイン中の職員の職員番号に基づく検索対象の制限は行わない。
- 初期表示時の検索条件は画面側で設定し、画面から本APIに検索条件を渡す。
  - 一般職員：問い合わせ職員番号にログイン中の職員番号を設定する。
  - 情シス職員：対応担当者職員番号にログイン中の職員番号を設定する。

## 4. 処理内容

1. ログインユーザーの職員番号を取得する。
2. 指定された検索条件からSQLの絞り込み条件を組み立てる。
3. 検索条件に一致する問題調査の総件数を取得する。
4. 調査開始日時の降順、同日時の場合は問題調査番号の降順で並べる。
5. `page` と `page_size` に基づいて一覧データを取得する。
6. 取得結果をレスポンスとして返す。

問い合わせ者や対応担当者に関する検索条件は、問題調査に関連付けられた問い合わせを対象に判定する。複数の問い合わせが条件に一致しても、問題調査自体は重複して表示しない。

## 5. 正常レスポンス

HTTPステータス：`200 OK`

レスポンス例：

```json
{
  "items": [
    {
      "問題調査番号": 301,
      "問題調査の名称や仮説": "ネットワーク接続が不安定",
      "問題調査状態": 1,
      "対応担当者職員氏名": "情シス太郎",
      "関連問い合わせ件数": 3,
      "自分の問い合わせを含む": true
    }
  ],
  "page": 1,
  "page_size": 50,
  "total": 1
}
```

※番号、氏名、件数などは説明用の例である。

| レスポンス項目 | 内容 |
|---|---|
| `items` | 問題調査の一覧 |
| `items[].問題調査番号` | 問題調査番号 |
| `items[].問題調査の名称や仮説` | 問題調査の名称や仮説 |
| `items[].問題調査状態` | 問題調査状態コード |
| `items[].対応担当者職員氏名` | 関連する問い合わせのうち、問い合わせ番号が最も小さいものの対応担当者氏名 |
| `items[].関連問い合わせ件数` | 関連付けられた問い合わせの件数 |
| `items[].自分の問い合わせを含む` | ログインユーザー自身が問い合わせ者である問い合わせを含むか |
| `page` | 現在のページ番号 |
| `page_size` | 1ページの取得件数 |
| `total` | 検索条件に一致する問題調査の総件数 |

検索結果が0件の場合もHTTP 200を返す。`items` は空配列、`total` は0となる。

## 6. エラーレスポンス

| HTTPステータス | 発生条件 |
|---|---|
| 401 Unauthorized | 未認証 |
| 422 Unprocessable Entity | パラメータの型や許容範囲が不正 |
| 500 Internal Server Error | 想定外のエラー |

## 7. 補足

- このAPIは検索・一覧取得専用であり、データの更新は行わない。
- 問題調査の詳細情報と、関連する問い合わせ問題調査の一覧は、詳細取得APIで取得する。
- 一覧の並び順は、調査開始日時の降順、問題調査番号の降順とする。
- ページングの初期値は1ページ50件とする。

## 認証API

### API22　ログイン

#### 1. 概要

職員番号とパスワードを使用して認証を行う。

認証に成功した場合、ログインセッションをデータベースに登録し、セッションIDをCookieに設定する。

#### 2. エンドポイント

- HTTPメソッド：POST
- URL：`/api/auth/login`
- 認証：不要
- リクエストボディ：JSON

#### 3. リクエスト項目

| 項目 | 型 | 制約 | 必須 |
|---|---|---|---|
| 職員番号 | string | 1～20文字 | ○ |
| パスワード | string | 1～128文字 | ○ |

#### 4. 処理内容

1. リクエストの職員番号を使用して、職員認証情報および職員情報を取得する。
2. アカウントが存在し、ログイン可否が有効であることを確認する。
3. Argon2を使用して、入力されたパスワードと保存済みのパスワードハッシュを検証する。
4. 認証に失敗した場合は、HTTP 401を返す。アカウントの不存在、ログイン不可、パスワード不一致について、利用者に返すエラーメッセージは共通とする。
5. 認証に成功した場合、ランダムなセッションIDを生成する。
6. セッションIDそのものではなく、SHA-256でハッシュ化した値をデータベースの「ログインセッション」に保存する。
7. セッション情報を登録し、セッションIDをCookieに設定する。
8. ログイン結果として、職員番号、氏名、所属を返す。

#### 5. セッションの有効期間

| 項目 | 設定 |
|---|---|
| 無操作期限 | 最終利用時点から30分 |
| 絶対有効期限 | ログインから12時間 |
| Cookieの最大有効期間 | 12時間 |

無操作期限は、認証済みAPIの利用時に延長する。ただし、絶対有効期限を超えて延長しない。

#### 6. Cookieの設定

| 属性 | 設定値 | 目的 |
|---|---|---|
| Cookie名 | `session_id` | セッションIDの保持 |
| HttpOnly | true | JavaScriptからの読み取りを制限する |
| Secure | true | HTTPSでの送信に限定する |
| SameSite | Lax | クロスサイトからのCookie送信を制限する |
| Path | `/` | アプリケーション全体で使用する |

#### 7. 正常レスポンス

HTTP 200

```json
{
  "message": "ログインしました。",
  "職員番号": "J0001",
  "氏名": "情シス太郎",
  "所属": "情報システム課"
}
```

上記の職員情報はレスポンス本文の例であり、実際には認証された職員の情報を返す。セッションIDはレスポンス本文ではなくCookieに設定する。

#### 8. エラー

| HTTPステータス | 発生条件 |
|---|---|
| 401 | アカウントが存在しない、ログイン不可、パスワード不一致 |
| 422 | リクエスト項目の欠落、型不正、文字数制約違反 |
| 500 | 想定外のサーバーエラー |

### API23　ログアウト

#### 1. 概要

現在のセッションを失効させ、ブラウザのセッションCookieを削除する。

#### 2. エンドポイント

- HTTPメソッド：POST
- URL：`/api/auth/logout`
- 認証：不要
- リクエストボディ：なし

#### 3. 処理内容

1. CookieからセッションIDを取得する。
2. セッションIDが存在する場合、SHA-256でハッシュ化する。
3. データベースに該当する有効なセッションが存在する場合、失効日時を記録する。
4. Cookieが存在しない場合や、該当セッションがすでに失効している場合も、ブラウザ側のCookie削除を試みる。
5. ログアウト結果を返す。

ログアウトAPIは、セッションが存在しない場合も正常終了する。

#### 4. 正常レスポンス

HTTP 200

```json
{
  "message": "ログアウトしました。"
}
```

レスポンスでは、`session_id` Cookieの削除を指示する。

Cookie削除時には、発行時と同じCookie名、Path、HttpOnly、Secure、SameSiteの設定を使用する。

#### 5. エラー

| HTTPステータス | 発生条件 |
|---|---|
| 500 | 想定外のサーバーエラー |

### 共通仕様　セッション認証

#### 1. 概要

認証が必要なAPIでは、Cookieに設定されたセッションIDを使用してログイン中の職員を特定する。

#### 2. 認証処理

1. CookieからセッションIDを取得する。
2. セッションIDをSHA-256でハッシュ化する。
3. データベースから該当セッションを検索する。
4. セッションが失効していないこと、無操作期限と絶対有効期限を超過していないこと、職員のログイン可否が有効であることを確認する。
5. 認証に成功した場合、無操作期限と最終利用日時を更新し、職員番号、氏名、所属を取得する。
6. 取得した職員情報を、認証済みAPIの操作者情報として使用する。

#### 3. 認証エラー

| HTTPステータス | 発生条件 |
|---|---|
| 401 | Cookieがない、セッションが無効・失効・期限切れ、職員がログイン不可 |

認証に失敗した場合、認証が必要なAPIの処理を実行しない。

#### 4. 補足

- セッションIDそのものはデータベースに保存しない。
- セッション認証は各業務APIから共通の認証処理を呼び出して実施する。
- ログアウトAPIは、Cookieがなくても正常終了する。







## 14. 今回のレビューで反映した重要事項

### 14.1 操作者をリクエストから取得しない

問い合わせ登録では、受付担当者をリクエストから受け取る方式ではなく、ログイン中の職員を受付担当者として使用する。

引き受け、対応完了、問題調査関連付けなどの操作でも、操作者はログイン情報から取得する。

### 14.2 問い合わせ更新時の受付時の処理

未引き受けの問い合わせは、受付担当者本人だけが編集できる。

未引き受けの問い合わせについて、受付時の処理を2「要調査」から1「即時解決」または3「他部署へ引き継ぎ」に変更した場合は、対応完了日時を設定して対応完了状態とする。

対応中の問い合わせでは、受付時の処理を変更できない。

### 14.3 問い合わせ一覧の初期条件

問い合わせ一覧APIでは、`初期条件` を必須とする。

- 1は初期表示
- 2は通常検索

初期表示ではログイン中の職員の所属・担当状況から対象範囲を決定する。通常検索では指定された検索条件を組み合わせて取得する。

職員の所属は、ログイン情報だけに依存せず、職員テーブルから確認する実装となっている。

本書は、GitHub上の現行コードで確認できた実装を基に作成した。

HTTPステータスコードは、明示的に実装されているエラーと、FastAPIの入力検証によるエラーを区別して記載する。レスポンス例の番号や日時は説明用の値であり、実際の値は処理結果に応じて返される。
