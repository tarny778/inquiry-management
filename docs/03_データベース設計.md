# 03_データベース設計

## 1. データベース設計の目的

本設計書では、問い合わせ管理Webアプリで使用するデータベースについて、テーブル構成、カラム、データ型、制約、各項目の意味および状態管理方法を定義する。

本システムでは、問い合わせ全体の対応状況と、問い合わせに関連する問題調査の状況を分離して管理する。

- **問い合わせ**：職員から受け付けた一連の問い合わせ
- **問題調査**：共通する原因や対応方法について調査する単位
- **問い合わせ問題調査**：個々の問い合わせと問題調査の関係、およびその関係における調査・解決確認の状況

同じ問題調査に複数の問い合わせを関連付けることで、共通する調査結果や対応案を複数の問い合わせに活用できる構造とする。

特に、問題調査が終了したことと、問い合わせ全体の対応が完了したことを同一の状態として扱わない。

## 2. データベース管理システム

データベース管理システムには PostgreSQL を使用する。

SQLによるテーブル作成、データ登録・更新、業務フローの検証を行い、FastAPIからデータベースを操作する構成とする。

## 3. テーブル構成

本システムでは、以下の5テーブルを基本とする。

| テーブル名 | 役割 |
|---|---|
| 職員 | 職員の基本情報を管理する |
| 問い合わせ | 問い合わせ一件全体の情報とライフサイクルを管理する |
| 問題調査 | 調査単位、共通の原因・対応案、調査状態および移行先を管理する |
| 問い合わせ問題調査 | 問い合わせと問題調査の関係、および関係ごとの状態・履歴を管理する |
| 対応担当者変更履歴 | 問い合わせの対応担当者が変更された履歴を管理する |

### 3-1. テーブル間の関係

- 職員と問い合わせは、職員番号を介して関連付ける。
- 問い合わせと問題調査は、問い合わせ問題調査を介して関連付ける。
- 1件の問い合わせに複数の問題調査を関連付けられる。
- 1件の問題調査に複数の問い合わせを関連付けられる。
- 1件の問い合わせに、対応担当者変更履歴を複数件記録できる。
- 問題調査は、NGによる移行先の問題調査を参照できる。

問題調査の移行では、過去の問い合わせ問題調査レコードを削除せず、移行前後の関係をそれぞれのレコードで記録する。

## 4. 職員テーブル

職員テーブルは、問い合わせ者などの職員の基本情報を管理する。

### 4-1. カラム

| カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|
| 職員番号 | VARCHAR(20) | 不可 | 主キー |
| 氏名 | VARCHAR(30) | 不可 | |
| 所属 | VARCHAR(30) | 不可 | |

### 4-2. 設計方針

職員番号を主キーとする。

問い合わせテーブルには問い合わせ者、受付担当者、対応担当者の職員番号を保持し、氏名などの基本情報は職員テーブルから取得する。
職員レコードの削除後も氏名を保持する必要性については、別途検討する。

一方、問い合わせ当時の所属は、職員テーブルの所属とは別に問い合わせテーブルに保存する。これにより、職員の異動後も問い合わせ当時の所属を確認できる。

## 5. 問い合わせテーブル

問い合わせテーブルは、職員から受け付けた問い合わせ一件全体の情報と対応状況を管理する。

### 5-1. カラム

| カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|
| 問い合わせ番号 | INTEGER | 不可 | 主キー、IDENTITY |
| 問い合わせ職員番号 | VARCHAR(20) | 可 | 職員への外部キー |
| 問い合わせ当時の所属 | VARCHAR(30) | 不可 | 受付当時の所属 |
| 受付経路 | VARCHAR(20) | 不可 | |
| 問い合わせ分類 | VARCHAR(30) | 不可 | |
| 件名 | VARCHAR(100) | 不可 | |
| 緊急度 | INTEGER | 不可 | CHECK：1、2、3 |
| 受付時の処理 | INTEGER | 不可 | CHECK：1、2、3 |
| 問い合わせ詳細 | VARCHAR(1000) | 可 | |
| 受付担当者 | VARCHAR(20) | 可 | 職員への外部キー |
| 対応担当者 | VARCHAR(20) | 可 | 職員への外部キー 即時解決等では未設定の場合がある |
| 受信日時 | TIMESTAMP | 不可 | 問い合わせを受信した日時 |
| 登録日時 | TIMESTAMP | 不可 | 初期値：CURRENT_TIMESTAMP |
| 引き受け日時 | TIMESTAMP | 可 | 対応担当者が引き受けた日時 |
| 対応完了日時 | TIMESTAMP | 可 | 問い合わせ全体の対応完了日時 |

### 5-2. 問い合わせ番号

問い合わせ番号はIDENTITYによって採番する。

問い合わせ一件を一意に識別するための主キーであり、問い合わせ問題調査などから参照される。

### 5-3. 問い合わせ者と所属

問い合わせ職員番号は職員テーブルの職員番号を参照する。

問い合わせ当時の所属は、問い合わせ受付時点の情報を保持するために設ける。職員テーブルの所属が変更されても、過去の問い合わせ当時の所属は変更しない。
また、職員レコードの削除に備えて、当時の氏名を文字列として記録するカラムの新設について、要検討とする。

### 5-4. 緊急度と受付時の処理

緊急度は整数値で管理し、1、2、3のみを許容する。

受付時の処理も整数値で管理し、1、2、3のみを許容する。

それぞれの値が示す名称や画面表示は、画面設計・API設計と整合させる。DBではCHECK制約によって許容値を制限する。

### 5-5. 受付担当者と対応担当者

受付担当者には、問い合わせを登録した情シス職員の職員番号を記録する。

対応担当者には、問い合わせを引き受けた職員の職員番号を記録する。対応担当者はNULLを許容する。

いずれも職員番号で記録するが、外部キー参照先となる職員レコードの、将来的な削除に備えて、職員番号とは別に、当時の氏名を文字列として記録するカラムの新設について、要検討する。

受付担当者と対応担当者は役割が異なるため、同一項目として扱わない。

対応担当者の変更は、対応担当者変更履歴テーブルにも記録する。

### 5-6. 問い合わせの日時

- 受信日時：問い合わせを受信した日時
- 登録日時：システムに問い合わせを登録した日時
- 引き受け日時：対応担当者が問い合わせを引き受けた日時
- 対応完了日時：問い合わせ全体の対応完了を明示的に実行した日時

それぞれ異なる業務イベントを表すため、混同しない。

## 6. 問題調査テーブル

問題調査テーブルは、調査単位ごとの名称・仮説、共通の原因や対応案、調査状態、予定日時および移行先を管理する。

### 6-1. カラム

| カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|
| 問題調査番号 | INTEGER | 不可 | 主キー、IDENTITY |
| 問題調査の名称や仮説 | VARCHAR(30) | 不可 | |
| 問題の原因 | VARCHAR(1000) | 可 | |
| 情シス側での対応 | VARCHAR(1000) | 可 | |
| 問い合わせ者側で必要な対応 | VARCHAR(1000) | 可 | |
| 問題調査状態 | INTEGER | 不可 | 初期値1、CHECK：1～3 |
| 調査開始日時 | TIMESTAMP | 不可 | 初期値：CURRENT_TIMESTAMP |
| 対応案策定予定日時 | TIMESTAMP | 可 | |
| 進捗更新の次回更新予定日時 | TIMESTAMP | 可 | |
| リアクション要求日時 | TIMESTAMP | 可 | |
| 問題調査断念日時 | TIMESTAMP | 可 | |
| 最新移行先の問題調査番号 | INTEGER | 可 | 同じテーブルへの外部キー |

### 6-2. 問題調査の名称や仮説

問題調査を識別するための名称、または調査開始時点の仮説を記録する。

調査開始時点では原因が確定していない場合があるため、確定した原因そのものとは区別する。

### 6-3. 原因と対応案

以下の項目には、問題調査において共有する原因・対応案を記録する。

- 問題の原因
- 情シス側での対応
- 問い合わせ者側で必要な対応

調査中は未確定のためNULLを許容する。

問い合わせ者へのリアクション要求後は、当該問題調査の内容を確定した記録として扱い、名称・仮説、原因、対応案等を変更しない。状態遷移と内容変更の制御は、API層で実装する。

### 6-4. 問題調査状態

問題調査状態は、次の値で管理する。

| 値 | 状態 | 意味 |
|---|---|---|
| 1 | 調査中 | 調査・対応案の検討を行っている |
| 2 | リアクション要求済み | 問い合わせ者に解決確認を依頼し、当該調査を確定した |
| 3 | 問題調査断念 | 問題調査そのものを断念した |

初期値は1とする。

状態2は問い合わせ者からOKを受けたことを意味しない。問い合わせ者からの反応は、問い合わせ問題調査テーブルで管理する。

### 6-5. 調査関連日時

- 調査開始日時：問題調査を開始した日時
- 対応案策定予定日時：対応案を策定する予定日時
- 進捗更新の次回更新予定日時：次に進捗を更新する予定日時
- リアクション要求日時：問い合わせ者への解決確認依頼を行った日時
- 問題調査断念日時：問題調査そのものを断念した日時

これらは業務イベントや予定を記録する項目であり、状態そのものとは区別する。

### 6-6. 最新移行先の問題調査番号

最新移行先の問題調査番号は、NGによる再調査への移行先を記録する。

問題調査テーブル自身の問題調査番号を参照する自己参照外部キーである。

NGによる移行先を決める際は、移行元のこの項目を利用する。移行先が存在し、調査中であれば、その問題調査を移行先として利用する。それ以外の場合は新しい問題調査を作成し、移行元の最新移行先として記録する。

他の移行元が参照している問題調査を横断的に検索して、自動的に統合する仕様にはしない。

## 7. 問い合わせ問題調査テーブル

問い合わせ問題調査テーブルは、問い合わせと問題調査の関連、およびその関連ごとの調査・解決確認の状態と履歴を管理する。

同じ問題調査に複数の問い合わせが関連付けられる場合でも、問い合わせ者ごとの反応や断念状況は個別に管理する。

### 7-1. カラム

| カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|
| 問い合わせ問題調査番号 | INTEGER | 不可 | 主キー、IDENTITY |
| 問題調査番号 | INTEGER | 不可 | 問題調査への外部キー |
| 問い合わせ番号 | INTEGER | 不可 | 問い合わせへの外部キー |
| 問い合わせ問題調査状態 | INTEGER | 不可 | 初期値1、CHECK：1～5 |
| 調査開始日時 | TIMESTAMP | 不可 | 初期値：CURRENT_TIMESTAMP |
| 断念日時 | TIMESTAMP | 可 | 当該問い合わせとの関係を断念した日時 |
| リアクション被要求日時 | TIMESTAMP | 可 | 問い合わせ者に解決確認を要求した日時 |
| リアクション日時 | TIMESTAMP | 可 | 問い合わせ者から反応を受けた日時 |
| リアクション内容 | INTEGER | 可 | CHECK：1、2 |
| NGでの移行先問題調査番号 | INTEGER | 可 | 移行先の問題調査への外部キー |

### 7-2. 問い合わせ問題調査状態

問い合わせ問題調査状態は、次の値で管理する。

| 値 | 状態 | 意味 |
|---|---|---|
| 1 | 調査中 | 当該問い合わせについて調査を進めている |
| 2 | 断念 | 当該問い合わせと問題調査の関係を断念した |
| 3 | リアクション待ち | 問い合わせ者からの解決確認を待っている |
| 4 | OK | 問い合わせ者から解決確認のOKを受けた |
| 5 | NG | 問い合わせ者からNGを受け、再調査へ移行した |

初期値は1とする。

この状態は、問い合わせ全体の状態や問題調査そのものの状態とは別に管理する。

### 7-3. 状態と日時の関係

状態と日時は同じものとして扱わない。

状態は「現在、どの段階にあるか」を示し、日時は「業務イベントがいつ発生したか」を記録する。

| 業務イベント | 状態・日時の扱い |
|---|---|
| 問い合わせに問題調査を関連付ける | 状態1、調査開始日時を設定 |
| 問い合わせ者にリアクションを要求する | 状態3、リアクション被要求日時を設定 |
| 問い合わせ者からOKを受ける | 状態4、リアクション内容1、リアクション日時を設定 |
| 問い合わせ者からNGを受ける | 状態5、リアクション内容2、リアクション日時、移行先を設定 |
| 当該問い合わせとの関係を断念する | 状態2、断念日時を設定 |

リアクション要求時点では、調査を終了した日時や断念日時を設定しない。

### 7-4. リアクション要求

リアクション要求は、同じ問題調査に関連付けられた問い合わせのうち、状態1のレコードを対象に行う。

すでに状態2のレコードは対象外とする。要求対象となったレコードには状態3とリアクション被要求日時を設定する。

同じ問題調査に関連付けられた問い合わせ者には、共通の原因・対応案を提示する。

### 7-5. OKを受けた場合

問い合わせ者からOKを受けた場合、対象レコードを状態4にする。

リアクション内容には1を、リアクション日時には反応を受けた日時を記録する。

この処理によって、当該問い合わせと問題調査の関係における解決確認は完了する。ただし、問い合わせ全体の対応完了は自動的に行わない。

### 7-6. NGを受けた場合

問い合わせ者からNGを受けた場合、既存レコードを削除せず、状態5に更新する。

リアクション内容には2を設定し、リアクション日時とNGでの移行先問題調査番号を記録する。

その後、同じ問い合わせについて、移行先の問題調査と関連付ける新しい問い合わせ問題調査レコードを作成する。新しいレコードの状態は初期値1とする。

これにより、移行前の履歴と移行後の調査を区別して保持できる。

### 7-7. 当該問い合わせとの関係を断念する場合

特定の問い合わせについて調査を断念する場合は、対象の問い合わせ問題調査レコードを状態2にし、断念日時を記録する。

この処理は、同じ問題調査に関連付けられた他の問い合わせの状態には影響しない。

問題調査そのものを断念する処理とは区別する。

## 8. 対応担当者変更履歴テーブル

対応担当者変更履歴テーブルは、問い合わせの対応担当者が変更された経過を記録する。

### 8-1. カラム

| カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|
| 問い合わせ番号 | INTEGER | 不可 | 問い合わせへの外部キー |
| 変更日時 | TIMESTAMP | 不可 | 初期値：CURRENT_TIMESTAMP |
| 変更後の対応担当者氏名 | VARCHAR(30) | 不可 | |
| 変更処理した職員氏名 | VARCHAR(30) | 不可 | |
| 変更理由 | VARCHAR(500) | 可 | |

### 8-2. 主キー

問い合わせ番号と変更日時の複合主キーとする。

同じ問い合わせについて複数回の変更履歴を保持する。

### 8-3. 設計方針

問い合わせテーブルには現在の対応担当者を保持し、本テーブルには変更の履歴を記録する。

現在の担当者情報と過去の変更履歴を分離することで、担当者の変更経過を追跡できる。

## 9. 主キー・外部キー

### 9-1. 主キー

主キーは、テーブル内のレコードを一意に識別するために設定する。

- 職員：職員番号
- 問い合わせ：問い合わせ番号
- 問題調査：問題調査番号
- 問い合わせ問題調査：問い合わせ問題調査番号
- 対応担当者変更履歴：問い合わせ番号と変更日時の複合主キー

問い合わせ、問題調査、問い合わせ問題調査の各番号はIDENTITYによって採番する。

### 9-2. 外部キー

外部キーによって、関連するレコードの存在を保証する。

- 問い合わせ.問い合わせ職員番号 → 職員.職員番号
- 問い合わせ.受付担当者 → 職員.職員番号
- 問い合わせ.対応担当者 → 職員.職員番号
- 問い合わせ問題調査.問い合わせ番号 → 問い合わせ.問い合わせ番号
- 問い合わせ問題調査.問題調査番号 → 問題調査.問題調査番号
- 問題調査.最新移行先の問題調査番号 → 問題調査.問題調査番号
- 問い合わせ問題調査.NGでの移行先問題調査番号 → 問題調査.問題調査番号
- 対応担当者変更履歴.問い合わせ番号 → 問い合わせ.問い合わせ番号

職員テーブルのレコードが削除された場合、問い合わせ履歴を保持するため、問い合わせ者、受付担当者、対応担当者の各職員番号は NULL とする（ON DELETE SET NULL）。

このため、上記3項目はNULLを許容する。ただし、通常の問い合わせ登録時には、APIで職員番号の存在を確認する。

外部キーは参照先レコードの存在を保証するものであり、業務上の状態遷移や更新可能条件まで自動的に保証するものではない。それらはAPI層などで制御する。

## 10. NULLの考え方

NULLは、値が未設定であることを表す。

NULLを0や空文字と同じものとして扱わない。

### 10-1. NULLを許容する主な項目

- 問い合わせ.対応担当者
- 問い合わせ.引き受け日時
- 問い合わせ.対応完了日時
- 問題調査.問題の原因
- 問題調査.情シス側での対応
- 問題調査.問い合わせ者側で必要な対応
- 問題調査.リアクション要求日時
- 問題調査.問題調査断念日時
- 問題調査.最新移行先の問題調査番号
- 問い合わせ問題調査.断念日時
- 問い合わせ問題調査.リアクション被要求日時
- 問い合わせ問題調査.リアクション日時
- 問い合わせ問題調査.リアクション内容
- 問い合わせ問題調査.NGでの移行先問題調査番号
- 対応担当者変更履歴.変更理由

### 10-2. NULLを許容する理由

調査開始時点では原因や対応案が確定していないことがある。

また、問い合わせを引き受ける前や、リアクション要求を行う前には、それぞれの日時がまだ存在しない。

このように、業務の進行に伴って設定される項目は、未発生・未確定の段階ではNULLを許容する。

## 11. 問い合わせ全体の状態判定

問い合わせ全体の状態は、専用の状態カラムを設けず、引き受け日時と対応完了日時から判定する。

| 条件 | 判定する状態 |
|---|---|
| 引き受け日時がNULL、対応完了日時がNULL | 対応待ち |
| 引き受け日時がNULLでなく、対応完了日時がNULL | 対応中 |
| 対応完了日時がNULLでない | 対応完了 |

この設計により、日時と状態の二重管理による不整合を防ぐ。

即時解決など、受付時点で対応が完了する問い合わせでは、登録時に対応完了日時を設定できる。対応担当者が設定されない場合もある。

## 12. 問い合わせ全体と問い合わせ問題調査の関係

問い合わせ全体の対応状態と、個々の問い合わせ問題調査の状態は、独立して管理する。

例えば、ある問い合わせに関連付けられた問題調査について、すべてOKまたは断念となっていても、それだけで問い合わせ全体を対応完了にはしない。

問い合わせ全体の対応完了は、対応担当者が明示的に実行する。

また、問い合わせ全体が対応中であっても、特定の問い合わせ問題調査についてはリアクション待ちやOKなどの状態になり得る。

これらの状態を混同しないことを、本システムの重要な設計方針とする。

## 13. 問い合わせ全体の対応完了

問い合わせ全体の対応完了は、対応担当者が明示的に実行する。

対応完了日時に完了処理の日時を設定することで、問い合わせ全体を対応完了と判定する。

問題調査や問い合わせ問題調査の状態だけを根拠として、問い合わせ全体の対応完了日時を自動設定しない。

対応完了処理を実行できる条件などの業務制御は、画面設計・API設計と整合させる。

## 14. 対応完了後の再開

問い合わせ対応完了後の再開機能については、今後の実装に向けて詳細仕様を検討する。

再開時の状態変更、過去の問い合わせ問題調査レコードの取り扱い、および再開後の問題調査との関連付けについては、詳細仕様の確定後に定義する。

なお、過去の対応経過を保持するというデータ管理方針は維持する。

## 15. 問題調査の共有

問題調査テーブルには、問題調査の名称や仮説、共通の原因、情シス側での対応、問い合わせ者側で必要な対応を保持する。

同じ問題調査に関連付けられた複数の問い合わせに対して、共通の調査結果や対応案を提示できる構造とする。

一方、問い合わせ者からのOK・NGや、個別の断念状況は問い合わせ問題調査テーブルで管理する。

共通する調査情報と、問い合わせごとに異なる反応・進捗を分離することで、同一の問題調査に関連する問い合わせ間で状態が不整合になることを防ぐ。

## 16. データの責任範囲

各テーブルが管理する情報の責任範囲を、次のように定義する。

| 情報 | 管理するテーブル |
|---|---|
| 職員の基本情報 | 職員 |
| 問い合わせ全体の情報・担当者・完了日時 | 問い合わせ |
| 共通する原因・対応案・調査状態・移行先 | 問題調査 |
| 問い合わせと問題調査の関係・個別状態・反応履歴 | 問い合わせ問題調査 |
| 対応担当者の変更経過 | 対応担当者変更履歴 |

情報の責任範囲を明確にし、同じ意味の情報を複数のテーブルで重複管理しない。

ただし、問い合わせ当時の所属など、過去の状態を保持する目的で保存する情報は、現在のマスタ情報とは別に管理する。

## 17. 状態を持たせる項目と持たせない項目

状態管理は、対象となる業務単位ごとに行う。

### 17-1. 問い合わせ

問い合わせ全体には専用の状態カラムを設けない。

引き受け日時と対応完了日時から状態を判定する。

### 17-2. 問題調査

問題調査そのものの状態は、問題調査状態カラムで管理する。

1：調査中、2：リアクション要求済み、3：問題調査断念とする。

### 17-3. 問い合わせ問題調査

問い合わせと問題調査の関係ごとの状態は、問い合わせ問題調査状態カラムで管理する。

1：調査中、2：断念、3：リアクション待ち、4：OK、5：NGとする。

日時は状態そのものを表すためではなく、業務イベントが発生した時点を記録するために使用する。

## 18. 業務上の日時と状態の役割

本システムでは、日時と状態の役割を明確に分ける。

| 業務イベント | 対象テーブル | 主な記録項目 |
|---|---|---|
| 問い合わせを受信した | 問い合わせ | 受信日時 |
| 問い合わせを登録した | 問い合わせ | 登録日時 |
| 問い合わせを引き受けた | 問い合わせ | 対応担当者、引き受け日時 |
| 問題調査を開始した | 問題調査・問い合わせ問題調査 | 調査開始日時 |
| 問い合わせ者にリアクションを要求した | 問題調査・問い合わせ問題調査 | リアクション要求日時、リアクション被要求日時 |
| 問い合わせ者からOKを受けた | 問い合わせ問題調査 | リアクション内容、リアクション日時 |
| 問い合わせ者からNGを受けた | 問い合わせ問題調査 | リアクション内容、リアクション日時、NGでの移行先問題調査番号 |
| 問題調査そのものを断念した | 問題調査 | 問題調査状態、問題調査断念日時 |
| 個別の問い合わせとの関係を断念した | 問い合わせ問題調査 | 問い合わせ問題調査状態、断念日時 |
| 問い合わせ全体の対応を完了した | 問い合わせ | 対応完了日時 |

同じ「完了」や「断念」に関係するイベントであっても、対象となる業務単位を明確に区別する。

## 19. データ整合性に関する考え方

データ整合性を確保するため、DB制約とアプリケーション側の業務制御を組み合わせる。

### 19-1. DB制約で保証すること

- 主キーによるレコードの一意性
- 外部キーによる参照先レコードの存在
- NOT NULLによる必須項目の入力
- CHECK制約による緊急度、受付時の処理、各状態、リアクション内容の許容値制限

### 19-2. アプリケーション側で制御すること

- ログインユーザーの役割に応じた操作権限
- 問い合わせの引き受け、対応完了等の実行条件
- 問題調査の状態に応じた内容変更の可否
- 問い合わせ問題調査の状態遷移
- NGによる移行先の選択と新規レコード作成
- 状態変更と日時記録の整合性
- 対応担当者の変更と履歴の記録

DB制約だけでは表現しきれない業務ルールは、API層で検証し、必要な更新を一連のトランザクションとして実行する。

## 20. DBに保持しない情報

DBには、業務上の意味を持つ情報や履歴を保持する。

一方、画面表示のためだけに導出できる情報は、原則として重複して保持しない。

例えば、問い合わせ全体の状態は、引き受け日時と対応完了日時から判定できるため、別途状態カラムを設けない。

また、問い合わせ者からの反応によって問い合わせ全体が自動完了するような、実際の業務ルールにない状態変化は行わない。

## 21. 履歴情報の保持方針

本システムでは、業務上必要な履歴を保持する。

### 21-1. 対応担当者変更履歴

対応担当者の変更前後の経過を追跡できるよう、変更のたびに履歴レコードを記録する。

### 21-2. 問い合わせ問題調査の履歴

NGによる再調査への移行時は、移行前のレコードを削除せず、状態5と移行先を記録する。

移行後は、新しい問い合わせ問題調査レコードを作成する。

### 21-3. 問い合わせ全体の履歴

問い合わせ全体の対応完了と、個々の問題調査の進捗を区別して記録する。

対応完了後の再開については、詳細仕様の確定後に履歴の扱いを定義する。

## 22. 要件・業務フローとの対応

各業務処理で主に参照・更新するテーブルと項目を以下に整理する。

| 業務処理 | 主な対象テーブル | 主な更新項目 |
|---|---|---|
| 問い合わせ登録 | 問い合わせ | 問い合わせ情報、受付担当者、受信日時、登録日時 |
| 問い合わせ引き受け | 問い合わせ | 対応担当者、引き受け日時 |
| 対応担当者変更 | 問い合わせ、対応担当者変更履歴 | 対応担当者、変更履歴 |
| 問題調査開始 | 問題調査、問い合わせ問題調査 | 問題調査情報、調査開始日時、関連レコード |
| 調査内容・対応案の更新 | 問題調査 | 名称や仮説、原因、対応案、予定日時 |
| リアクション要求 | 問題調査、問い合わせ問題調査 | 問題調査状態、リアクション要求日時、個別状態、リアクション被要求日時 |
| 問い合わせ者からOK | 問い合わせ問題調査 | 状態、リアクション内容、リアクション日時 |
| 問い合わせ者からNG | 問題調査、問い合わせ問題調査 | 移行先、最新移行先、状態、リアクション内容、リアクション日時 |
| 問題調査そのものの断念 | 問題調査 | 問題調査状態、問題調査断念日時 |
| 個別の問い合わせとの関係の断念 | 問い合わせ問題調査 | 状態、断念日時 |
| 問い合わせ全体の対応完了 | 問い合わせ | 対応完了日時 |
| 対応完了後の再開 | 今後定義 | 詳細仕様検討中 |

画面・APIの実装時には、本設計書の状態管理と日時管理の方針に従う。

## 23. SQLテスト一覧

データベース設計に基づき、主要な業務フローについてSQLテストを実施する。

| テスト番号 | テスト内容 | 主な確認事項 |
|---|---|---|
| 01 | DDL・テーブル作成 | テーブル、主キー、外部キー、CHECK制約等が定義どおり作成されること |
| 02 | 問い合わせ登録 | 問い合わせ情報が登録され、初期状態を正しく判定できること |
| 03 | 問い合わせ引き受け | 対応担当者と引き受け日時が設定され、問い合わせ全体が対応中と判定できること |
| 04 | 問題調査開始 | 問題調査と問い合わせ問題調査が適切に作成・関連付けされること |
| 05 | リアクション要求 | 対象となる問い合わせ問題調査がリアクション待ちとなり、日時が記録されること |
| 06 | OK | 個別レコードがOKとなり、リアクション内容と日時が記録されること |
| 07 | 断念 | 問題調査そのもの、または個別の関係を断念した場合に、対象の状態と日時が正しく更新されること |
| 08 | NGによる移行 | 移行前の履歴を保持し、移行先を適切に選択または作成し、新しい関連レコードを作成できること |

対応完了後の再開については、詳細仕様が確定していないため、現時点のSQLテスト対象から除外する。

各テストは、正常系だけでなく、対象外レコードが更新されないこと、状態と日時の整合性が保たれること、および過去の履歴が失われないことも確認する。
