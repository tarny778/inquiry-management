# 20261007午後_03_データベース設計

## 1. データベース設計の目的

本設計書では、「問い合わせ管理Webアプリ」で使用するデータベースについて、テーブル構成、カラム、データ型、制約、各項目の意味および状態管理方法を定義する。

本システムでは、問い合わせそのものと、問い合わせに紐づく問題を分離して管理する。

- **問い合わせ**：問い合わせ者から受け付けた一連の問い合わせ
- **問題**：問い合わせの原因となる具体的な問題
- **問い合わせ問題**：ある問い合わせと、ある問題との関係

同じ問題が複数の問い合わせで発生する可能性があるため、「問題」は問い合わせから独立した情報として管理する。

---

## 2. データベース管理システム

PostgreSQLを使用する。

---

## 3. テーブル構成

本システムでは、以下の5テーブルを基本とする。

1. 職員

3. 問題

### 5-2. 職員情報の保持方法

問い合わせテーブルでは、職員情報について「最新の情報を参照するもの」と「問い合わせ当時の事実として保存するもの」を区別して管理する。

#### 問い合わせ者

「問い合わせ職員番号」は職員テーブルへのFKとして保持する。

問い合わせ者の氏名は問い合わせテーブルには保存せず、職員番号を利用して職員テーブルからJOINして表示する。

これにより、職員の氏名が変更された場合でも、現在の氏名を表示できる。

一方、「問い合わせ当時の所属」はスナップショットとして保持する。

これは、職員マスタの現在の所属ではなく、**問い合わせを受け付けた当時の所属**を記録するためである。

問い合わせ当時の所属を基準とした統計・検索を将来行う可能性があるため、職員テーブルから現在の所属を取得する方式にはしない。

職員が退職等により将来職員マスタから削除された場合、問い合わせ者の氏名を過去の問い合わせから導出できなくなる可能性はある。

しかし、数年後に問い合わせ者の氏名を追跡する必要性は低いと判断し、氏名のスナップショットは保持しない。

#### 受付担当者

受付担当者は、問い合わせを電話、メール等で受け付け、その内容を問い合わせレコードとして登録した職員を指す。

受付・登録というフェーズを担った職員であり、過去の事実として記録する必要がある。

そのため、職員番号をFKとして保持するのではなく、受付担当者の氏名をスナップショットとして保持する。

#### 対応担当者

対応担当者は、要調査の問い合わせについて、紐づく問題を調査し、調査状況を更新し、問い合わせ者にリアクションを求め、必要に応じて再調査を行い、最終的に問い合わせを対応完了へ導く職員を指す。

対応担当者は、現在の対応責任者を示すため、問い合わせテーブルに保持する。

対応担当者についても、将来にわたって当時の責任所在を追跡できるよう、氏名をスナップショットとして保持する。

受付担当者と対応担当者は、単純に「過去の担当者」と「現在の担当者」という時間軸だけで区別するものではなく、それぞれ異なる業務フェーズと役割を担う。

受付担当者と対応担当者が同一人物となることもある。

### 5-3. 対応担当者の変更

対応担当者を変更した場合、問い合わせテーブルの「対応担当者」を現在の担当者に更新する。

過去の変更については、「対応担当者変更履歴」に記録する。

対応担当者の変更処理を行った職員についても、将来の責任所在を追跡できるよう、スナップショットとして履歴に保存する。

### 5-4. 問い合わせ全体の状態

問い合わせテーブルには「問い合わせ状態」カラムを持たせない。

問い合わせ全体の状態は、「引き受け日時」と「対応完了日時」から判断する。

| 状態 | 引き受け日時 | 対応完了日時 |
|---|---|---|
| 引き受け待ち | NULL | NULL |
| 対応中 | NOT NULL | NULL |
| 対応完了 | NOT NULL | NOT NULL |

対応担当者が問い合わせを引き受けると「引き受け日時」を設定し、問い合わせ全体は「対応中」となる。

対応担当者が明示的に対応完了を行った時点で「対応完了日時」を設定し、問い合わせ全体を「対応完了」とする。

問い合わせ問題の状態が「調査無事終了」となったことだけでは、問い合わせ全体は自動的に対応完了とはしない。

### 5-5. 即時解決・他所属へ案内

受付時処理が以下の場合、問題を登録せずに問い合わせ全体を完了できる。

- 即時解決
- 他所属へ案内

この場合、対応完了日時には登録日時を設定する。

## 6. 問題テーブル

問題テーブルは、問い合わせの原因となる具体的な問題を管理する。

同じ問題が複数の問い合わせから発生する可能性があるため、問い合わせとは独立して管理する。

### 6-1. カラム

| No. | カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|---|
| 1 | 問題番号 | INTEGER | 不可 | PK、IDENTITY |
| 2 | 問題名称 | VARCHAR(30) | 不可 | |
| 3 | 問題の原因 | VARCHAR(1000) | 可 | |
| 4 | 情シス側での対応 | VARCHAR(1000) | 可 | |
| 5 | 問い合わせ者側で必要な対応 | VARCHAR(1000) | 可 | |
| 6 | 原因と対応の最新更新日時 | TIMESTAMP | 可 | |

### 6-2. 問題テーブルの状態管理

問題テーブルには状態を表すカラムを持たせない。

問題そのものは「調査中」「解決済み」等の状態を持つものではなく、原因・対応方法等の知識を管理するための情報として扱う。

問い合わせごとの調査状態は、「問い合わせ問題」テーブルで管理する。

### 6-3. 原因と対応の最新更新日時

「原因と対応の最新更新日時」は、問題テーブルに保持している原因、情シス側での対応、問い合わせ者側で必要な対応等の情報を最後に更新した日時を記録する。

ある問い合わせ者から未解決のリアクションを受けたことだけを理由として、この日時をNULLにしたり更新したりしない。

問題は複数の問い合わせから共有される可能性があるためである。

---

## 7. 問い合わせ問題テーブル

問い合わせ問題テーブルは、問い合わせと問題の関係を管理する。

1つの問い合わせに複数の問題を関連付けることができる。

また、1つの問題を複数の問い合わせに関連付けることができる。

そのため、問い合わせと問題の多対多の関係を管理する中間テーブルとして機能する。

### 7-1. カラム

| No. | カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|---|
| 1 | 問題番号 | INTEGER | 不可 | FK → 問題.問題番号 |
| 2 | 問い合わせ番号 | INTEGER | 不可 | FK → 問い合わせ.問い合わせ番号 |
| 3 | 問い合わせ問題状態 | INTEGER | 不可 | 1～4 |
| 4 | 現在の調査状況 | VARCHAR(1000) | 不可 | 対応担当者が入力 |
| 5 | 内部メモ | VARCHAR(1000) | 可 | |
| 6 | 予定解決日時 | TIMESTAMP | 可 | |
| 7 | 次回進捗更新予定日時 | TIMESTAMP | 可 | |
| 8 | 調査開始日時 | TIMESTAMP | 不可 | |
| 9 | 調査を終えた日時 | TIMESTAMP | 可 | |
| 10 | 最新NG日時 | TIMESTAMP | 可 | |
| 11 | リアクション要求最新日時 | TIMESTAMP | 可 | |

主キーは「問題番号」と「問い合わせ番号」の複合主キーとする。

### 7-2. 問い合わせ問題状態

「問い合わせ問題状態」は、問い合わせと問題との関係について、現在どの状態にあるかを管理する。

状態は以下の4種類とする。

| 値 | 状態 |
|---|---|
| 1 | 調査中 |
| 2 | リアクション待ち |
| 3 | 調査無事終了 |
| 4 | 調査断念 |

この状態は日時から推測するのではなく、業務上の判断に基づいて明示的に更新する。

### 7-3. 状態遷移

基本的な状態遷移は以下とする。

```text
調査中
  │
  │ リアクションを要求
  ↓
リアクション待ち
  │
  ├─ OK ─→ 調査無事終了
  │
  └─ NG ─→ 調査中
               │
               └─ 再調査
                    │
                    └─ リアクションを要求
                         ↓
                      リアクション待ち

調査中
  │
  └─ 調査断念 → 調査断念
```

### 7-4. 調査開始日時

「調査開始日時」は、その問い合わせ問題について最初に調査を開始した日時を記録する。

問い合わせ者からNGのリアクションを受けて再調査する場合でも、調査開始日時は更新しない。

これは、再調査を含めた一連の調査について、最初に調査を開始した時点を記録するためである。

### 7-5. 調査を終えた日時

「調査を終えた日時」は、単なる一回の調査作業が終了した日時ではない。

その問い合わせと問題との関係について、最終的に調査を終了した日時を記録する。

以下の場合に設定する。

- 問い合わせ者からOKを受け、「調査無事終了」となった場合
- 対応担当者が関連する問題の調査を断念し、「調査断念」となった場合

一方、リアクションを要求して「リアクション待ち」となった時点では、まだ最終的に終了していないためNULLとする。

問い合わせ者からNGを受けて「調査中」に戻った場合もNULLのままとする。

### 7-6. 最新NG日時

「最新NG日時」は、問い合わせ者から最後に「解決していない」と回答された日時を記録する。

NGが複数回発生した場合は、そのたびに最新の日時へ更新する。

NGの全履歴をこのカラムだけで管理するものではない。

### 7-7. リアクション要求最新日時

「リアクション要求最新日時」は、問い合わせ者に対して最後にリアクションを要求した日時を記録する。

再調査後に再度リアクションを要求した場合は、その日時に更新する。

### 7-8. 現在の調査状況

「現在の調査状況」は、対応担当者が現在の調査・対応内容を自由記述する項目である。

システムが問い合わせ者からのNGを受けたことだけを理由に、「再調査中」等の文言へ自動変更することはしない。

---

## 8. 問い合わせ問題の状態と日時の関係

状態と日時は、それぞれ異なる役割を持つ。

| 業務イベント | 問い合わせ問題状態 | 調査を終えた日時 | 最新NG日時 | リアクション要求最新日時 |
|---|---:|---|---|---|
| 調査開始 | 1 調査中 | NULL | NULL | NULL |
| リアクション要求 | 2 リアクション待ち | NULL | 既存値を維持 | 現在日時 |
| 問い合わせ者NG | 1 調査中 | NULL | 現在日時 | 既存値を維持 |
| 問い合わせ者OK | 3 調査無事終了 | 現在日時 | 既存値を維持 | 既存値を維持 |
| 調査断念 | 4 調査断念 | 現在日時 | 既存値を維持 | 既存値を維持 |

「調査を終えた日時」は、リアクション要求時には設定しない。

また、NGによる再調査時に「調査を終えた日時」をNULLに戻すという処理も行わない。NGを受けた時点でも、そもそもこの日時はNULLだからである。

---

## 9. 対応担当者変更履歴テーブル

対応担当者変更履歴テーブルは、問い合わせの対応担当者が変更された履歴を管理する。

現在の対応担当者は問い合わせテーブルで管理し、過去の変更については本テーブルで管理する。

### 9-1. カラム

| No. | カラム名 | データ型 | NULL | 制約・備考 |
|---|---|---|---|---|
| 1 | 問い合わせ番号 | INTEGER | 不可 | FK → 問い合わせ.問い合わせ番号 |
| 2 | 変更日時 | TIMESTAMP | 不可 | |
| 3 | 変更後の対応担当者氏名 | VARCHAR(30) | 不可 | スナップショット |
| 4 | 変更処理した職員氏名 | VARCHAR(30) | 不可 | スナップショット |
| 5 | 変更理由 | VARCHAR(500) | 可 | |

「問い合わせ番号」と「変更日時」を主キーとする。

### 9-2. スナップショットとする理由

対応担当者および変更処理者は、基本的に情シス所属の職員を想定する。

これらについては、将来、職員マスタから職員が削除された場合でも、

- 誰が対応担当者だったのか
- 誰が担当変更を処理したのか

という過去の責任所在を追跡できる必要がある。

そのため、職員番号をFKとして参照するのではなく、担当者氏名をスナップショットとして保存する。

## 11. NULLの考え方

NULLは、「まだ発生していない」「該当しない」等の意味で使用する。

代表例：

- 対応担当者：まだ引き受けられていない場合
- 引き受け日時：まだ引き受けられていない場合
- 対応完了日時：まだ対応完了していない場合
- 調査を終えた日時：問い合わせ問題がまだ最終終了していない場合
- 最新NG日時：まだNGが発生していない場合
- リアクション要求最新日時：まだリアクションを要求していない場合

## 12. 問い合わせ全体の状態判定

問い合わせ全体の状態は、以下のルールで判定する。

### 引き受け待ち

```text
引き受け日時 IS NULL
AND
対応完了日時 IS NULL
```

### 対応中

```text
引き受け日時 IS NOT NULL
AND
対応完了日時 IS NULL
```

### 対応完了

```text
対応完了日時 IS NOT NULL
```

問い合わせ状態を別カラムとして保持しないことで、日時と状態が不整合になることを防ぐ。

---

## 13. 問い合わせ問題状態の管理

問い合わせ問題状態は、以下の値をDBに保持する。

```text
1 = 調査中
2 = リアクション待ち
3 = 調査無事終了
4 = 調査断念
```

DBでは1～4以外の値を登録できないようCHECK制約を設定する。

問い合わせ問題状態は、調査日時等から自動判定するものではない。

---

## 14. 問い合わせ全体と問い合わせ問題の関係

問い合わせ全体の状態と、問い合わせ問題の状態は別々に管理する。

例えば、以下の状態が成立する。

```text
問い合わせ
  └─ 対応中

     問い合わせ問題A
       └─ 調査無事終了

     問い合わせ問題B
       └─ 調査中
```

また、すべての問い合わせ問題が「調査無事終了」または「調査断念」となっても、問い合わせ全体を自動的に対応完了にはしない。

対応担当者が問い合わせ全体を確認し、明示的に対応完了とした時点で「対応完了日時」を設定する。

---

## 15. 問い合わせ全体の対応完了

対応担当者が問い合わせ全体として対応完了と判断した場合、問い合わせテーブルの「対応完了日時」に現在日時を設定する。

対応完了日時は、問題の調査終了日時や問い合わせ者のOK日時をコピーするものではない。

**対応担当者が問い合わせ全体を対応完了とした時点の日時**を記録する。

そのため、以下のような状態も成立する。

```text
問題A：調査無事終了
問題B：調査断念

問い合わせ全体：対応中
```

この状態から、対応担当者が問い合わせ全体の対応完了を実行することで、

```text
問い合わせ全体：対応完了
```

となる。

---

## 16. 対応完了後の再開

対応完了後、一定期間を「対応再開依頼受付期間」とする。

対応再開依頼受付期間内に問い合わせ者から再開依頼があった場合は、既存の問い合わせを再開する。

再開時には、

```text
対応完了日時 = NULL
```

とする。

これにより、問い合わせ全体は「対応中」に戻る。

現在の対応担当者は変更せず、現在の対応担当者へ再対応を通知する。

対応再開依頼受付期間の具体的な期間および営業日による判定方法は、今後決定する。

対応再開依頼受付期間を過ぎた後に新たな対応が必要となった場合は、新しい問い合わせとして登録し、新しい問い合わせ番号を付与する。

---

## 17. 問題の共有

同じ問題が複数の問い合わせで発生する可能性がある。

例えば、

```text
問い合わせ001 ─┐
問い合わせ002 ─┼─ 問題100
問い合わせ003 ─┘
```

のような関係を持つことができる。

問題の原因や対応方法等の知識は問題テーブルに保持し、個々の問い合わせにおける調査状況やリアクション状況は問い合わせ問題テーブルに保持する。

これにより、共有される知識と個別問い合わせの進捗を分離する。

---

## 18. データの責任範囲

各テーブルの役割は以下のとおり。

### 職員

現在の職員情報を管理する。

### 問い合わせ

問い合わせそのものと、問い合わせ全体の受付・担当・完了に関する情報を管理する。

### 問題

問題に関する知識を管理する。

### 問い合わせ問題

問い合わせと問題の関係、およびその関係についての調査状況・リアクション状況を管理する。

### 対応担当者変更履歴

対応担当者の変更履歴を管理する。

---

## 19. 状態を持たせる項目と持たせない項目

### 状態を持たせる

```text
問い合わせ問題.問い合わせ問題状態
```

問い合わせ問題について、現在の業務上の判断状態を明示的に管理する必要があるため。

### 状態を持たせない

```text
問い合わせ.問い合わせ状態
問題.問題状態
```

問い合わせ全体の状態は引き受け日時・対応完了日時から判定できる。

問題自体には、問い合わせごとの調査状態を持たせる必要がない。

---

## 20. 業務上の日時と状態の役割

日時は状態そのものではなく、業務上発生したイベントの時点を記録する。

主な日時項目：

- 受信日時
- 登録日時
- 引き受け日時
- 対応完了日時
- 調査開始日時
- 調査を終えた日時
- 最新NG日時
- リアクション要求最新日時
- 原因と対応の最新更新日時

状態は、必要な場合に「問い合わせ問題状態」として明示的に保持する。

---

## 21. データ整合性に関する考え方

DB上で以下の整合性を確保する。

### 問い合わせ

- 問い合わせ番号は一意
- 問い合わせ職員番号は職員テーブルに存在する
- 受付時の処理は1～3
- 対応完了日時は、対応完了前はNULL
- 引き受け日時が設定されることで、問い合わせ全体を対応中として扱う

### 問題

- 問題番号は一意

### 問い合わせ問題

- 問題番号と問い合わせ番号の組み合わせは一意
- 問題番号は問題テーブルに存在する
- 問い合わせ番号は問い合わせテーブルに存在する
- 問い合わせ問題状態は1～4
- 調査を終えた日時は、状態3または4となった場合に設定する
- 状態1または2では調査を終えた日時をNULLとする

---

## 22. DBに保持しない情報

以下は、重複して保持しない。

### 問い合わせ全体の状態

「問い合わせ状態」というカラムは作成しない。

引き受け日時と対応完了日時から判定する。

### 問い合わせ者の氏名

問い合わせテーブルには保持しない。

問い合わせ職員番号から職員テーブルをJOINして表示する。

### 問題の状態

問題テーブルには状態カラムを作成しない。

問い合わせごとの状態は問い合わせ問題テーブルで管理する。

### 問い合わせ問題の状態を表す複数のフラグ

例えば、

```text
調査中フラグ
リアクション待ちフラグ
調査終了フラグ
調査断念フラグ
```

のような複数のboolean型カラムは作成しない。

「問い合わせ問題状態」という1つの状態カラムで管理する。

### 問い合わせ全体の未解決リアクション状態

問い合わせ問題単位でNGを管理するため、問い合わせテーブルには未解決リアクション専用の状態カラムを持たせない。

---

## 23. 対応完了後の問い合わせの扱い

対応完了後も、問い合わせレコード自体は削除しない。

対応履歴および過去の問い合わせ情報として保持する。

対応再開依頼受付期間内であれば、同じ問い合わせを再開する。

期間終了後に新たな対応が必要となった場合は、新しい問い合わせとして登録する。

---

## 24. 履歴情報の保持方針

本システムでは、「現在の情報」と「過去の事実」を区別して保持する。

### 最新情報を参照するもの

問い合わせ者の氏名など、職員番号から現在の情報を取得するもの。

### 当時の事実を保持するもの

- 問い合わせ当時の所属
- 受付担当者
- 現在の対応担当者
- 対応担当者変更履歴における変更後担当者
- 対応担当者変更履歴における変更処理者

これらは、将来マスタ情報が変更・削除された場合でも、当時の情報を追跡する必要があるため、スナップショットとして保持する。

---

## 25. データベース設計の基本原則

本システムでは、以下を基本原則とする。

1. 問い合わせと問題を分離する。
2. 問い合わせと問題の関係を「問い合わせ問題」で管理する。
3. 問い合わせ全体の状態は、引き受け日時と対応完了日時から判定する。
4. 問い合わせ問題の状態は、「問い合わせ問題状態」カラムで管理する。
5. 問題そのものには状態を持たせない。
6. 日時カラムは、状態ではなく業務イベントが発生した時点を記録する。
7. 問い合わせ者の職員番号はFKとして保持する。
8. 問い合わせ者の氏名は職員マスタからJOINして取得する。
9. 問い合わせ当時の所属はスナップショットとして保持する。
10. 受付担当者・対応担当者・担当変更処理者は、過去の責任所在を追跡できるようスナップショットとして保持する。
11. 問い合わせ問題の調査終了は、問い合わせ者のOKまたは調査断念によって確定する。
12. 問い合わせ問題が終了したことと、問い合わせ全体が対応完了となることを分離する。
13. 問い合わせ全体の対応完了は、対応担当者の明示的な操作によって記録する。
14. 対応完了後の再開は、対応再開依頼受付期間内であれば既存問い合わせを再利用する。
15. 対応再開依頼受付期間終了後は、新しい問い合わせとして扱う。

## 27. SQLテストとの対応

データベース設計に基づき、主要な業務フローについてSQLテストを実施する。

### 27-1. 問い合わせ登録

`02_test_01_問い合わせを登録.sql`

問い合わせを登録し、受付時処理等の初期値を確認する。

### 27-2. 問い合わせを引き受ける

`03_test_02_問い合わせを引き受ける.sql`

対応担当者が問い合わせを引き受けた際に、

- 対応担当者
- 引き受け日時

が設定され、問い合わせ全体が「対応中」と判定できることを確認する。

### 27-3. 問い合わせを仮グループ化する

`04_test_03_問い合わせを仮グループ化.sql`

問い合わせと問題を関連付け、問い合わせ問題を作成する。

その際、

```text
問い合わせ問題状態 = 1（調査中）
```

として管理する。

### 27-4. リアクションを要求する

`05_test_04_リアクションを要求する.sql`

リアクションを要求した際に、

```text
問い合わせ問題状態 = 2（リアクション待ち）
調査を終えた日時 = NULL
リアクション要求最新日時 = 現在日時
```

となることを確認する。

### 27-5. 問い合わせ者がOKする

`06_test_05_問い合わせ者がOKする.sql`

問い合わせ者がOKした際に、

```text
問い合わせ問題状態 = 3（調査無事終了）
調査を終えた日時 = 現在日時
```

となることを確認する。

この処理では、問い合わせ全体の「対応完了日時」は更新しない。

### 27-6. 問い合わせを対応完了する

`07_test_06_問い合わせを対応完了する.sql`

対応担当者が問い合わせ全体を対応完了とした際に、

```text
問い合わせ.対応完了日時 = 現在日時
```

となることを確認する。

対応完了日時には、問題の調査を終えた日時や問い合わせ者がOKした日時をコピーしない。

### 27-7. 未解決で再調査する

`08_test_07_未解決で再調査する.sql`

問い合わせ者からNGのリアクションを受けた際に、

```text
問い合わせ問題状態 = 1（調査中）
最新NG日時 = 現在日時
```

となることを確認する。

このとき、

```text
調査開始日時
調査を終えた日時
リアクション要求最新日時
```

について、誤って更新されないことも確認する。

その後、再調査を行い、再度リアクションを要求した場合は、

```text
問い合わせ問題状態 = 2（リアクション待ち）
リアクション要求最新日時 = 現在日時
```

となることを確認する。
