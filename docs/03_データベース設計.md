# 20261007午後_03_データベース設計

## 1. データベース設計の目的

本システムでは、問い合わせを単なる一件の記録として管理するのではなく、

- 誰から問い合わせを受けたのか
- どのような問い合わせだったのか
- 受付時にどのような処理を行ったのか
- 誰が対応しているのか
- 問い合わせに関連する問題は何か
- 問題ごとの調査・解決確認がどこまで進んでいるか
- 対応担当者が変更されたか
- 問い合わせ全体がいつ完了したか

を追跡できる構造とする。

特に、本システムでは、

**「問い合わせ全体の対応状況」と「個々の問題の調査・解決状況」を分離する。**

---

# 2. テーブル一覧

# 3. テーブル間の関係

```text
職員
  │
  │ 1 : N
  ▼
問い合わせ
  │
  ├──────────────┐
  │              │
  │ 1 : N        │ 1 : N
  ▼              ▼
問い合わせ問題   対応担当者変更履歴
  ▲
  │ N : 1
  │
問題
```

`問い合わせ` と `問題` は多対多の関係になる。

そのため、中間テーブルとして `問い合わせ問題` を設ける。

# 6. 問い合わせ全体の状態判定

問い合わせ全体の状態は、`引き受け日時` と `対応完了日時` から判断する。

| 引き受け日時 | 対応完了日時 | 状態 |
|---|---|---|
| NULL | NULL | 引き受け待ち |
| あり | NULL | 対応中 |
| あり | あり | 対応完了 |

通常の要調査案件ではこの3パターンを使用する。

ただし、即時解決・他所属へ案内の場合は、受付時点で対応完了となるため、

```text
引き受け日時 = NULL
対応完了日時 = 登録日時
```

となる。

したがって、実装上は、

```text
対応完了日時 IS NOT NULL
    → 対応完了
```

を最優先で判定する。

それ以外で、

```text
引き受け日時 IS NOT NULL
    → 対応中
```

とする。

それ以外は、

```text
引き受け待ち
```

となる。

# 7. 受付時の処理

`受付時の処理` は以下とする。

| 値 | 処理 |
|---:|---|
| 1 | 即時解決 |
| 2 | 要調査 |
| 3 | 他所属へ案内 |

## 即時解決

```text
受付時の処理 = 1
引き受け日時 = NULL
対応完了日時 = 登録日時
```

問題を登録する必要はない。

## 要調査

```text
受付時の処理 = 2
引き受け日時 = NULL
対応完了日時 = NULL
```

として、対応担当者の引き受けを待つ。

## 他所属へ案内

```text
受付時の処理 = 3
引き受け日時 = NULL
対応完了日時 = 登録日時
```

問題を登録する必要はない。

---

# 8. 対応担当者が引き受けた場合

対応担当者が問い合わせを引き受けた時点で、

```text
引き受け日時 = 現在日時
```

とする。

この時点で問い合わせ全体は「対応中」となる。

まだ `問い合わせ問題` が存在しなくてもよい。

# 10. 問い合わせ問題テーブル

## 10-1. 役割

`問い合わせ` と `問題` の関連を管理するとともに、その問い合わせにおける問題ごとの調査・解決状況を管理する。

## 10-2. カラム定義

| # | カラム名 | データ型 | NULL | 制約・初期値 | 内容 |
|---:|---|---|---|---|---|
| 1 | 問題番号 | INTEGER | 不可 | FK → 問題.問題番号 | 関連する問題 |
| 2 | 問い合わせ番号 | INTEGER | 不可 | FK → 問い合わせ.問い合わせ番号 | 関連する問い合わせ |
| 3 | 現在の調査状況 | VARCHAR(1000) | 不可 | - | 現在の調査状況 |
| 4 | 内部メモ | VARCHAR(1000) | 可 | - | 内部向けメモ |
| 5 | 予定解決日時 | TIMESTAMP | 可 | - | 解決予定日時 |
| 6 | 次回進捗更新予定日時 | TIMESTAMP | 可 | - | 次回進捗更新予定日時 |
| 7 | 調査開始日時 | TIMESTAMP | 不可 | 初回はDEFAULT CURRENT_TIMESTAMP | 現在の調査サイクルの開始日時 |
| 8 | 調査を終えた日時 | TIMESTAMP | 可 | - | 現在の調査サイクルの終了日時 |
| 9 | 問題解決確認日時 | TIMESTAMP | 可 | - | 問い合わせ者が問題解決を確認した日時 |
| 10 | 未解決リアクション日時 | TIMESTAMP | 可 | - | 問い合わせ者から未解決との反応を受けた日時 |

主キー：

```text
PRIMARY KEY (問題番号, 問い合わせ番号)
```

# 11. 問題単位の状態

問題単位の状態は状態カラムを持たず、以下の日時から判断する。

- 調査を終えた日時
- 未解決リアクション日時
- 問題解決確認日時

| 調査終了 | 未解決リアクション | 解決確認 | 状態 |
|---|---|---|---|
| NULL | NULL | NULL | 調査中・調査が必要 |
| あり | NULL | NULL | 調査終了・問い合わせ者確認待ち |
| あり | NULL | あり | 問題解決確認済み |
| NULL | あり | NULL | 未解決リアクション後、再調査が必要 |
| あり | あり | NULL | 再調査終了・再度確認待ち |
| あり | あり | あり | 問題解決確認済み |

最優先の判定ルールは、

```text
調査を終えた日時 IS NULL
    → 現在は調査中・再調査が必要
```

とする。

---

# 12. 未解決リアクション

問い合わせ者から未解決との反応を受けた場合、

```text
未解決リアクション日時 = 現在日時
調査を終えた日時 = NULL
```

とする。

その後、再調査を行う。

再調査終了時には、

```text
調査を終えた日時
```

を再設定する。

---

# 13. 問い合わせ完了の条件

要調査の問い合わせについて、必要な問題がすべて解決確認済みとなった場合、問い合わせ全体を完了する。

その時点で、

```text
対応完了日時
```

を設定する。

対応完了日時は、最後に必要な問題について設定された `問題解決確認日時` とする。

したがって、

```text
問題解決確認日時
        ↓
対応完了日時
```

という関係になる。

---

# 14. 問い合わせと問題の状態の役割分担

## 問い合わせ

```text
引き受け待ち
対応中
対応完了
```

判定に使用するもの：

```text
引き受け日時
対応完了日時
```

## 問題

```text
調査中
調査終了・確認待ち
問題解決確認済み
再調査が必要
```

判定に使用するもの：

```text
調査を終えた日時
未解決リアクション日時
問題解決確認日時
```

この二層構造によって、

```text
問い合わせ：対応中
問題：なし
```

や、

```text
問い合わせ：対応中

問題A：解決確認済み
問題B：調査中
```

といった状態を表現できる。

# 16. スナップショット情報

過去の問い合わせ時点の情報を保持するため、

- 問い合わせ当時の所属
- 受付担当者
- 対応担当者

は問い合わせ側に保存する。

特に `問い合わせ当時の所属` は、職員の現在の所属が変更されても過去の記録を変化させないために必要である。

# 17. NULLの考え方

NULLは「まだ値が存在しない」状態を表す。

例えば、

- 対応担当者が未設定
- 引き受け日時が未発生
- 対応完了日時が未発生
- 調査終了日時が未設定
- 問題解決確認が未実施

などはNULLとする。

一方、登録時点で必須となる情報はNOT NULLとする。

# 20. CHECK制約

受付時の処理：

```text
受付時の処理 BETWEEN 1 AND 3
```

問い合わせ状態カラムは存在しないため、状態値に対するCHECK制約は設けない。

問い合わせの完了については、

```text
対応完了日時 IS NOT NULL
```

で完了状態を判断する。

即時解決・他所属へ案内の場合は、

```text
対応完了日時 = 登録日時
```

とする。

# 21. 時系列に関する基本ルール

通常の要調査案件では、

```text
受信日時
 ↓
登録日時
 ↓
引き受け日時
 ↓
調査開始日時
 ↓
調査を終えた日時
 ↓
問題解決確認日時
 ↓
対応完了日時
```

という流れになる。

未解決リアクションが発生した場合は、

```text
調査終了
 ↓
未解決リアクション
 ↓
再調査開始
 ↓
再調査終了
 ↓
問題解決確認
```

となる。

即時解決・他所属へ案内の場合は、

```text
受信
 ↓
登録
 ↓
対応完了
```

となる。

# 23. 完了後の新しい問い合わせ

対応完了となった問い合わせを再開するのではなく、後日新しい問い合わせが発生した場合は、新しい問い合わせ番号で登録する。

これにより、問い合わせごとのライフサイクルを保持する。

# 25. DB設計上の基本方針

1. 問い合わせと問題を別のエンティティとして扱う
2. 問い合わせと問題の多対多関係を `問い合わせ問題` で管理する
3. 問い合わせ全体の対応状態と問題単位の調査状態を分離する
4. 状態を別カラムとして重複保存せず、日時情報から判断できる状態は日時から導出する
5. 問題解決確認日時と問い合わせ対応完了日時を分離する
6. 対応担当者が引き受けた時点で問い合わせ全体を対応中とする
7. 問題がまだ設定されていない状態でも、問い合わせ全体を対応中として扱えるようにする
8. 完了した問い合わせを再利用せず、新しい問い合わせとして登録する
9. 過去の問い合わせ時点の情報はスナップショットとして保持する
10. DB制約とAPI・サービス層の業務ロジックを適切に分担する
11. 現時点で不要な履歴テーブルや状態フラグを増やさない

# 27. DB実装前の確認

この設計をもとにPostgreSQLへ実際のテーブルを作成する。

実装時には、

- CREATE TABLE
- PRIMARY KEY
- FOREIGN KEY
- NOT NULL
- DEFAULT
- CHECK
- IDENTITY
- TIMESTAMP

などを設定する。

その後、

- 問い合わせの正常登録

検証で問題が発見された場合は、設計を修正し、その変更をGitのコミット履歴として残す。
