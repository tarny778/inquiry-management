# データベース設計（現行版）

## 1. 方針

DBMSはPostgreSQLとする。問い合わせ、調査、両者の関係、職員、職員認証情報、ログインセッションの6テーブルで現行機能を構成する。問い合わせ状態は日時から導出し、調査状態と問い合わせ調査状態はコードで保持する。

すべての日時列は実際の時点を表すため `TIMESTAMPTZ` とする。PostgreSQLは時点を保存し、表示時のタイムゾーンは接続設定に従う。業務画面は日本時間で表示する。

## 2. テーブル一覧と関係

| テーブル | 主な役割 |
|---|---|
| 職員 | 職員番号、氏名、所属 |
| 職員認証情報 | パスワードハッシュ、ログイン可否 |
| ログインセッション | セッションIDのハッシュ、有効期限、失効情報 |
| 問い合わせ | 受付内容、担当者、受付・対応日時 |
| 調査 | 共通の原因・仮説、対応案、状態、移行先 |
| 問い合わせ調査 | 問い合わせと調査の関連、個別状態と回答履歴 |

職員は認証情報と1対0/1で結び付き、認証情報は複数のログインセッションを持てる。問い合わせは問い合わせ調査を介して複数の調査に結び付き、調査も複数の問い合わせを共有する。NG移行先は調査を参照する。

## 3. `職員`

| 列 | 型 | NULL | 制約・意味 |
|---|---|---:|---|
| 職員番号 | VARCHAR(20) | 不可 | 主キー |
| 氏名 | VARCHAR(30) | 不可 | 表示名 |
| 所属 | VARCHAR(30) | 不可 | 情報システム課か否かの権限判定にも使用 |

## 4. `職員認証情報`

| 列 | 型 | NULL | 制約・意味 |
|---|---|---:|---|
| 職員番号 | VARCHAR(20) | 不可 | 主キー、職員へのFK、削除時CASCADE |
| パスワードハッシュ | TEXT | 不可 | Argon2ハッシュ |
| ログイン可否 | BOOLEAN | 不可 | DEFAULT TRUE |
| 作成日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |
| 更新日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |
| パスワード更新日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |

平文パスワードは保存しない。ログイン可否がFALSEの職員は認証できない。

## 5. `ログインセッション`

| 列 | 型 | NULL | 制約・意味 |
|---|---|---:|---|
| セッションIDハッシュ | VARCHAR(64) | 不可 | 主キー。Cookieに渡したIDのSHA-256 |
| 職員番号 | VARCHAR(20) | 不可 | 職員認証情報へのFK、削除時CASCADE |
| 作成日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |
| 無操作期限 | TIMESTAMPTZ | 不可 | アイドル有効期限 |
| 絶対有効期限 | TIMESTAMPTZ | 不可 | ログインからの最大期限 |
| 最終利用日時 | TIMESTAMPTZ | 可 | 最終認証済み利用 |
| 失効日時 | TIMESTAMPTZ | 可 | NULLなら失効していない |

CHECK制約で無操作期限が絶対有効期限を超えないことを保証する。職員番号に索引を設定する。

## 6. `問い合わせ`

| 列 | 型 | NULL | 制約・意味 |
|---|---|---:|---|
| 問い合わせ番号 | INTEGER IDENTITY | 不可 | 主キー |
| 問い合わせ職員番号 | VARCHAR(20) | 可 | 職員へのFK、削除時SET NULL |
| 問い合わせ当時の所属 | VARCHAR(30) | 不可 | 受付時スナップショット |
| 受付経路 | VARCHAR(20) | 不可 | 電話・メール・フォーム |
| 問い合わせ分類 | VARCHAR(30) | 不可 | 現行アプリでは分類A/B/C |
| 件名 | VARCHAR(100) | 不可 | 問い合わせ件名 |
| 緊急度 | INTEGER | 不可 | CHECK 1, 2, 3 |
| 受付時の処理 | INTEGER | 不可 | CHECK 1, 2, 3 |
| 問い合わせ詳細 | VARCHAR(1000) | 可 | 本文 |
| 受付担当者 | VARCHAR(20) | 可 | 職員へのFK、削除時SET NULL |
| 対応担当者 | VARCHAR(20) | 可 | 職員へのFK、削除時SET NULL |
| 受信日時 | TIMESTAMPTZ | 不可 | 受信時刻 |
| 登録日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |
| 引き受け日時 | TIMESTAMPTZ | 可 | NULLなら未引き受け |
| 対応完了日時 | TIMESTAMPTZ | 可 | NULLなら未完了 |

問い合わせ状態列は持たない。状態は引き受け日時・対応完了日時から導出する。

## 7. `調査`

| 列 | 型 | NULL | 制約・意味 |
|---|---|---:|---|
| 調査番号 | INTEGER IDENTITY | 不可 | 主キー |
| 調査の名称 | VARCHAR(30) | 不可 | 必須名称 |
| 原因・仮説 | VARCHAR(1000) | 可 | 調査内容 |
| 情シス側での対応 | VARCHAR(1000) | 可 | 対応案 |
| 問い合わせ者側で必要な対応 | VARCHAR(1000) | 可 | 依頼者側の対応 |
| 調査状態 | INTEGER | 不可 | DEFAULT 1、CHECK 1〜3 |
| 調査開始日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |
| 対応案策定予定日時 | TIMESTAMPTZ | 可 | 予定 |
| 進捗更新の次回更新予定日時 | TIMESTAMPTZ | 可 | 予定 |
| リアクション要求日時 | TIMESTAMPTZ | 可 | 問い合わせ者への要求日時 |
| 調査断念日時 | TIMESTAMPTZ | 可 | 断念日時 |
| 最新移行先の調査番号 | INTEGER | 可 | 調査への自己参照FK |

## 8. `問い合わせ調査`

| 列 | 型 | NULL | 制約・意味 |
|---|---|---:|---|
| 問い合わせ調査番号 | INTEGER IDENTITY | 不可 | 主キー |
| 調査番号 | INTEGER | 不可 | 調査へのFK |
| 問い合わせ番号 | INTEGER | 不可 | 問い合わせへのFK |
| 問い合わせ調査状態 | INTEGER | 不可 | DEFAULT 1、CHECK 1〜5 |
| 調査開始日時 | TIMESTAMPTZ | 不可 | DEFAULT CURRENT_TIMESTAMP |
| 断念日時 | TIMESTAMPTZ | 可 | 個別断念日時 |
| リアクション被要求日時 | TIMESTAMPTZ | 可 | 回答依頼日時 |
| リアクション日時 | TIMESTAMPTZ | 可 | 回答日時 |
| リアクション内容 | INTEGER | 可 | CHECK 1または2 |
| NGでの移行先調査番号 | INTEGER | 可 | 調査へのFK |

UNIQUE（問い合わせ番号、調査番号）で同じ組み合わせの重複を防ぐ。CHECKでNG移行先が元調査と同一にならないようにする。

## 9. 状態値と日時の意味

### 調査状態

| 値 | 意味 |
|---:|---|
| 1 | 調査中 |
| 2 | リアクション要求済み |
| 3 | 断念 |

### 問い合わせ調査状態

| 値 | 意味 | 主な日時・項目 |
|---:|---|---|
| 1 | 調査中 | 調査開始日時 |
| 2 | 断念 | 断念日時 |
| 3 | リアクション待ち | リアクション被要求日時 |
| 4 | OK | リアクション内容1、リアクション日時 |
| 5 | NG | リアクション内容2、リアクション日時、移行先番号 |

DDLでは状態コード範囲等を検査する。状態と各日時・リアクション項目の全組み合わせの整合性、操作者の権限、現在状態からの遷移はAPIで検証する。

## 10. 整合性制約とアプリケーション制御

DBは主キー、外部キー、NOT NULL、コード値CHECK、ログイン期限CHECK、問い合わせと調査の組み合わせUNIQUEを担う。受付経路・分類の選択肢、状態遷移、担当者本人確認、調査の受入可能状態、一括処理全件検証、NG移行先の再利用・作成などはAPIで検証する。

CHECK・UNIQUE追加前には既存データの整合性を確認する。外部キーの検索性能に関わる索引は、データ量・実行計画を基に別途評価する。

## 11. データ保持と将来構想

現行機能に論理削除・担当者変更履歴テーブルは含めない。対応担当者変更履歴および論理削除は必要に応じて将来検討する。メール通知、問い合わせ取り込み、CSV出力、FAQ整理支援も現行スキーマの対象外であり、採用時に個別設計する。
