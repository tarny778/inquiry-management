# 04. 画面設計書

## 1. 目的

本書では、問い合わせ管理Webアプリの画面構成、表示・入力項目、操作、権限および画面間の遷移を定義する。

細かなレイアウトや表示方法は、実装時に調整する。初期実装に必要な業務ルールと操作を優先し、過度に細部を作り込まない。

## 2. 画面一覧

| 画面ID | 画面名 | 主な目的 |
|---|---|---|
| 101 | 問い合わせ詳細 | 問い合わせの確認・登録・編集 |
| 102 | 問い合わせ一覧・検索 | 問い合わせの検索・一覧表示・一括操作 |
| 103 | 対応担当者変更履歴 | 対応担当者の変更履歴の確認 |
| 201 | 調査詳細 | 調査と関連する問い合わせごとの調査状況の確認・操作 |
| 202 | 調査一覧・検索 | 調査の検索・一覧表示 |
| 401 | ログイン | 利用者の認証 |

画面301「問い合わせ調査詳細」と画面302「問い合わせ調査一覧・検索」は独立画面として設けず、問い合わせ調査の確認・操作を画面201に統合する。

## 3. 共通ルール

### 3.1 利用者区分

- 一般職員：自分の問い合わせを中心に確認し、リアクション回答などを行う。
- 情シス職員：問い合わせの受付・対応、調査および関連する業務操作を行う。

### 3.2 権限確認

- 表示するデータと操作可能な機能は、ログイン利用者の区分および担当状況に応じて制御する。
- ボタンの表示制御だけでなく、API側でも操作権限を検証する。
- 操作時点で状態や担当者が変更されている場合は、API側で実行可否を再確認する。

### 3.3 状態表示

- 問い合わせの状態は、引き受け日時と対応完了日時から判定する。
  - 引き受け待ち：引き受け日時がNULL、対応完了日時がNULL
  - 対応中：引き受け日時がNULLでなく、対応完了日時がNULL
  - 対応完了：対応完了日時がNULLでない
- 調査と問い合わせ調査の状態は、それぞれの状態カラムを正とする。
- 画面には、原則として状態コードではなく状態名を表示する。

## 4. 画面101：問い合わせ詳細

### 4.1 目的

問い合わせ1件の詳細確認、登録、編集などを行う。

### 4.2 主な表示・入力項目

| 項目 | 表示・入力方針 |
|---|---|
| 問い合わせ番号 | 登録後に表示 |
| 問い合わせ者 | 職員情報から表示 |
| 問い合わせ当時の所属 | 表示・登録 |
| 受付経路 | 選択・表示 |
| 問い合わせ分類 | 選択・表示 |
| 件名 | 入力・表示 |
| 緊急度 | 選択・表示 |
| 受付時の処理 | 選択・表示 |
| 問い合わせ詳細 | 入力・表示 |
| 受付担当者 | 登録時に自動設定・表示 |
| 対応担当者 | 表示 |
| 受信日時 | 入力・表示 |
| 登録日時 | 自動設定・表示 |
| 引き受け日時 | 引き受け時に設定・表示 |
| 対応完了日時 | 対応完了時に設定・表示 |

### 4.3 主な操作

| 操作 | 実行条件・仕様 |
|---|---|
| 新規登録 | 情シス職員が実行できる。登録者を受付担当者として設定する |
| 編集 | 引き受け待ちの場合は受付担当者、対応中の場合は現在の対応担当者が実行できる |
| 引き受け | 引き受け待ちの問い合わせを引き受ける。詳細な一括操作との関係は画面102で定義する |
| 対応完了 | 対応中の問い合わせについて、現在の対応担当者が実行できる |
| 担当者変更履歴の確認 | 画面103へ移動する |

### 4.4 業務ルール

- 問い合わせの対応完了は、対応担当者が明示的に実行する。
- 関連する問い合わせ調査がすべて終了しても、問い合わせを自動的に対応完了とはしない。
- 即時解決や他部署への引き継ぎなど、受付時点で対応完了とする場合は、登録時に対応完了日時を設定する。
- 対応再開や論理削除など、初期実装で必要性の低い機能は後回しとする。

## 5. 画面102：問い合わせ一覧・検索

### 5.1 目的

問い合わせを条件検索し、一覧から詳細確認や一括操作を行う。

### 5.2 初期検索条件

| 利用者区分 | 初期表示の対象 |
|---|---|
| 一般職員 | 自分の問い合わせのうち、引き受け待ち・対応中のもの |
| 情シス職員 | すべての引き受け待ち問い合わせと、自分が現在の対応担当者である対応中問い合わせ |

利用者は検索条件を変更して再検索できる。

### 5.3 主な検索条件

- 問い合わせ番号・・・表示
- 問い合わせ者
- 問い合わせ当時の所属
- 受付経路
- 問い合わせ分類・・・表示
- 件名・・・表示
- 緊急度（情シス職員のみ）・・・表示
- 受付担当者
- 対応担当者・・・表示
- 問い合わせ状態・・・表示
- 受信日時

初期実装で必要な条件を優先し、細かな配置や選択肢は実装時に調整する。

### 5.4 検索条件の動作

- 同じ項目で複数の選択肢を指定した場合はOR条件とする。
- 異なる項目間はAND条件とする。
- 文字列検索は部分一致とする。
- 検索条件のクリア時は、利用者区分に応じた初期検索条件へ戻す。
- 検索を実行したときは、選択中の問い合わせをすべて解除する。

### 5.5 一覧表示

- 1ページあたり50件を表示する。
- 問い合わせ番号を表示し、詳細画面へのリンクを設ける。
- 問い合わせ状態は状態名で表示する。
- 一覧の行をチェックボックスで選択できるようにする。
- ページを移動しても選択状態を維持する。
- 一般職員には緊急度を表示しない。
- 初期並び順は受信日時とする。
- 列見出しから並べ替えができるようにする。
- 選択件数と、現在のページの全選択・選択解除を画面上部に表示する。

### 5.6 一括操作

一括操作は情シス職員のみ利用できる。

| 操作 | 実行条件・仕様 |
|---|---|
| 引き受け | 引き受け待ち＝対応担当者未設定の問い合わせが対象。情シス職員が対象 |
| 対応完了 | 対応中で、実行者が現在の対応担当者であり、状態1「調査中」または状態3「リアクション待ち」の関連レコードが存在しない問い合わせが対象 |
| 調査への関連付け | 対応中で、実行者が現在の対応担当者である問い合わせが対象 |

- 条件を満たさない問い合わせが選択されている場合は、実行前に対象を確認する。
- 一部の対象だけを処理する部分実行は行わず、条件を満たさない場合は一括処理全体を実行しない。
- 実行できない場合は理由を表示する。
- 対応再開などは初期実装では対象外とする。

### 5.7 調査への関連付けポップアップ

「調査への関連付け」操作時に、小さなポップアップを表示する。

#### 新規に調査を作成する場合

- 「調査の名称」を入力する。
- 当該項目は必須とする。
- 「新規に調査を作成し関連付ける」ボタンを設ける。
- 調査レコードと問い合わせ調査レコードを同時に作成する。

#### 既存の調査に関連付ける場合

- 状態が「調査中」の調査を選択するプルダウンを設ける。
- 選択肢には「調査の名称」を表示する。
- 「既存の調査に関連付ける」ボタンを設ける。
- 選択した調査に対して、問い合わせ調査レコードを作成する。

#### 共通ルール

- 「キャンセル」ボタンでポップアップを閉じる。キャンセル時は登録しない。
- 対象の問い合わせが対応中で、実行者が現在の対応担当者であることを確認する。
- 調査と問い合わせ調査の登録は、同一トランザクションで実行する。
- 同じ問い合わせを同じ調査に二重に関連付けない。
- 既存の調査が選択できない状態になっていないか、登録時に再確認する。

## 6. 画面201：調査詳細

### 6.1 目的

調査1件の内容と、関連する問い合わせごとの調査状況を確認し、それぞれに必要な業務操作を行う。

画面上部に調査全体の情報を表示し、画面下部に関連する問い合わせ調査を一覧表示する。

### 6.2 画面構成

- 上部：調査の詳細情報と、調査全体に対する操作
- 下部：関連する問い合わせ調査の一覧と、問い合わせごとの操作

調査全体が終了した後も、下部の一覧は表示し続ける。これにより、リアクション要求後の回答操作や回答内容の確認を同じ画面で行えるようにする。

### 6.3 調査全体の表示・入力項目

| 項目 | 表示・入力方針 |
|---|---|
| 調査番号 | 登録後に表示 |
| 調査の名称 | 入力・表示 |
| 原因・仮説 | 入力・表示 |
| 情シス側での対応 | 入力・表示 |
| 問い合わせ者側で必要な対応 | 入力・表示 |
| 調査状態 | 状態名を表示 |
| 調査開始日時 | 自動設定・表示 |
| 対応案策定予定日時 | 入力・表示 |
| 進捗更新の次回更新予定日時 | 入力・表示 |
| リアクション要求日時 | リアクション要求時に登録・表示 |
| 調査断念日時 | 調査断念時に登録・表示 |
| 最新移行先の調査番号 | 登録されている場合に表示 |

### 6.4 調査全体の操作

| 操作 | 実行条件・仕様 |
|---|---|
| 編集 | 調査状態が「調査中」の場合に実行できる |
| リアクション要求 | 調査状態が「調査中」の場合に実行できる |
| 調査断念 | 調査状態が「調査中」の場合に実行できる |

調査の新規作成は、画面102の関連付け操作を通じて行う。画面201は、登録済みの調査を確認・操作する画面とする。

### 6.5 関連する問い合わせ調査の一覧

調査に関連付けられた問い合わせ調査を、画面下部に一覧表示する。

表示項目の詳細は実装時に調整するが、問い合わせ番号、問い合わせ者、問い合わせ調査状態、リアクション日時・内容など、個々の進捗と回答を確認できるようにする。

- 問い合わせ番号から対象の問い合わせを確認できるようにする。
- 問い合わせ調査の状態は状態名で表示する。
- 断念日時、リアクション被要求日時、リアクション日時、リアクション内容、NGでの移行先調査番号などは、必要に応じて確認できるようにする。
- 一覧に表示しきれない情報は、対象行の選択などによりポップアップ等で確認できるようにする。
- 表示項目やポップアップの細かな仕様は後回しとする。

### 6.6 問い合わせ調査に対する操作

| 操作 | 実行条件・仕様 |
|---|---|
| 問い合わせの確認 | 問い合わせ番号から対象の問い合わせを確認できる |
| 問い合わせ単位の調査断念 | 問い合わせ調査状態が「調査中」で、実行者が当該問い合わせの現在の対応担当者である場合に実行できる |
| リアクション回答 | 問い合わせ調査状態が「リアクション待ち」で、実行者が当該問い合わせの問い合わせ者である場合に実行できる |

各操作は対象の問い合わせ調査レコード単位で実行する。

### 6.7 業務ルール

#### 調査全体

- 調査状態カラムを状態の正とする。
  - 1：調査中
  - 2：リアクション要求済み
  - 3：調査断念
- 調査中の場合のみ、調査の内容編集、リアクション要求、調査断念が可能。
- リアクション要求時は、調査状態を2に変更し、リアクション要求日時を設定する。
- 調査断念時は、調査状態を3に変更し、調査断念日時を設定する。
- 状態2・3は、調査全体の終了状態とする。
- 終了した調査は編集・再利用しない。

#### 問い合わせ調査

- 問い合わせ調査状態カラムを状態の正とする。
  - 1：調査中
  - 2：断念
  - 3：リアクション待ち
  - 4：OKで完了
  - 5：NGで移行先へ
- 調査中の場合のみ、問い合わせ単位の調査断念が可能。
- 断念時は断念日時を登録し、状態を2に変更する。
- リアクション待ちの場合のみ、リアクション回答が可能。
- リアクション回答時はリアクション内容とリアクション日時を登録し、状態を4または5に変更する。
- 状態2・4・5は、問い合わせ調査自体の終了状態とする。
- 終了した問い合わせ調査は再利用しない。NGの場合は移行先の調査に新しい問い合わせ調査を作成する。

#### 共通ルール

- 調査全体の状態と、個々の問い合わせ調査の状態は独立して管理する。
- 調査全体の終了によって、関連する問い合わせ調査の状態を自動変更しない。
- 問い合わせ調査が終了しても、関連付けられた問い合わせを自動的に対応完了とはしない。
- 調査が終了した後も、下部一覧で関連する問い合わせ調査の状態やリアクション内容を確認できるようにする。

## 7. 画面202：調査一覧・検索

### 7.1 目的

調査を条件検索し、一覧から対象を選択して画面201「調査詳細」へ移動する。

### 7.2 初期検索条件

| 利用者区分 | 初期表示の対象 |
|---|---|
| 一般職員 | 自分の問い合わせに関連付けられた調査のうち、問い合わせが対応中のもの |
| 情シス職員 | 自分が現在の対応担当者である問い合わせに関連付けられた調査のうち、問い合わせが対応中のもの |

利用者は検索条件を変更して再検索できる。

### 7.3 検索条件

初期実装では、次の項目を中心に検索できるようにする。

- 調査番号
- 関連付けられた問い合わせ番号
- 問い合わせ者
- 対応担当者
- 問い合わせ状態
- 調査状態
- 調査の名称

検索条件の詳細な配置や選択肢は実装時に調整する。

### 7.4 検索条件の動作

- 同じ項目で複数の選択肢を指定した場合はOR条件とする。
- 異なる項目間はAND条件とする。
- 文字列検索は部分一致とする。
- 検索条件のクリア時は、利用者区分に応じた初期検索条件へ戻す。
- 検索を実行したときは、一覧の表示を更新する。

### 7.5 一覧表示

- 1ページあたり20件を表示する。
- 調査番号を表示し、詳細画面へのリンクを設ける。
- 調査状態は状態名で表示する。
- 調査開始日時を初期並び順とする。
- 列見出しから並べ替えができるようにする。
- 対応案策定予定日時および進捗更新の次回更新予定日時を表示し、問い合わせ者が進捗を把握できるようにする。
- 一覧の行選択用チェックボックスは設けない。
- 調査1件に複数の問い合わせが関連付いている場合、条件を満たす関連問い合わせが1件でもあれば調査を表示する。同じ調査を重複表示しない。

### 7.6 操作

- 調査番号または詳細リンクから、画面201「調査詳細」へ移動する。
- 一括操作は設けない。

## 8. 画面103：対応担当者変更履歴

### 8.1 目的

問い合わせに関する対応担当者の変更履歴を確認する。

### 8.2 表示項目

- 問い合わせ番号
- 変更前の対応担当者
- 変更後の対応担当者
- 変更日時
- 変更理由（DB設計で管理する場合）

### 8.3 操作

- 対象の問い合わせから履歴を参照できるようにする。
- 初期実装では履歴の参照を中心とし、履歴自体の編集・削除は行わない。

※詳細な表示項目は、対応担当者変更履歴テーブルの設計に合わせて調整する。

## 9. 画面401：ログイン

### 9.1 目的

利用者を認証し、利用者区分と権限に応じた画面を表示する。

### 9.2 主な入力項目

- ログインID
- パスワード

### 9.3 操作

- ログイン
- 認証失敗時のエラーメッセージ表示

※認証方式や職員情報との連携方法は、実装時に決定する。

## 10. 初期実装での方針

- 主要な業務フローを実現することを優先する。
- 細かなレイアウトやポップアップの表示方法は実装時に調整する。
- 論理削除、対応再開など、初期実装で必要性の低い機能は後回しとする。
- 状態遷移、権限確認、二重登録防止、トランザクション管理など、業務上重要なルールはAPI側で実装・検証する。
- 画面設計で細部を決めきることに時間をかけすぎず、API設計・実装・テストへ進む。
