# 04_画面設計書

## 1. 本書の目的

本書では、問い合わせ管理Webアプリケーションの画面構成、表示項目、操作、操作権限を定義する。

本書は初期実装に必要な仕様を定めることを目的とする。細かな例外処理や使用頻度の低い機能は、必要に応じて後続の改修で対応する。

|---|---|---|
| 101 | 問い合わせ詳細 | 問い合わせの登録・確認・編集、個別操作 |
| 102 | 問い合わせ一覧・検索 | 問い合わせの検索・一覧表示、一括操作 |
| 103 | 対応担当者変更履歴 | 対応担当者の変更履歴の確認 |

| 202 | 問い合わせ問題調査一覧・検索 | 問い合わせ問題調査の検索・一覧表示 |

## 3. 共通仕様

### 3.1 利用者区分

| 利用者区分 | 基本的な役割 |
|---|---|
| 一般職員 | 自分の問い合わせの登録・確認、対応結果の確認 |
| 情シス職員 | 問い合わせの受付・対応、問題調査、職員情報の管理 |

操作権限に応じて、ボタンの表示・非表示や活性・非活性を切り替える。

画面上で操作を制限するだけでなく、API側でも利用者の権限と操作条件を検証する。

### 3.2 共通の表示・操作方針

- 一覧から詳細画面へ移動できるようにする。
- 登録日時や操作日時など、システムで管理する日時は原則として自動設定する。
- 状態は数値コードそのものではなく、利用者に分かる名称で表示する。
- 入力エラーや操作条件を満たさない場合は、理由を利用者に表示する。
- データの整合性を保つため、重要な業務ルールはバックエンド側で検証する。

## 4. 画面101：問い合わせ詳細

### 4.1 目的

問い合わせ1件の内容を確認し、登録・編集や個別の業務操作を行う。

### 4.2 主な表示・入力項目

| 項目 | 表示・入力方針 |
|---|---|
| 問い合わせ番号 | 登録後に表示 |
| 問い合わせ職員 | 職員情報から選択・表示 |
| 問い合わせ当時の所属 | 登録時点の所属を保存・表示 |
| 受付経路 | 選択・表示 |
| 問い合わせ分類 | 選択・表示 |
| 件名 | 入力・表示 |
| 緊急度 | 情シス職員が入力・確認 |
| 受付時の処理 | 受付時の対応内容を選択・表示 |
| 問い合わせ詳細 | 入力・表示 |
| 受付担当者 | 登録者を自動設定 |
| 対応担当者 | 担当者を表示 |
| 受信日時 | 入力・表示 |
| 登録日時 | 自動設定・表示 |
| 引き受け日時 | 引き受け時に自動設定 |
| 対応完了日時 | 対応完了時に自動設定 |

※上記は初期実装向けの項目案。必須・任意、選択肢、文字数などの詳細は既存の要件定義書・DB設計書に合わせる。

### 4.3 主な操作

| 操作 | 実行条件・仕様 |
|---|---|
| 新規登録 | 情シス職員が実行できる。登録者を受付担当者に設定する |
| 編集 | 引き受け前は受付担当者、引き受け後は現在の対応担当者が実行できる |
| 引き受け | 引き受け待ちの問い合わせを対応中にする |
| 対応完了 | 対応中の問い合わせについて、業務上の完了条件を満たす場合に実行する |
| 問い合わせ問題調査の確認 | 関連する問題調査の情報を確認できるようにする |
| 対応担当者変更履歴の確認 | 画面103へ移動する |

### 4.4 業務ルール

- 問い合わせの状態は、引き受け日時と対応完了日時から判定する。
  - 引き受け待ち：引き受け日時がNULL、対応完了日時がNULL
  - 対応中：引き受け日時がNULLではなく、対応完了日時がNULL
  - 対応完了：対応完了日時がNULLではない
- 即時解決や他部署への案内など、登録時点で対応が完了するケースでは、登録時に対応完了日時を設定する。
- 対応完了は、関連する問い合わせ問題調査がすべて終了していることを条件とする。
- 問い合わせ問題調査が終了しても、問い合わせ自体を自動的に対応完了にはしない。
- 削除、対応再開などの詳細仕様は初期実装では扱わず、必要性を確認してから設計する。

## 5. 画面102：問い合わせ一覧・検索

### 5.1 目的

問い合わせを条件検索し、一覧から対象を選択して個別画面への移動や一括操作を行う。

### 5.2 初期検索条件

| 利用者区分 | 初期表示の対象 |
|---|---|
| 一般職員 | 自分の問い合わせのうち、引き受け待ちまたは対応中のもの |
| 情シス職員 | すべての引き受け待ち、および自分が対応中のもの |

利用者は検索条件を変更して再検索できる。

### 5.3 検索条件

初期実装では、次の項目を中心に検索できるようにする。

- 問い合わせ番号
- 件名
- 問い合わせ職員
- 問い合わせ当時の所属
- 問い合わせ分類
- 受付経路
- 問い合わせ状態
- 受信日時

緊急度は情シス職員向けの検索条件とする。

検索条件の詳細な配置や、選択肢の細部は実装時に調整する。

### 5.4 検索条件の動作

- 同じ項目で複数の選択肢を指定した場合はOR条件とする。
- 異なる項目間はAND条件とする。
- 文字列検索は部分一致とする。
- 検索条件のクリア時は、利用者区分に応じた初期検索条件へ戻す。
- 検索を実行したときは、選択中の問い合わせをすべて解除する。

### 5.5 一覧表示

- 1ページあたり50件を表示する。
- 問い合わせ番号を表示し、詳細画面へのリンクを設ける。
- 問い合わせ状態は名称で表示する。
- 一覧の行をチェックボックスで選択できるようにする。
- ページを移動しても選択状態を維持する。
- 情シス職員には緊急度を表示する。一般職員には表示しない。
- 情シス職員の初期並び順は緊急度、受信日時の順とする。
- 一般職員の初期並び順は受信日時を基準とする。
- 列見出しから並べ替えができるようにする。

### 5.6 一括操作

一括操作は情シス職員向けとする。

| 操作 | 実行条件・仕様 |
|---|---|
| 一括引き受け | 引き受け待ちの問い合わせが対象 |
| 一括対応完了 | 対応中で、終了していない関連問い合わせ問題調査がなく、実行者が現在の対応担当者であること |
| 問題調査への関連付け | 対応中で、実行者が現在の対応担当者であること |
| 一括対応再開 | 将来の対応候補。再開条件を確定してから実装する |

### 5.7 一括操作の共通ルール

- 画面上部に選択件数を表示する。
- 現在のページの全件選択・選択解除をできるようにする。
- 操作対象の状態や権限が条件を満たさない場合は、実行できないようにする。
- 実行条件を満たさない理由を利用者に表示する。
- 一括処理は、対象の一部だけを更新するのではなく、全対象の検証に成功した場合にまとめて実行する。
- 引き受け時に対応担当者が未設定、または別の職員の場合は、実行者への担当変更を確認する。
- 一括処理の対象や実行結果は、バックエンド側でも検証する。

## 6. その他の画面

以下は初期実装に向けた概要であり、詳細な項目や操作は、主要画面の実装を進める中で必要な範囲を定義する。

### 6.1 画面103：対応担当者変更履歴

対象の問い合わせについて、対応担当者の変更日時、変更後の担当者、変更処理を行った職員、変更理由を確認する。

### 6.2 画面201：問い合わせ問題調査詳細

問い合わせと問題調査の関連情報、調査状態、調査の進捗を確認する。権限と状態に応じて、調査の開始、リアクション要求、OK・NG、断念などの操作を行う。

### 6.3 画面202：問い合わせ問題調査一覧・検索

問い合わせ問題調査を検索し、一覧表示する。対象を選択して画面201へ移動できるようにする。

### 6.4 画面301：問題調査詳細

問題調査の名称・仮説、原因、対応案、状態、各種日時を確認する。調査状態に応じて編集可能な項目を制御する。

### 6.5 画面302：問題調査一覧・検索

問題調査を検索し、一覧表示する。対象を選択して画面301へ移動できるようにする。

### 6.6 画面401：ログイン

利用者を認証し、認証された利用者の権限に応じて画面を利用できるようにする。

### 6.7 画面501：情シス職員マスタ

情シス職員の情報を管理する。利用できる操作は権限に応じて制限する。

## 7. 初期実装の対象範囲

### 7.1 優先して実装する機能

- ログインと利用者区分に応じた権限制御
- 問い合わせの登録・一覧・詳細表示
- 問い合わせの引き受け
- 問い合わせ問題調査の開始
- リアクション要求とOK・NGの処理
- 問い合わせおよび問題調査の主要な状態遷移

### 7.2 後続対応とする機能

- 問い合わせの削除・論理削除
- 対応再開の詳細仕様
- 使用頻度の低い例外処理
- 画面の細かな見た目の調整
- 初期実装に不可欠ではない追加機能

後続対応とした項目は、必要になった段階で要件・DB・APIとの整合性を確認して設計する。
