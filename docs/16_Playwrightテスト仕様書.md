# Playwrightテスト仕様書

- 文書状態：確定版
- 対象：問い合わせ管理Webアプリケーション
- テスト方式：PlaywrightによるE2Eテスト
- テスト対象環境：E2E専用データベース `inquiry_management_e2e`

---

## 1. 目的

本仕様書は、問い合わせ管理Webアプリケーションについて、利用者が画面を通じて業務を正しく完遂できることを確認するためのPlaywrightテストの範囲、テストケース、テストデータの管理方針を定める。

API単体テストであるpytestと役割を分担し、画面操作から業務処理の結果までを一連の流れとして検証する。

## 2. テストの基本方針

### 2.1 Playwrightとpytestの役割分担

| テスト方式 | 主な確認対象 |
|---|---|
| Playwright | 画面表示、画面遷移、入力操作、ボタンの表示・有効状態、業務操作の結果、画面への反映 |
| pytest | APIの入力検証、認証・権限チェック、状態遷移の制約、異常系、一括処理の原子性、DB更新の整合性 |

pytestで検証済みのAPI異常系を、Playwrightで一律に重複検証することはしない。

ただし、利用者が画面上で遭遇する重要なエラーや、画面上の操作制御についてはPlaywrightでも確認する。

### 2.2 テストの独立性

各テストケースは、他のテストケースの実行結果に依存しないものとする。

各テストの開始前に必要なデータを準備し、終了後に作成した業務データを削除する。

テストの実行順序を変更しても、同じ結果が得られることを基本とする。

### 2.3 テストの実行方式

当面は同一E2E DBを使用するため、Playwrightのテストは直列実行とする。

並列実行は、テストごとにDBを分離できる仕組みを整備した後に検討する。

## 3. テスト対象範囲

以下のA〜GをPlaywrightの基本テスト対象とする。

| 区分 | 対象業務 |
|---|---|
| A | 認証・画面切り替え |
| B | 問い合わせの新規登録・編集 |
| C | 問い合わせの引き受け・完了・再開 |
| D | 問い合わせの検索 |
| E | 調査の作成・関連付け・編集 |
| F | 調査・問い合わせ調査の状態遷移 |
| G | 調査の検索・詳細確認 |

### 3.1 Playwrightの対象外を基本とするもの

以下はpytestを中心に検証する。

- APIの入力値の形式・範囲の検証
- 存在しないレコード番号への操作
- 不正な状態からの状態遷移
- 他職員によるAPIへの不正な更新要求
- 一括処理における一部失敗時の全件ロールバック
- 重複した番号・関連付けの拒否
- 再開期限の境界値
- 同時実行・ロック制御
- APIのレスポンス形式の詳細な検証

画面から通常操作を行った際の結果や、画面上の操作制御はPlaywrightで確認する。

## 4. 権限制御に関する共通仕様

### 4.1 基本的な考え方

権限制御は、原則として画面またはダイアログへの遷移ボタンで行う。

遷移先の画面・ダイアログが表示された後は、実行ボタン自体に職員区分や業務権限による制限を設けない。

ただし、バックエンドAPIでは、実行時に改めて認証・権限・状態を検証する。

### 4.2 問い合わせ一覧

| 操作 | 一般職員 | 情報システム課職員 |
|---|---|---|
| 新規登録 | 非表示 | 表示・有効 |
| 一括引き受け | 非表示 | 表示・有効 |
| 一括完了 | 非表示 | 表示・有効 |
| 一括関連付け | 非表示 | 表示・有効 |

### 4.3 問い合わせ詳細

| 操作 | 一般職員 | 情報システム課職員・権限なし | 情報システム課職員・権限あり |
|---|---|---|---|
| 編集画面への遷移 | 非表示 | 表示・無効 | 表示・有効 |
| 引き受け | 非表示 | 表示・無効 | 表示・有効 |
| 対応完了 | 非表示 | 表示・無効 | 表示・有効 |
| 再開 | 非表示 | 表示・無効 | 表示・有効 |

### 4.4 関連付けダイアログ

ダイアログ内の操作ボタンは、全職員に表示・有効とする。

ダイアログへの遷移・表示は、問い合わせ一覧側の操作ボタンで制御する。

### 4.5 調査詳細

| 操作 | 一般職員 | 情報システム課職員・権限なし | 情報システム課職員・権限あり |
|---|---|---|---|
| 編集画面への遷移 | 非表示 | 表示・無効 | 表示・有効 |
| リアクション要求 | 非表示 | 表示・無効 | 表示・有効 |
| 調査全体の断念 | 非表示 | 表示・無効 | 表示・有効 |

### 4.6 調査編集画面

保存ボタンは全職員に表示・有効とする。

編集画面への遷移ボタンで権限制御を行い、保存APIではバックエンドが改めて権限を検証する。

### 4.7 問い合わせ調査の個別操作

OK回答、NG回答、個別断念のボタンは、操作する職員が権限を持ち、かつ対象の問い合わせ調査が操作可能な状態の場合に限り表示・有効とする。

それ以外の場合は非表示とする。

## 6. テストデータ管理方針

### 6.1 対象データベース

Playwrightでは、E2E専用DB `inquiry_management_e2e` のみを使用する。

開発DB `inquiry_management_dev`、本番DB `inquiry_management`、pytest用DB `inquiry_management_test` は使用しない。

DB初期化・後片付け処理では、接続先DB名が `inquiry_management_e2e` であることを必ず検証する。

### 6.2 基準状態

各テストの開始前・終了後の基準状態を以下とする。

| テーブル | 基準状態 |
|---|---|
| 職員 | 共通職員3名を保持 |
| 職員認証情報 | 共通職員の認証情報を保持 |
| ログインセッション | 0件 |
| 問い合わせ | 0件 |
| 調査 | 0件 |
| 問い合わせ調査 | 0件 |

職員・職員認証情報は共通データとして維持する。

業務データとログインセッションは各テストの前後に初期化する。

### 6.3 共通職員

| 職員番号 | 所属 | 用途 |
|---|---|---|
| J0001 | 情報システム課 | 操作担当者・権限あり |
| J0002 | 情報システム課 | 別の情シス職員・権限なしの比較対象 |
| T0001 | 総務課 | 一般職員・問い合わせ者 |

3名それぞれのログイン情報をE2E DBに登録する。

パスワードはテストコードに直接記述せず、環境変数から取得する。GitHubにはパスワードや認証情報を登録しない。

### 6.4 個別テストデータ

問い合わせ・調査・問い合わせ調査は、各テストで必要なものだけを作成する。

テストデータは、業務上の状態を明示して準備する。

| データ種別 | 代表的な状態 |
|---|---|
| 問い合わせ | 引き受け待ち |
| 問い合わせ | 対応中 |
| 問い合わせ | 対応完了 |
| 調査 | 調査中 |
| 調査 | リアクション要求済み |
| 調査 | 断念 |
| 問い合わせ調査 | 調査中 |
| 問い合わせ調査 | 断念 |
| 問い合わせ調査 | リアクション待ち |
| 問い合わせ調査 | OK |
| 問い合わせ調査 | NG |

必要な状態の組み合わせは、各テストケースの事前条件に合わせて準備する。

### 6.5 テストデータ作成の共通化

テストデータ作成処理は、業務状態ごとに共通化する。

関数の単位は以下を基本とする。

| 関数の例 | 作成するデータ |
|---|---|
| `createPendingInquiry()` | 引き受け待ち問い合わせ |
| `createInProgressInquiry()` | 対応中問い合わせ |
| `createCompletedInquiry()` | 対応完了問い合わせ |
| `createInvestigation()` | 調査 |
| `createInquiryInvestigation()` | 問い合わせと調査の関連 |
| `createReactionPendingRelation()` | リアクション待ちの関連 |

関数の具体的な引数・戻り値・実装方法は、別途設計する。

### 6.6 IDの扱い

問い合わせ番号、調査番号、問い合わせ調査番号は、シーケンスの現在値を予測してはならない。

INSERTの `RETURNING` またはAPIレスポンスから、実際に採番された番号を取得して使用する。

テストデータ作成関数は、作成したレコードの実際のIDを戻り値として返す。

シーケンスに欠番が生じても問題ないものとする。

### 6.7 後片付け

各テスト終了後、次の業務データを削除する。

- ログインセッション
- 問い合わせ調査
- 調査
- 問い合わせ

職員・職員認証情報は削除しない。

削除順序は外部キー制約を考慮する。

IDENTITYのシーケンスはリセットせず、採番値を維持する。

## 7. 実行・管理方針

### 7.1 実行順序

テストは直列実行とする。

同一DBを複数テストが同時に初期化・後片付けすることを防ぐ。

### 7.2 テストの前後処理

各テストは以下の流れで実行する。

1. E2E DBへの接続を確認する。
2. テスト開始前の基準状態を整える。
3. 必要なテストデータを作成する。
4. Playwrightで画面操作を実行する。
5. 画面表示・業務結果を検証する。
6. 作成した業務データとセッションを削除する。
7. 基準状態に戻ったことを確認する。

テストが失敗した場合でも後片付けが実行されるようにする。

### 7.3 テストデータの検証

画面表示だけで判断できない業務上の重要な結果は、E2E DBのデータを確認する。

特に以下はDB上の状態も確認する。

- 問い合わせの引き受け・完了日時と担当者
- 問い合わせの状態導出
- 調査状態
- 問い合わせ調査状態
- NG回答時の移行先調査と関連
- 調査全体の断念時の関連状態

ただし、画面操作を伴わないAPIの詳細な検証はpytestの責務とする。

## 8. 実装の進め方

仕様書確定後、次の順番で実装する。

| 順番 | 作業 | 完了条件 |
|---|---|---|
| 1 | E2E DBの基準状態整備 | 共通職員・認証情報があり、業務データが0件 |
| 2 | DB初期化・後片付け処理 | テスト前後で基準状態に戻せる |
| 3 | テストデータ作成処理 | 必要な業務状態のデータを共通関数で作成できる |
| 4 | ログイン共通処理 | 職員を切り替えてログインできる |
