# 20261007午後_02_業務フロー・状態遷移

## 1. 基本方針

本システムでは、

- 問い合わせ全体の状態
- 問い合わせに関連する個々の問題の状態

を分離して管理する。

問い合わせ全体は、

1. 引き受け待ち
2. 対応中
3. 対応完了

の3状態とする。

「具体的な問題の調査が始まったかどうか」は問い合わせ全体の状態には使用せず、`問い合わせ問題` において管理する。

---

# 2. 問い合わせ全体の状態

| 状態 | 判定条件 | 意味 |
|---|---|---|
| 引き受け待ち | 引き受け日時＝NULL | 対応担当者がまだ引き受けていない |
| 対応中 | 引き受け日時≠NULL かつ 対応完了日時＝NULL | 対応担当者が引き受け、対応責任を持っている |
| 対応完了 | 対応完了日時≠NULL | 問い合わせ全体の対応が完了した |

問い合わせ状態を独立したカラムとして保存しない。

---

# 3. 問い合わせ受付時

問い合わせを受け付けたら、受付担当者は受付時の処理を判断する。

選択肢は、

1. 即時解決
2. 要調査
3. 他所属へ案内

の3つとする。

---

# 4. 即時解決のフロー

```text
問い合わせ受付
    ↓
即時解決
    ↓
対応完了
```

登録時点で、

```text
引き受け日時 = NULL
対応完了日時 = 登録日時
```

とする。

この場合、対応担当者による引き受けは発生しない。

また、問題を登録する必要もない。

---

# 5. 他所属へ案内のフロー

```text
問い合わせ受付
    ↓
他所属へ案内
    ↓
対応完了
```

登録時点で、

```text
引き受け日時 = NULL
対応完了日時 = 登録日時
```

とする。

この場合も、対応担当者による引き受けは発生しない。

問題を登録する必要もない。

---

# 6. 要調査のフロー

```text
問い合わせ受付
    ↓
要調査
    ↓
引き受け待ち
    ↓
対応担当者が引き受ける
    ↓
対応中
    ↓
問題の設定・調査
    ↓
問題ごとの解決確認
    ↓
必要な問題がすべて解決確認済み
    ↓
対応完了
```

---

# 7. 対応担当者が引き受けた時点

対応担当者が問い合わせを引き受けた時点で、

```text
引き受け日時 = 現在日時
```

を設定する。

この時点で問い合わせ全体は「対応中」となる。

重要なのは、

**具体的な問題の調査をまだ開始していなくても、問い合わせ全体としては対応中である**

という点である。

対応担当者は、引き受けた以上、その問い合わせに対応する責任を持つ。

---

# 8. 対応中の問い合わせと問題

対応中の問い合わせは、問題の調査状況によってさらに細かく表現できる。

### ケース1：問題未設定

```text
問い合わせ：対応中
問い合わせ問題：なし
```

まだ具体的な問題を特定できていない状態。

### ケース2：問題1件を調査中

```text
問い合わせ：対応中

問題A：調査中
```

### ケース3：複数問題を調査中

```text
問い合わせ：対応中

問題A：調査中
問題B：調査中
```

### ケース4：一部解決、一部調査中

```text
問い合わせ：対応中

問題A：解決確認済み
問題B：調査中
```

このように、

**問い合わせ全体の状態と問題単位の状態は独立して表現する。**

---

# 9. 問題単位の状態

問題単位では、以下の3つの日時を中心に状態を管理する。

- 調査を終えた日時
- 未解決リアクション日時
- 問題解決確認日時

状態は以下のようになる。

| 調査終了 | 未解決リアクション | 解決確認 | 状態 |
|---|---|---|---|
| NULL | NULL | NULL | 調査中・調査が必要 |
| あり | NULL | NULL | 調査終了・問い合わせ者確認待ち |
| あり | NULL | あり | 問題解決確認済み |
| NULL | あり | NULL | 未解決リアクション後、再調査が必要 |
| あり | あり | NULL | 再調査終了・再度確認待ち |
| あり | あり | あり | 問題解決確認済み |

---

# 10. 問題の調査開始

問題を設定したら、調査を開始する。

初回調査開始時に、

```text
調査開始日時
```

を設定する。

問題単位の状態としては、

```text
調査を終えた日時 = NULL
```

であるため、「調査中・調査が必要」と判断する。

---

# 11. 調査終了

調査が一旦終了したら、

```text
調査を終えた日時 = 現在日時
```

とする。

この時点では、まだ問い合わせ者が「解決した」と確認していないため、

```text
問題解決確認日時 = NULL
```

であれば、「問い合わせ者確認待ち」となる。

---

# 12. 問い合わせ者による解決確認

問い合わせ者が問題解決を確認した場合、

```text
問題解決確認日時 = 現在日時
```

とする。

これにより、その問題は「問題解決確認済み」となる。

---

# 13. 未解決リアクション

問い合わせ者から「まだ解決していない」との反応を受けた場合、

```text
未解決リアクション日時 = 現在日時
調査を終えた日時 = NULL
```

とする。

これにより、問題は再び「調査中・再調査が必要」となる。

---

# 14. 再調査

未解決リアクション後は再調査を行う。

再調査開始時には、

```text
調査開始日時
```

を現在の調査サイクルの開始日時として更新する。

再調査終了時には、

```text
調査を終えた日時
```

を再設定する。

その後、再び問い合わせ者による解決確認を行う。

---

# 15. 問題解決確認の繰り返し

問題については、

```text
調査
 ↓
調査終了
 ↓
問い合わせ者確認
 ├─ 解決 → 問題解決確認
 │
 └─ 未解決
      ↓
    再調査
      ↓
    調査終了
      ↓
    再度確認
```

というループを許容する。

---

# 16. 複数問題の場合

一つの問い合わせに複数の問題がある場合、それぞれを独立して管理する。

例えば、

```text
問い合わせA
 ├─ 問題1：解決確認済み
 ├─ 問題2：調査中
 └─ 問題3：確認待ち
```

の場合、問い合わせ全体は対応中である。

問題1が解決していても、問題2・問題3が残っているため、問い合わせ全体は完了しない。

---

# 17. 問い合わせ全体の完了

問い合わせに必要な問題がすべて解決確認済みとなった場合、問い合わせ全体を完了する。

その時点で、

```text
対応完了日時
```

を設定する。

対応完了日時は、最後に必要な問題について問題解決確認が行われた日時とする。

したがって、

```text
最後の問題解決確認
        ↓
問い合わせ全体の対応完了
```

となる。

---

# 18. 問い合わせ状態と問題状態の分離

今回の設計では、以下を明確に分離する。

### 問い合わせ全体

```text
引き受け待ち
対応中
対応完了
```

### 問題単位

```text
調査中
調査終了・確認待ち
解決確認済み
未解決による再調査
```

この分離により、

「問い合わせは対応中だが、具体的な問題はまだ設定されていない」

という状態も自然に表現できる。

---

# 19. 完了後の再問い合わせ

一度対応完了となった問い合わせについて、後日新しい問い合わせや反応があった場合、過去の問い合わせを再び対応中には戻さない。

新しい問い合わせとして登録する。

```text
過去の問い合わせ
    ↓
対応完了
    ↓
後日、新しい問い合わせ
    ↓
新しい問い合わせ番号
```

これにより、一つの問い合わせのライフサイクルを保持する。

---

# 20. 対応担当者変更

対応中の問い合わせについて、必要に応じて対応担当者を変更できる。

変更時には、

- 現在の対応担当者を更新
- 対応担当者変更履歴を登録

する。

変更履歴には、

- 問い合わせ番号
- 変更日時
- 変更後の対応担当者
- 変更処理を行った職員

を保存する。

---

# 22. 状態判定ルール

問い合わせ全体の状態は、状態カラムを持たず、日時から判断する。

```text
引き受け日時 IS NULL
    → 引き受け待ち

引き受け日時 IS NOT NULL
AND
対応完了日時 IS NULL
    → 対応中

対応完了日時 IS NOT NULL
    → 対応完了
```

問題単位の状態についても、状態カラムを持たず、問題単位の日時から判断する。

---

# 23. 設計上の重要な分離

本システムでは、以下を別の概念として扱う。

### 対応担当者が問い合わせを引き受けた

```text
引き受け日時
```

### 問題について調査を開始した

```text
問い合わせ問題.調査開始日時
```

### 問題の調査を一旦終えた

```text
問い合わせ問題.調査を終えた日時
```

### 問題が解決したことを問い合わせ者が確認した

```text
問い合わせ問題.問題解決確認日時
```

### 問い合わせ全体の対応が完了した

```text
問い合わせ.対応完了日時
```

これらを混同しないことを、本システムの重要な設計方針とする。
