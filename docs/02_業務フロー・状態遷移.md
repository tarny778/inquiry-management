# 20261008_02_業務フロー・状態遷移

## 1. 基本方針

本システムでは、

- 問い合わせ全体の状態
- 問い合わせ問題の状態

を分離して管理する。

問い合わせ全体は、

1. 引き受け待ち
2. 対応中
3. 対応完了

の3状態とする。

一方、問い合わせ問題は、

1. 調査中
2. リアクション待ち
3. 調査無事終了
4. 調査断念

の4状態とする。

問い合わせ全体の状態と問い合わせ問題の状態は独立して管理する。

「具体的な問題の調査が始まったかどうか」は問い合わせ全体の状態には使用せず、`問い合わせ問題` において管理する。

---

# 2. 問い合わせ全体の状態

問い合わせ全体の状態は、状態を独立したカラムとして保存せず、日時から判断する。

| 状態 | 判定条件 | 意味 |
|---|---|---|
| 引き受け待ち | 引き受け日時 IS NULL かつ 対応完了日時 IS NULL | 対応担当者がまだ引き受けていない |
| 対応中 | 引き受け日時 IS NOT NULL かつ 対応完了日時 IS NULL | 対応担当者が引き受け、対応責任を持っている |
| 対応完了 | 対応完了日時 IS NOT NULL | 問い合わせ全体の対応が完了した |

問い合わせ全体の状態を表す `問い合わせ状態` カラムは設けない。

---

# 3. 問い合わせ受付時

問い合わせを受け付けたら、受付担当者は受付時の処理を判断する。

選択肢は、

1. 即時解決
2. 要調査
3. 他所属へ案内

の3つとする。

---

# 4. 即時解決のフロー

```text
問い合わせ受付
    ↓
即時解決
    ↓
対応完了
```

登録時点で、

```text
引き受け日時 = NULL
対応完了日時 = 登録日時
```

とする。

この場合、対応担当者による引き受けは発生しない。

また、問い合わせ問題を登録する必要もない。

---

# 5. 他所属へ案内のフロー

```text
問い合わせ受付
    ↓
他所属へ案内
    ↓
対応完了
```

登録時点で、

```text
引き受け日時 = NULL
対応完了日時 = 登録日時
```

とする。

この場合も、対応担当者による引き受けは発生しない。

問い合わせ問題を登録する必要もない。

---

# 6. 要調査のフロー

```text
問い合わせ受付
    ↓
要調査
    ↓
引き受け待ち
    ↓
対応担当者が引き受ける
    ↓
対応中
    ↓
問題の設定・調査
    ↓
問い合わせ問題ごとの対応
    ↓
対応担当者が問い合わせ全体の対応完了を判断
    ↓
対応完了
```

問い合わせ問題の状態と問い合わせ全体の状態は独立して管理する。

---

# 7. 対応担当者が引き受けた時点

対応担当者が問い合わせを引き受けた時点で、

```text
引き受け日時 = 現在日時
```

を設定する。

この時点で問い合わせ全体は「対応中」となる。

重要なのは、

**具体的な問題の調査をまだ開始していなくても、問い合わせ全体としては対応中である**

という点である。

対応担当者は、引き受けた以上、その問い合わせに対応する責任を持つ。

---

# 8. 対応中の問い合わせと問い合わせ問題

対応中の問い合わせは、問い合わせ問題の設定・調査状況によってさらに細かく表現できる。

### ケース1：問題未設定

```text
問い合わせ：対応中
問い合わせ問題：なし
```

まだ具体的な問題を特定できていない状態。

### ケース2：問題1件を調査中

```text
問い合わせ：対応中

問題A：調査中
```

### ケース3：複数問題を調査中

```text
問い合わせ：対応中

問題A：調査中
問題B：調査中
```

### ケース4：一部の問題が終了し、一部が対応中

```text
問い合わせ：対応中

問題A：調査無事終了
問題B：調査中
```

### ケース5：一部の問題が終了し、一部がリアクション待ち

```text
問い合わせ：対応中

問題A：調査無事終了
問題B：リアクション待ち
```

このように、

**問い合わせ全体の状態と問い合わせ問題の状態は独立して表現する。**

---

# 9. 問い合わせ問題の状態

問い合わせ問題には、`問い合わせ問題状態` カラムを設ける。

状態は以下の4つとする。

| 状態値 | 状態名 | 意味 |
|---:|---|---|
| 1 | 調査中 | 問題について調査または再調査を行っている |
| 2 | リアクション待ち | 調査結果を提示し、問い合わせ者からの反応を待っている |
| 3 | 調査無事終了 | 問い合わせ者からOKを受け、問い合わせ問題との関係を終了した |
| 4 | 調査断念 | この問い合わせについて、問題との関連調査を断念した |

問い合わせ問題の状態は、日時の組み合わせから推測するのではなく、`問い合わせ問題状態` によって管理する。

一方、

- 調査開始日時
- 調査を終えた日時
- 最新NG日時
- リアクション要求最新日時

は、それぞれの業務イベントが発生した日時を記録する。

---

# 10. 問い合わせ問題の調査開始

問題を設定し、調査を開始したら、

```text
問い合わせ問題状態 = 1（調査中）
```

とする。

初回調査開始時に、

```text
調査開始日時 = 現在日時
```

を設定する。

`調査開始日時` は、その問い合わせ問題について最初に調査を開始した日時を保持する。

再調査を行う場合も、この日時は更新しない。

---

# 11. リアクション要求

調査担当者が調査結果をまとめ、問い合わせ者に解決状況の確認を求める。

この時点では、問い合わせ者による確認がまだ完了していないため、問い合わせ問題との関係は終了していない。

そのため、

```text
問い合わせ問題状態 = 2（リアクション待ち）
調査を終えた日時 = NULL
リアクション要求最新日時 = 現在日時
```

とする。

重要なのは、

**リアクションを要求した時点では、`調査を終えた日時` は設定しない**

ことである。

`調査を終えた日時` は、問い合わせ者からOKを受けて問い合わせ問題との関係が最終的に終了した時点、または調査を断念した時点で設定する。

---

# 12. 問い合わせ者がOKした場合

問い合わせ者から「解決した」とのOKを受けた場合、

```text
問い合わせ問題状態 = 3（調査無事終了）
調査を終えた日時 = 現在日時
```

とする。

この時点で、その問い合わせ問題についての対応関係が終了したものとする。

`調査を終えた日時` は、

**問い合わせ者がOKを返したことによって、問い合わせ問題との関係が最終的に終了した日時**

を表す。

ただし、問い合わせ全体の対応完了を意味するものではない。

---

# 13. 問い合わせ者がNGした場合

問い合わせ者から「まだ解決していない」とのNGを受けた場合、

```text
問い合わせ問題状態 = 1（調査中）
最新NG日時 = 現在日時
```

とする。

この時点では、問い合わせ問題は再調査が必要な状態である。

`調査を終えた日時` は、もともと NULL であるため、NGによってNULLに戻す処理は行わない。

また、

```text
調査開始日時
```

は変更しない。

`調査開始日時` は、その問い合わせ問題について最初に調査を開始した日時を保持する。

`現在の調査状況` は対応担当者が入力する自由記入項目であり、未解決リアクションを受けたことだけを理由としてシステムが自動的に書き換えることはしない。

問題テーブルに登録された、

```text
問題の原因
情シス側での対応
問い合わせ者側で必要な対応
```

についても、問い合わせ者からNGを受けたことだけを理由として削除・NULL化しない。

---

# 14. 再調査

未解決リアクション後は、問い合わせ問題を再び「調査中」として再調査を行う。

再調査開始時には、

```text
調査開始日時
```

を更新しない。

再調査では、必要に応じて問題の原因・対応を再検討する。

問題の知識内容を更新した場合は、

```text
問題の原因
情シス側での対応
問い合わせ者側で必要な対応
原因と対応の最新更新日時
```

を更新する。

再調査の結果、問い合わせ者に再度確認を求める場合は、

```text
問い合わせ問題状態 = 2（リアクション待ち）
リアクション要求最新日時 = 現在日時
```

とする。

この時点でも、

```text
調査を終えた日時 = NULL
```

である。

その後、問い合わせ者からOKを受けた場合に、

```text
問い合わせ問題状態 = 3（調査無事終了）
調査を終えた日時 = 現在日時
```

とする。

したがって、再調査後は、

```text
再調査
  ↓
原因・対応の再検討
  ↓
リアクション要求
  ↓
リアクション待ち
  ↓
問い合わせ者による確認
```

という流れになる。

---

# 15. 調査断念

問い合わせについて問題との関連調査を継続することが適切でないと判断した場合、調査を断念できる。

その場合、

```text
問い合わせ問題状態 = 4（調査断念）
調査を終えた日時 = 現在日時
```

とする。

調査断念も、問い合わせ問題との関係を終了させる業務上の判断である。

したがって、調査断念時には `調査を終えた日時` を記録する。

---

# 16. 問題に対するOK・NGの繰り返し

問い合わせ問題については、

```text
調査中
  ↓
リアクション要求
  ↓
リアクション待ち
  ├─ OK → 調査無事終了
  │
  └─ NG → 調査中
             ↓
           再調査
             ↓
        リアクション要求
             ↓
        リアクション待ち
             ↓
        OK または NG
```

というループを許容する。

NGを受けた場合、再調査を行った後、再度リアクションを要求できる。

---

# 17. 複数問題の場合

一つの問い合わせに複数の問題がある場合、それぞれの問い合わせ問題を独立して管理する。

例えば、

```text
問い合わせA
├─ 問題1：調査無事終了
├─ 問題2：調査中
└─ 問題3：リアクション待ち
```

の場合、問い合わせ全体は「対応中」である。

また、

```text
問い合わせA
├─ 問題1：調査無事終了
├─ 問題2：調査無事終了
└─ 問題3：調査無事終了
```

となった場合でも、問い合わせ全体の「対応完了」を自動的には設定しない。

問い合わせ全体の対応完了は、対応担当者が問い合わせ全体を確認した上で明示的に行う。

---

# 18. 問い合わせ全体の対応完了

対応担当者が、問い合わせ全体について必要な対応が終了したと判断した場合、「対応完了」を実行する。

その時点で、

```text
対応完了日時 = 現在日時
```

を設定する。

これにより、問い合わせ全体は「対応完了」となる。

対応完了日時は、

**対応担当者が問い合わせ全体の対応完了を実行した日時**

を表す。

したがって、

```text
最後の問い合わせ問題が調査無事終了
        ↓
対応担当者が問い合わせ全体を確認
        ↓
「対応完了」を実行
        ↓
対応完了日時 = 現在日時
```

となる。

問い合わせ問題の「調査無事終了」と、問い合わせ全体の「対応完了」は別の業務イベントである。

---

# 19. 対応完了後の対応再開

対応完了後、一定期間を「対応再開依頼受付期間」とする。

この期間内に問い合わせ者から再対応の依頼があった場合は、同じ問い合わせを再開する。

再開時には、

```text
対応完了日時 = NULL
```

とする。

これにより、問い合わせ全体は再び「対応中」となる。

再開後は、現在の対応担当者へ再対応を通知する。

再開時には新しい問い合わせ番号を発行せず、元の問い合わせ番号を維持する。

---

# 20. 対応再開依頼受付期間終了後の新しい問い合わせ

対応再開依頼受付期間を過ぎた後に、新たな問い合わせや対応依頼が発生した場合は、過去の問い合わせを再開しない。

新しい問い合わせとして登録する。

```text
過去の問い合わせ
    ↓
対応完了
    ↓
対応再開依頼受付期間終了
    ↓
新しい問い合わせ
    ↓
新しい問い合わせ番号
```

これにより、一つの問い合わせについてのライフサイクルを保持する。

---

# 21. 対応担当者変更

対応中の問い合わせについて、必要に応じて対応担当者を変更できる。

変更時には、

- 現在の対応担当者を更新
- 対応担当者変更履歴を登録

する。

変更履歴には、

- 問い合わせ番号
- 変更日時
- 変更後の対応担当者
- 変更処理を行った職員

を保存する。

---

# 22. 状態遷移全体

問い合わせ全体と問い合わせ問題の状態遷移を分けて管理する。

### 問い合わせ全体

```text
                    問い合わせ受付
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
          即時解決       要調査       他所属へ案内
             │            │            │
             │            ▼            │
             │        引き受け待ち       │
             │            │            │
             │       引き受ける         │
             │            │            │
             │            ▼            │
             │         対応中           │
             │            │            │
             │            │            │
             │            ▼            │
             │     対応担当者が         │
             │   「対応完了」を実行     │
             │            │            │
             └────────────┼────────────┘
                          ▼
                       対応完了
                          │
                 ┌────────┴────────┐
                 │                 │
       再開受付期間内          期間終了後
                 │                 │
                 ▼                 ▼
             対応中へ戻る       新しい問い合わせ
```

### 問い合わせ問題

```text
                 問題を設定
                     ↓
                   調査中
                     │
              リアクション要求
                     ↓
              リアクション待ち
                │           │
               OK           NG
                │           │
                ▼           ▼
          調査無事終了     調査中
                              │
                            再調査
                              │
                              └──→ リアクション要求
                                      ↓

調査中
  │
  └── 調査断念 → 調査断念
```

# 23. 状態判定ルール

## 23-1. 問い合わせ全体

問い合わせ全体の状態は、状態カラムを持たず、日時から判断する。

```text
引き受け日時 IS NULL
AND
対応完了日時 IS NULL
    ↓
引き受け待ち
```

```text
引き受け日時 IS NOT NULL
AND
対応完了日時 IS NULL
    ↓
対応中
```

```text
対応完了日時 IS NOT NULL
    ↓
対応完了
```

## 23-2. 問い合わせ問題

問い合わせ問題の状態は、日時から判断しない。

`問い合わせ問題状態` カラムによって管理する。

```text
1 → 調査中
2 → リアクション待ち
3 → 調査無事終了
4 → 調査断念
```

日時は、状態そのものではなく、各業務イベントの発生日時を記録する。

---

# 24. 設計上の重要な分離

本システムでは、以下を別の概念として扱う。

### 対応担当者が問い合わせを引き受けた

```text
問い合わせ.引き受け日時
```

### 問題について最初に調査を開始した

```text
問い合わせ問題.調査開始日時
```

### 問い合わせ者へリアクションを要求した

```text
問い合わせ問題.リアクション要求最新日時
```

### 問い合わせ者からNGを受けた

```text
問い合わせ問題.最新NG日時
```

### 問い合わせ問題との関係を最終的に終了した

```text
問い合わせ問題.調査を終えた日時
```

この日時は、問い合わせ者からOKを受けて「調査無事終了」となった場合、または「調査断念」となった場合に設定する。

リアクション要求時点では設定しない。

### 問い合わせ全体の対応を完了した

```text
問い合わせ.対応完了日時
```

これは、対応担当者が問い合わせ全体の対応完了を明示的に実行した日時を記録する。

これらを混同しないことを、本システムの重要な設計方針とする。

---

# 25. 状態管理と日時管理の基本原則

本システムでは、

**状態と日時を同じものとして扱わない。**

問い合わせ全体については、`引き受け日時` と `対応完了日時` から状態を判断する。

一方、問い合わせ問題については、`問い合わせ問題状態` によって状態を管理し、日時は業務イベントを記録する。

したがって、

```text
問い合わせ全体
    → 日時から状態を判断

問い合わせ問題
    → 状態カラムで状態を管理
    → 日時はイベント記録
```

とする。

この設計により、

- 問い合わせを引き受けた
- 問題の調査を開始した
- 問い合わせ者へリアクションを要求した
- 問い合わせ者からNGを受けた
- 問い合わせ問題との関係を終了した
- 問い合わせ全体の対応を完了した

という異なる業務イベントを、それぞれ正しく記録できる。
